# OS-PERFLATCH: on the unit a Perform filter slot pressed with the pad and let go again ended at the release (an injected pad release), though the header says "latched until another row". This is the simulator
# half of that check, with the real engine: one looped noise note on T1 (a long note; its brightness shows the filter), T1 switched on in the bank, slot 4 (LOWPASS, pad 15 = its first row).
# What the code does, and this scenario holds it (new Community OS behaviour, OS-PERF2 / seq/perform.h):
#   1. A value turned in with the encoder while the pad is held is the LIVE value only (not in EDIT): the release reloads the row's stored value, which is 0 = no FX, so the filter ENDS with the pad. That is the
#      unit's result, by design, not a latch failure: PerformBank::pad_up (seq/src/perform.cpp) "what the encoder made of the value while the pad was held does not outlive the pad". The header hint "latched until
#      another row" is true of a row that holds a stored value. KNOWN CASE: pinned below as the bright window after the release.
#   2. With EDIT on (Rec) the encoder STORES the value in the row: the release leaves the filter on at the stored value (latched), until another row of the slot or row 0 is pressed. The dark window.
#   3. Row 0 of the slot (pad 3) ends it: bright again.
#   4. A second tap of the same pad while it is latched does NOT release it (OS-CLEANUP, QA-PRF-190: by design; the unit finding "a second tap did not release a held LFO row, only RESET did"). The slots page has no
#      tap-again-ends rule (the DJ page's LATCH has one, QA-PRF-116 / 126): the tap selects the row that is already the slot's. The dark window after the second tap, before row 0.
document sound
audio on
wait 30

# T1: the NOISE instrument (2), one note on the first step of the pattern, a looped sample that keeps sounding.
tap rec
action cursor.jump_fraction 0
action instrument.select 2
pad 12
assert model pat.1.0.0.instr=2
tap rec

tap performance
press shift
pad 0
release shift
# OS-PRFDEFAULTS: a new project's LOWPASS row 1 holds -30, not 0. The cases below are about a row that holds 0, so the row is made 0 first (EDIT on, +30, EDIT off); this is before the render, so no
# window moves. (The first row with its default is the pro session's step 9.)
tap rec
pad 15 down
wait 20
encoder +30
wait 20
pad 15 up
wait 20
tap rec
wait 20
render latch 1570
tap play

# live value only: held, the filter bites; released, it ends (known case 1)
pad 15 down
wait 20
encoder -30
wait 150
pad 15 up
wait 250
# EDIT on: the same turn is stored, the release leaves the filter on (2)
tap rec
pad 15 down
wait 20
encoder -30
wait 100
pad 15 up
wait 20
tap rec
wait 300
# a second tap of the SAME pad keeps it (4): the tap selects the row that is already the slot's, so the filter stays on at its stored value; only another row, row 0 or RESET ends it
pad 15 down
wait 20
pad 15 up
wait 280
# row 0 of the slot ends it (3)
pad 3
wait 300
tap play
wait 1
