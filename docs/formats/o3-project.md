Code: model `model` (`o3os::model`), format `formats/native` (`o3os::formats::native`), Python reference `tools/o3project.py`. Tests: `tests/model_test.cpp`, `native_format_test.cpp`, `native_fuzz_test.cpp`, ctest `project_python`.

A project is one file. Samples stay as WAV files next to it; the file stores relative paths (see "Samples").

## 1. Conventions

- **Big-endian.** Every multi-byte integer is big-endian, as in IFF. Floats are IEEE-754 binary32 stored as their 32-bit pattern (also big-endian); the model never holds NaN or infinity (a file that does is rejected), so the pattern is the value.
- **Text.** `str` is one length byte followed by that many bytes. No terminator, no NUL inside (a NUL is an error), no encoding is enforced (UTF-8 is expected; the core does not look). Maximum lengths are in section 8.
- **Chunk id** is four ASCII characters in `0x20..0x7E`.
- **Chunk** = id (4) + payload length `n` (u32) + payload (`n` bytes) + one zero pad byte when `n` is odd, so every chunk starts at an even offset. The length does not include the pad.
- **Chunk version** is the first u16 of every payload of a known chunk: major in the high byte, minor in the low byte. All chunks are `0x0100` (1.0) in this version except `INST`, which is 1.1 (the sample rate) or, for an instrument that chose its playback engine, 1.2, or, for an instrument one of whose MIDI fields or VEL> is not its default, 1.3, or, for an instrument with an LFO of the Sine shape, 1.4 (OS-LFOSINE: the 1.3 layout, no new byte), or, for a Sample instrument with the stereo flag, 1.5 (OS-STEREO step 2: the 1.3 layout and one byte), or, for an instrument with a loop of 2 or more (the writer's gate) or a non-zero WT byte, 1.6 (OS-CEWTENV W1: the 1.5 layout and twelve bytes), or, for a Sample instrument with the play-thru flag, 1.7 (OS-CEPLAYTHRU P1: the 1.6 layout and one byte), or, for a Module instrument with a RATE other than 0, 1.8 (OS-MODRATE S3: the 1.7 layout and one byte), or, for a Sample or Module instrument with a non-zero CC A..F byte (a CC letter), 1.9 (OS-PARAMAUTO S1: the 1.8 layout whole, no new byte); and `PERF` and `SCEN`, which are 1.2 when a slot holds PLAYMODE (id 18) with a value 4..23, the custom play orders (OS-PERFMODES M3), 1.1 when a slot holds the Perform FX 20 or 21 (OS-PERFFX P1) and 1.0 otherwise; and `APPM`, which is 1.1 when more than six apps are stored (OS-APPUX S3) and 1.0 otherwise. The gates are independent: each chunk is bumped by its own condition only. A reader reads it **before** any length rule (rules for versions in section 3, "Versions").

## 2. Container

```
"FORM"  u32 length   "O3PJ"   chunk chunk ... chunk
```

`length` counts everything after the length field itself: the 4 bytes `O3PJ` plus all chunks with their headers and pads. It must be even and at least 4. The file is `length + 8` bytes; bytes after that are ignored (the reader never looks at them).

Order of chunks, as written:

| Chunk | Count | Content |
|---|---|---|
| `PHDR` | 1, first | project header, master section |
| `TRAK` | 1 | the 16 track slots |
| `MODR` | 1 | module references |
| `SONG` | 1 | order list |
| `PATT` | 0..128 | one per pattern (with its per-track lengths), ascending id |
| `INST` | 0..64 | one per instrument, ascending slot |
| `SETS` | 0..1 | the project's settings (OS-002d), only when one is not its default |
| `LRNB` | 0..1 | the project's MIDI Learn bindings (OS-002d), only when one is in use |
| `MIDI` | 0..1 | the project's MIDI routing, offsets and CC numbers (OS-004d), only when the project has them |
| `USBS` | 0..1 | the USB mode, profile and stem map (OS-004d), only when the project has them; 1.1 for 4 or 6 outputs (OS-USBOUTS) |
| `MIXR` | 0..1 | the mixer's routing matrix, OUT mode and levels (OS-004d), only when the project has them |
| `PERF` | 0..1 | the twelve Perform slots (OS-004d), only when the project has them; 1.2 for a PLAYMODE slot with a value 4..23 (OS-PERFMODES M3), 1.1 for the FX 20 or 21 (OS-PERFFX P1) |
| `APPM` | 0..1 | the parameters of the SD apps the project remembers (OS-004d), only when there are some |
| `NOTE` | 0..1 | the note-entry settings: root, scale, octave, SCALE LOCK and JUMP (OS-PERSIST2), only when the project has them; 1.1 for a scale outside the panel's twelve (OS-SCALES28) |
| `MUTE` | 0..1 | the MUTE MODE of each track (OS-PERSIST2), only when the project has them |
| `SCEN` | 0..1 | the Perform scenes 1..3 and LATCH (OS-PERSIST2), only when the project has them; 1.2 for a stored scene's PLAYMODE slot with a value 4..23 (OS-PERFMODES M3), 1.1 for the FX 20 or 21 (OS-PERFFX P1) |
| `SNFX` | 0..1 | the send effects' controls of the MASTER FX page (OS-PERSIST2), only when the project has them |
| `LAW ` | 0..1 | the instrument volume law (OS-BUG-PASTE24), only when it is the 1.1.14 table (law 1) |
| `INSX` | 0..1 | the inserts: effect modules on the track strips and the master (OS-INSFX S3a), only when the project has one |
| `MEVT` | 0..1 | the MIDI take lanes: recorded events per pattern track (OS-MIDIREC-P1 S1), only when the project has one; the last known chunk |
| unknown | 0..16 | chunks this version does not know (the OG formats' `OGPM` and `OGPN` among them), in the order they were read |
| `CRC ` | 1, last | CRC-32 of every byte before this chunk's header |

Reading is stricter than writing only where it protects the model: `PHDR` must be the first chunk of all; known chunks must appear in the order above (only `PATT` and `INST` repeat; `SETS` comes after the last `INST`, `LRNB` after `SETS`, then `MIDI`, `USBS`, `MIXR`, `PERF`, `APPM`, `NOTE`, `MUTE`, `SCEN`, `SNFX`, `LAW `, `INSX`, `MEVT` in that order, each once); `CRC ` must be the last chunk and end exactly at the end of `FORM`. `TRAK`, `MODR` and `SONG` may be absent (defaults: default tracks, no modules, empty song; a module count in `PHDR` must still match). Unknown chunks may appear anywhere after `PHDR`; they are written back after the known chunks (their position among the known ones is not kept).

The pad byte must be zero. Everything else a reader finds wrong is an error (section 7); it never guesses.

**CRC.** CRC-32/ISO-HDLC (the one of zlib, PNG and Ethernet: reflected polynomial `0xEDB88320`, initial value and final xor `0xFFFFFFFF`; the check value of `"123456789"` is `0xCBF43926`) over the bytes from offset 0 up to, not including, the header of the `CRC ` chunk. It therefore covers the `FORM` length field. The `CRC ` payload is `u16 version`, `u32 crc`.

## 3. Chunks

Offsets are payload offsets. `[...]` is a run of the preceding item.

### PHDR (project header)

| Offset | Size | Field | Valid |
|---|---|---|---|
| 0 | 2 | version | `0x01xx` |
| 2 | 1 | active tracks | 1..16 (new project: 12) |
| 3 | 1 | default pattern length | 1..128 (32) |
| 4 | 4 | tempo, BPM x 100 | 4000..80000 (13000 = 130.00) |
| 8 | 1 | swing, percent | 25..75 (50) |
| 9 | 1 | master volume | 0..100 (86) |
| 10 | 1 | dry volume | 0..100 (86) |
| 11 | 1 | reverb volume | 0..100 (86) |
| 12 | 1 | delay volume | 0..100 (86) |
| 13 | 1 | master flags | bit 0 dry mute, 1 reverb mute, 2 delay mute, 3 limiter; bits 4..7 must be 0 |
| 14 | 2 | number of `PATT` chunks | <= 128, must equal the chunks that follow |
| 16 | 1 | number of `INST` chunks | <= 64, must equal |
| 17 | 1 | number of modules | <= 16, must equal the `MODR` entries |
| 18 | 1+n | project name | `str`, <= 32 |

Length 19 + name, so 19..51. Engine FX settings (reverb, delay and limiter parameters) are not stored yet; they arrive with the audio engine as new chunks (older readers keep them as unknown chunks).

### TRAK (track slots)

`u16 version`, `u8 slot count` (1..16; writers always write 16, missing slots keep their defaults), then per slot:

| Size | Field | Valid |
|---|---|---|
| 1 | type | 0 Audio, 1 MIDI, 2 External audio (ADR 0003) |
| 1 | flags | bit 0 mute, bit 1 solo; others 0 |
| 1 | volume | 0..100 (86) |
| 1 | pan | 0..100, 50 centre |
| 1 | output bus | 0 master mix, 1..16 stem buses |
| 1+n | name | `str`, <= 20 |

### MODR (module references, ADR 0002)

`u16 version`, `u8 count` (<= 16), then per module: `u8 ABI major`, `u8 ABI minor`, `str name` (1..31 characters: a file stem in `/modules`; no `/`, `\`, `:`, control characters, and not `.` or `..`; names are unique). Opening a project loads these; a missing one mutes the instruments that name it.

### SONG (order list)

`u16 version`, `u8 length` (0..255), then `length` bytes, each a pattern id 1..255. An id may name a pattern that does not exist (it plays as empty).

### PATT (one pattern)

| Offset | Size | Field | Valid |
|---|---|---|---|
| 0 | 2 | version | |
| 2 | 1 | id | 1..255, unique |
| 3 | 1 | track count | 1..16 (writers: 16) |
| 4 | 1+n | name | `str`, <= 30 |
| | | per stored track, in order: | |
| +0 | 1 | track length (steps that play) | 1..128 |
| +1 | 1 | stored steps `s` | 0..128 |
| +2 | 7 s | steps 0..s-1 | see "Step" |

A pattern always has 16 tracks of 128 steps in memory, and **every track has its own length**, as in the OG file (a length byte per track; nothing requires them equal). Steps past a track's length are kept (lengthening it brings them back). Steps from `s` on are empty: writers store the minimum `s` (up to the last non-empty step, whatever the length), readers accept any `s` up to 128. Tracks beyond the track count are empty and take the project's default pattern length (`PHDR`). There is no pattern-level length in the file or in `Pattern`; `Project::pattern_length(id)` derives one, the longest of the first `active tracks` tracks. Payload at most 5 + 30 + 16 x (2 + 896) = 14,403 bytes.

**Step** (7 bytes, alignment 1, declared in `model/step.h`; the in-memory layout is this layout):

| Byte | Field | Meaning |
|---|---|---|
| 0 | note | 0 empty; 1..128 = note 0..127 plus one (1 = C-0); 253 fade, 254 cut, 255 off; 129..252 reserved, kept |
| 1 | instrument | 0 none; 1..64 = instrument slot + 1 |
| 2 | volume | 0..127; 255 not set |
| 3, 4 | FX 1 type, value | |
| 5, 6 | FX 2 type, value | |

FX types follow ADR 0004: 0 none, 1..42 the OG types, 43..95 core FX (43..62 assigned by amendments 1 and 2, 63..95 free), 96..127 tracker-ce FX (the OG id + 53, amendment 3 / OS-CEFXIDS: inert until defined, shown as `?` and the value), 128..255 declared by the instrument's engine module. Steps are untrusted data (PAR-003): the model and the format keep every byte exactly as written, whatever it means; it is sanitised where it is used. The empty step is `00 00 FF 00 00 00 00`.

### INST (one instrument)

| Offset | Size | Field | Valid |
|---|---|---|---|
| 0 | 2 | version | |
| 2 | 1 | slot | 0..63, unique |
| 3 | 1 | kind | 1 Sample, 2 MIDI, 3 Module (a free slot has no chunk) |
| 4 | 1 | MIDI channel | 1..16 for MIDI, else 0 |
| 5 | 1 | module index | into `MODR` for Module, else 255 |
| 6 | 1+n | name | `str`, <= 32 |
| | 1+n | sample path | `str`, <= 96, relative (see "Samples"), may be empty |
| | 296 | sampler block | below, always present (also for MIDI and Module kinds) |
| | 2 | blob length `b` | 0..256, 0 unless Module |
| | b | module parameter blob | opaque, never interpreted by the core, kept verbatim |
| | 4 | sample rate (version 1.1) | u32, Hz; 0 = not recorded (played at 44,100 Hz, the rate of the PCM in an OG `.pti`); any value is carried, sanitised where it is used |
| | 1 | playback engine (version 1.2, OS-004d) | u8: 0 automatic, 1 Modern, 2 Amiga, 3 12-bit, 4 8-bit; a larger value reads as 0 |
| | 12 | MIDI fields and VEL> (version 1.3, OS-INSTUI S8b + S9) | twelve u8, in this order: velocity 1..127 (default 127), program 0..128 (0 none, else program + 1; 0), out 0..3 (0 the device's MIDI OUT, 1 DIN, 2 USB, 3 both; 0), PB range 0..24 semitones (2: the bend range the Micro-tune FX is sent for as pitch bend, 0 sends none), offset 0..100 ms (0), CC A..F 0..131 (0 the Config page's number, 1..128 controller 0..127, 129 PROG, 130 channel aftertouch, 131 polyphonic aftertouch; 0 each), VEL> 0..100 % (100: the keyboard's velocity as it is; 0 ignores it; between is linear, played = 127 - VEL> / 100 x (127 - velocity)). A value out of its range reads as the field's default |
| | 1 | stereo flag (version 1.5, OS-STEREO step 2) | u8: 0 mono, 1 stereo; a Sample instrument's only (a 1.5 chunk of a MIDI or Module instrument with 1 reads 0 and loads); a value above 1 reads as 0. **New Community OS behaviour** |
| | 12 | WT bytes (version 1.6, OS-CEWTENV W1) | `wt_bend`, `wt_sust` of the six LFO slots, in slot order (u8 each; `Lfo::wt_bend`, `Lfo::wt_sust`): the OG LFO entry's bytes +2/+3, verified parity (tracker-ce@7fd6c2c:core/source/mtStructs.h:629-637). Present only in a 1.6 chunk; an older chunk reads them as 0 and its loop of 2 or 3 as 1. The minor is new Community OS behaviour |
| | 1 | play-thru flag (version 1.7, OS-CEPLAYTHRU P1) | u8: 0 a slice stops at the next slice point, 1 it plays on to the sample end (`Instrument::slice_thru`; OG instrument byte 279, verified parity tracker-ce@7fd6c2c:core/source/mtStructs.h:653-654, :763, read raw with no version rule: core/FileManager/fileManagerInstrument.cpp:663-706). Written only for a Sample instrument with the flag set; an older chunk and a value above 1 read as 0. **New Community OS behaviour** (the minor and the gate) |
| | 1 | module RATE (version 1.8, OS-MODRATE S3) | u8: 0 FULL, 1 = 1/2, 2 = 1/4 (`Instrument::rate`, the value of the module instrument's RATE row; `docs/specs/OS-MODRATE.md` section 3.3). A Module instrument's only: written only for a Module instrument with a RATE other than 0; an older chunk, a value above 2 and a 1.8 chunk of a Sample or MIDI instrument read as 0 (the model's canonical form clears it there; a file is not failed for it). **New Community OS behaviour** |

Length 306 + name + path + b, at most 690, in version 1.0; version 1.1 adds the 4 bytes of the sample rate (310 + name + path + b, at most 694). **INST is written as version 1.1** (OS-002c: a WAV import keeps the rate of the sample, `Instrument::sample_rate`); every other chunk is written as 1.0. A reader that knows 1.1 reads a 1.0 chunk as rate 0 (and rejects a 1.0 chunk with the four bytes: unused bytes). A reader that only knows 1.0 skips the four bytes and says `newer_minor` (the rate is lost on its next save), which is the minor-version rule below working as designed: this is the first chunk to use it.

**INST 1.2 (OS-004d)** appends one byte after the rate: the instrument's playback engine (`Instrument::engine`, which was the struct's padding byte, so the in-memory layout did not change). The stored value is the engine plus one, so that 0 is "automatic", what every instrument was before: the engine follows the instrument (a sample instrument at a Paula rate, 8,287 or 8,363 Hz, that plays as a one shot or a forward loop is Amiga, the rest Modern), 1 Modern, 2 Amiga (Paula: integer period, sample-and-hold, BLEP), 3 Modern with the output rounded to 12 bits, 4 with 8 bits. **The writer writes 1.2 only for an instrument whose engine is not 0 and 1.1 for every other**, so a project that never chose an engine is byte for byte the file it was (and an older reader meets no newer minor in it; a file that does have an engine is read by an older build as a newer minor of INST: the engine is lost on its next save, the instrument is otherwise intact). A reader that knows 1.2 reads a 1.1 chunk as engine 0; a 1.2 chunk is exactly one byte longer than 1.1 (a cut or a spare byte is `Malformed`); a value above 4 (an engine a later version added) reads as 0. The Amiga filter model (A500 / A1200 / LED) is an engine-wide setting of the voices, not an instrument's, and is not stored.

**INST 1.3 (OS-INSTUI S8b + S9)** appends twelve bytes after the engine byte (the table above; `Instrument::midi_velocity`, `midi_program`, `midi_out`, `midi_pb_range`, `midi_offset`, `midi_cc[6]`, `vel_sens`; the struct grew from 704 to 716 bytes). **The engine byte is always present in a 1.3 chunk** (0 for automatic), since the twelve follow it by position. **The writer writes 1.3 only for an instrument one of whose twelve bytes is not its default, 1.2 for an instrument whose engine alone is not automatic, and 1.1 for every other**, so a project that never used the fields is byte for byte the file it was (checked against the build before INST 1.3: the small, state, persist2 and maximal fixtures have the same size and CRC-32; `tests/inst_midi_format_test.cpp`). A reader that knows 1.3 reads a 1.2 or 1.1 chunk as the defaults; a 1.3 chunk is exactly 13 bytes longer than 1.1 (a cut or a spare byte is `Malformed`); a value out of a field's range reads as that field's default (as the engine byte does, so a later version may add values). **An older reader** (INST 1.2 or 1.1, such as the build before OS-INSTUI S8b) meets a newer minor of `INST`: it reads the instrument as far as it knows (the rate, the engine), skips the twelve bytes, reports `newer_minor`, and writes the instrument back as 1.2 / 1.1: the fields are lost on its next save and nothing else of the instrument changes (checked with a reader of the build before INST 1.3 on a 1.3 file). The fields apply to a MIDI instrument (VEL>: a sample instrument); the bytes of the other kind stay at their defaults, except the six CC A..F bytes of a Sample or Module instrument from INST 1.9, which are CC letters (parameter codes; see 1.9 below). **Learn bindings** to the twelve parameters (ids `0x80..0x8B`) are ordinary `LRNB` entries (no change of that chunk): an older reader keeps and writes them back, but has no such parameter, so a control change bound to one does nothing there.

**INST 1.5 (OS-STEREO step 2, `docs/specs/OS-STEREO.md` decision S1; new Community OS behaviour)** appends one byte after the twelve of 1.3: the instrument's stereo flag (`Instrument::stereo`, 0 mono, 1 stereo; the struct grows from 716 to 720 bytes: the stereo byte and three explicit zero `reserved` bytes, so there is no tail padding and a whole-instrument `memcmp` is defined). The layout before it is 1.3's, whole (the engine byte and the twelve MIDI bytes always present, as in 1.4); the Sine LFO gate stays "minor >= 4", so a 1.5 chunk reads shape 5 as Sine. **The writer writes 1.5 only for a Sample instrument with the flag set** (it covers a Sine LFO too), so every project without a stereo instrument is byte for byte the file it was (the existing fixtures' sizes and CRC-32 are pinned: `tests/inst_midi_format_test.cpp`, ctest `project_python`). A reader that knows 1.5 reads an older chunk as 0 and a value above 1 as 0 (as the engine byte does); a 1.5 chunk of a MIDI or Module instrument with the flag at 1 reads 0 and the project loads (the flag is a Sample instrument's, so the reader drops it as it drops a value above 1; `validate_instrument` still refuses it on an in-memory instrument); a 1.5 chunk is exactly 1 byte longer than the same instrument's 1.4 chunk (a cut or a spare byte is `Malformed`). An older reader meets 1.5 as a newer minor, reads the instrument as of 1.4, skips the byte and loses the flag on its next save: the instrument then plays mono, by design. The flag is the instrument's wish: it plays stereo only while the sample bank also holds the side signal (decision S4). **The side signal is a second file, `samples/<stem>_s.wav`** (slice (b), decision S2: the instrument's `sample_path` with `.wav` replaced by `_s.wav`; 16-bit mono PCM at the instrument's rate, exactly as many frames as the mid; S = L - M, M = (L + R) / 2 being the file `sample_path` names, which stays the mid and is read by every other tool). The writer writes the flag only for an instrument whose side file the same save writes (or holds): a flag with no side signal in the bank, or no side file name that fits and is no other instrument's `sample_path`, is saved as 0, so the saved flag is never without its file. A reader that finds the flag and no usable side file (missing, unreadable, not mono, another length or rate than the mid, no room) loads the instrument as a mono sample, clears the flag and counts it (`stereo lost`); the project is never refused for it. **An older build never reads `<stem>_s.wav`** (no instrument names it), plays the mid and loses the flag with its next save, by design; the side file is then left on the card unused. **Known limit.** The reader checks the side file's length and rate, not its content, and a save writes the mid, then the side file, then the project file, each atomically. If the power fails after a new mid is written and before the project file, the old project (flag 1) meets the new mid and the old side file; when the audio kept its length (a same-length edit such as a reverse or a fade) it loads as stereo with a side signal that no longer matches the mid. The mid is never damaged, and the next save rewrites both. A side file that no instrument names any more (the instrument went mono, or was renamed) stays on the card: nothing deletes it. **Names.** An instrument whose side name would be another instrument's `sample_path` (in any case) or longer than the guard's 31 characters is saved mono, with the strip saying `STEREO SAVED MONO: <NAME>`; no save or load ever writes over another instrument's sample file. The Python mirror `tools/o3project.py` knows the flag only (the side file is not part of the project file; the `stereo` fixture of `project_python`).

**INST 1.4 (OS-LFOSINE, `docs/specs/OS-LFOSINE.md`)** adds no field and no byte: its layout is 1.3's whole (the engine byte and the twelve always present), and the version only says that an LFO shape of 5 is **Sine** (the sixth shape; 0 Rev Saw, 1 Saw, 2 Triangle, 3 Square, 4 Random). The writer writes 1.4 only for an instrument one of whose six LFOs has shape 5, so a project that never used Sine is byte for byte the file it was. A reader that knows 1.4 reads a shape of 5 in an older chunk as 2 (Triangle: what it played, the older build holding a larger shape to Triangle), and a shape above 5 in any chunk as 2 (a later shape plays as Triangle); an older reader meets 1.4 as a newer minor with nothing appended, reads it whole, keeps the byte and plays it as Triangle (`tests/lfosine_format_test.cpp`; the Python mirror `tools/o3project.py` does the same).

**INST 1.6 (OS-CEWTENV W1, `docs/specs/OS-CEWTENV.md`)** appends twelve bytes after the stereo byte: `wt_bend` and `wt_sust` of the six LFO slots, in slot order (u8 each; `model::Lfo`'s two bytes that were its padding, so the struct size did not change). They are the OG LFO entry's bytes +2/+3 of a WT slot (loop 2 WT Env, 3 WT LFO): the warp (X in the high nibble, Y in the low one) and the sustain (0 one-shot, 1..99 freeze %) — verified parity, tracker-ce@7fd6c2c:core/source/mtStructs.h:629-637. The layout before them is 1.5's, whole (the engine byte, the twelve MIDI bytes and the stereo byte always present), so 1.6 covers 1.5 and 1.4 too. **The writer writes 1.6 only for an instrument with a loop of 2 or more or a non-zero WT byte** (`model::inst_uses_wt`; the gate is a loop of 2 or more as W1 pinned it — the maximal fixture's random loops — not the exact test, which is what a loop MEANS on read), so every project without WT bytes is byte for byte the file it was (the existing fixtures' sizes and CRC-32 are pinned: ctest `project_python`); within the twelve bytes it writes zeros for a slot whose loop is not 2 or 3. A reader that knows 1.6 reads an older chunk's WT bytes as 0 and its **loop of 2 or 3 as 1** (an LFO: what those files played — they came from a tracker-ce file through an older build, which had already lost the contour and warps; spec assumption A3, new Community OS behaviour), and a WT slot's shape **verbatim** (the contour 0..255; in an older chunk the shape rule of 1.4 applies: above the last shape, Triangle); in a 1.6 chunk it also reads the WT bytes of a slot whose loop is **not** 2 or 3 as 0 (only 2 and 3 are WT slots), so a stray byte in a file cannot force 1.6 on every later save — the next save writes the older minor unless the instrument really has a WT slot. A 1.6 chunk is exactly 12 bytes longer than the same instrument's 1.5 chunk (a cut or a spare byte is `Malformed`). **An older reader** (INST 1.5 or less, such as the build before this slice) meets 1.6 as a newer minor: the twelve bytes are the payload's tail, after every field it knows, so it reads the instrument as of 1.5, skips them, reports `newer_minor`, and writes the instrument back without them on its next save. Round trips: `tests/native_format_test.cpp` (the 1.6 cases), ctest `project_python` (the `wt` fixture: C++ against `tools/o3project.py`, both ways).

**INST 1.7 (OS-CEPLAYTHRU P1, `docs/specs/OS-CEPLAYTHRU.md`)** appends one byte after the twelve WT bytes of 1.6: the instrument's play-thru flag (`Instrument::slice_thru`, 0 a slice stops at the next slice point, 1 it plays on to the sample end in the Slice and Beat Slice modes; the flag is kept for any play mode and ignored outside the two slice modes). The byte is the same one the OG instrument file holds at 279 (verified parity, tracker-ce@7fd6c2c:core/source/mtStructs.h:653-654; that file's byte is an open research question until OS-CECHECK (a), measured 0 in all 70 fixture instruments). The layout before it is 1.6's, whole, so 1.7 covers 1.6, 1.5 and 1.4 too. **The writer writes 1.7 only for a Sample instrument with the flag set**, so every project without the flag is byte for byte the file it was (the existing fixtures' sizes and CRC-32 are pinned: ctest `project_python`; an unflagged WT instrument stays 1.6). A reader that knows 1.7 reads an older chunk as 0 and a value above 1 as 0 (as the stereo byte does); a 1.7 chunk is exactly 1 byte longer than the same instrument's 1.6 chunk (a cut or a spare byte is `Malformed`). **An older reader** (INST 1.6 or less, such as the build before this slice) meets 1.7 as a newer minor: the byte is the payload's tail, after every field it knows, so it reads the instrument as of 1.6, skips it, reports `newer_minor`, and loses the flag on its next save. Round trips: `tests/native_format_test.cpp` (the 1.7 cases), ctest `project_python` (the `playthru` fixture: C++ against `tools/o3project.py`, both ways).

**INST 1.8 (OS-MODRATE S3, `docs/specs/OS-MODRATE.md` section 3.3; new Community OS behaviour)** appends one byte after the play-thru byte of 1.7: the module instrument's RATE (`Instrument::rate`, 0 FULL, 1 = 1/2, 2 = 1/4; the struct stays 720 bytes: the byte was one of its two reserved bytes). The layout before it is 1.7's, whole, so 1.8 covers 1.7 and every older layout too. **The writer writes 1.8 only for a Module instrument whose RATE is not 0**, so every project without a RATE is byte for byte the file it was (the existing fixtures' sizes and CRC-32 are pinned: ctest `project_python`); a Sample or MIDI instrument never writes it (`Project::set_instrument` clears the field for them). A reader that knows 1.8 reads an older chunk as RATE 0 and a value above 2 as 0; a 1.8 chunk is exactly 1 byte longer than the same instrument's 1.7 layout (a cut or a spare byte is `Malformed`). **An older reader** (INST 1.7 or less) meets 1.8 as a newer minor: the byte is the payload's tail, after every field it knows, so it reads the instrument as of 1.7, skips the byte, reports `newer_minor`, and loses the RATE on its next save. Round trips: `tests/native_format_test.cpp` (the 1.8 cases), ctest `project_python` (the `modrate` fixture: C++ against `tools/o3project.py`, both ways).

**INST 1.9 (OS-PARAMAUTO S1, `docs/specs/OS-PARAMAUTO.md` section 3; new Community OS behaviour)** adds no field and no byte: its layout is 1.8's whole, and the version only says that the six `midi_cc` bytes (CC A..F) of a **non-MIDI** (Sample or Module) instrument are **CC letters**: byte L (0 = A .. 5 = F) is the parameter the letter moves when a step FX CC A..F is played, 0 meaning no letter. A Sample instrument's code is the parameter field plus one (1..120, a learnable field 0x00..0x77); a Module instrument's code is the module parameter index plus one (1..32). The letters are project-wide (the lowest instrument slot that holds a letter owns it; a later duplicate is ignored and not rewritten). The writer writes 1.9 only for a non-MIDI instrument with at least one non-zero CC byte, and never for a MIDI instrument (its CC bytes keep the meaning of 1.3: a controller number, 0..131). **Loader:** a non-MIDI instrument read from a chunk older than 1.9 gets its six CC bytes as 0 (no letter), so every older file loads and behaves as before and is written back unchanged (an older chunk never carried letters); a stray non-zero byte of such a chunk (a hand-edited file) is dropped and counted once per instrument in `Report::settings_skipped`. **Older readers:** a reader that knows only up to 1.8 sees a newer minor with nothing appended, keeps the bytes and rewrites them, and the letters do nothing there (new Community OS behaviour). Test: `tests/param_auto_test.cpp`, `tools/o3project.py` (`project_python`).

### SETS and LRNB (OS-002d)

`SETS` is the project's settings (kind `Project`: anti-aliasing, limiter mode, sends mode; snap to zero waits for a sourced default), `LRNB` its MIDI Learn bindings. Layout, rules and the defaults: `docs/formats/o3-settings.md` sections 2, 3 and 6; the same two chunks, read by the same code, are the device settings file. `SETS` is `u16 version`, `u16 count`, `count` x (`u32 ParamId`, `f32 value`), written (all three entries, 28 bytes) only when one setting is not its default; `LRNB` is `u16 version`, `u16 count`, `count` x (`u32 ParamId`, `u8 cc`, `u8 channel`, `u8 mode`, `u8 flags`), written only when a binding is in use (OS-INSFX S7: an insert's parameter is bindable, `ParamKind::Insert`, id index `track * 2 + slot`, 32 for the master insert; an older firmware skips those entries, counts them and drops them on its next save; see `docs/formats/o3-settings.md`). A project with neither is the file it was before they existed (the 186 bytes of section 4). **Reading is tolerant**: an entry for a setting this version does not have, with a value outside its range, or an invalid or conflicting binding is skipped and counted (`Report::settings_skipped`), the setting keeps its default; only a chunk whose length does not fit its count, or a count above 64 in a chunk of this minor version, is `Malformed` (a newer minor with a count above 64 is read as far as 64 and the rest counted as skipped).

### The project-level state (OS-004d): `MIDI`, `USBS`, `MIXR`, `PERF`, `APPM`

State that was runtime only until OS-004d (maintainer decision 2026-10-12: make it persistent at project level). Five new chunks, each version 1.0 with the layouts below (`PERF` is 1.1 when a slot uses the Perform FX 20 or 21; `APPM` is 1.1 when more than six apps are stored). **A chunk is written only when the project has the part** (the model keeps a flag per part, `Project::state_present()`, set by the first `set_midi / set_usb / set_mix / set_perf` and by a file that has the chunk; `APPM` is written when an app is remembered), so the default project is still the 186 bytes of section 4 and every project that never said anything is the file it was. Reading is strict, like `PHDR` and `TRAK` (the one tolerance: in `PERF` an FX id above the table reads as none, with its row and values reset, and a row above 3 as off, so that a later version that adds an FX does not make this one refuse the project; the same rule as `INST`'s engine): a value outside its range, a count the layout does not fit, a part twice or out of order and unused bytes in a chunk of this minor are `Malformed`; a newer minor only appends (read as far as 1.0, the rest skipped at any length, `newer_minor` set, lost on the next save). A file without a chunk reads as the part's defaults (and "absent"); for `PERF` those are the values of the table in `docs/specs/OS-PERFFX.md` section 9, not zeros (below).

`MIDI` (20 bytes): `u16 version`, `u8 out_ports` (bit 0 DIN, bit 1 USB; the ports clock, Start, Continue, Stop and SPP go out on: CLOCK OUT per port), `u8 note_ports` (the ports the notes, CC and program changes of MIDI tracks go out on), `u8 notes_channel` (0..15: where a MIDI event without a channel goes), `u8 follow` (the clock-follow bandwidth: 0 tight, 1 normal, 2 loose), `u8 cc_number[6]` (CC A..F, 0..127 or 255 = unassigned), `i16 in_offset_dms[2]`, `i16 out_offset_dms[2]` (per port DIN, USB, 0.1 ms, -1000..1000). These are the `midi::MidiConfig` fields (`midi/config.h`) that have no row in the settings table or that the project may override; `mode`, `in_port` and `sync_correction` stay the device's.

`USBS` (5 + 2 slots, 7..27 bytes): `u16 version`, `u8 mode` (0 STANDARD, 1 AUDIO), `u8 profile` (0 P2, 1 P8, 2 P10, 3 P11; the engine does not feed P4S, which is not stored), `u8 slots` (must be the profile's channel count: 2, 8, 10, 11), then `u16 mask[slots]`: the sources each stem slot sums, bit i = source i of `audio/stem_map.h` (T1..T12, Master L, Master R, Send A, Send B).

**`USBS` 1.1 (OS-USBOUTS, 2026-10-29: the number of USB outputs is a per-project choice, 4 or 6 outputs added to 2, 8, 10 and 11).** A project with 2, 8, 10 or 11 outputs writes `USBS` **1.0 byte for byte as above** (a build before this one reads and writes it the same). A project with **4 or 6 outputs** writes 1.1, 22 bytes: `u16 version` (0x0101), `u8 mode`, `u8 profile` = 1 (P8), `u8 slots` = 8, `u16 mask[8]`, then **`u8 channels`** (4 or 6). The masks are the real ones in slots 0..channels-1 (the user's map of the 4 or 6 stems, Master L/R last) followed by P8's factory masks for the rest (slots 4..7 for 4 outputs: T5, T6, Master L, Master R; slots 6..7 for 6 outputs: Master L, Master R), so that **a v1.0.x reader, which reads a 1.1 chunk through the newer-minor rule (known part parsed, the rest skipped, `newer_minor` reported), loads the project as P8 (8 outputs) with the real masks first**, and never refuses it (a profile byte 4 or more would refuse the whole project there). A v1.0.x build that saves such a project again writes it as P8: the 4 or 6 count is lost, the project comes back with 8 outputs and the stem map's first slots kept (accepted). A 1.1 reader takes the count: it must be 4 or 6 with profile 1 and 8 slots (anything else, a missing count byte or an unused byte after it is `Malformed`), and the masks past the count are zero. The profile byte of the chunk stays 0..3 in every version (the in-memory `usb::Profile` has P4 = 5 and P6 = 6; P4S = 4 is never stored). The volume of USB RETURN is still not in the chunk (a device setting; the return is presented only below 10 outputs, ADR 0012 amendment 8).

`MIXR` (25 bytes): `u16 version`, `u8 strips` (17), `u8 route[17]` (the routing matrix: bits MAIN 1, CUE 2, SNDA 4, SNDB 8, REC 16, USB 32 of strips T1..T16 and the input strip; the input strip has no USB bit), `u8 ret_route[2]` (where the SNDA / SNDB return goes: bit 0 MAIN, bit 1 CUE), `u8 out_mode` (0 STEREO, 1 MAIN L / CUE R), `u8 cue_level` (0..100), `u8 in_level` (0..100). Track volume, pan, mute, solo and the master levels are the model's own parameters (`TRAK`, `PHDR`) and are not repeated here. Defaults: tracks MAIN + USB, input MAIN + CUE, returns MAIN, STEREO, CUE 100, input 0 (what `MixBoard` and the graph start with).

`PERF` (99 bytes in every version): `u16 version`, `u8 slots` (12), then per slot `u8 fx` (0..19 in version 1.0: `seq::PerfFx`, 0 none; **0..21 in versions 1.1 and 1.2**, which add 20 BITDEPTH 0..15 and 21 OVERDRV 0..100, OS-PERFFX P1; a larger id reads as none), `u8 row` (0..3, the selected row; 0 off; a larger one reads as off) and `i16 value[3]` (rows 1..3, -100..100). **The PLAYMODE slot (id 18) may hold 0..23 in version 1.2** (4..23 are the custom play orders C1..C20, OS-PERFMODES M3): in 1.0 and 1.1 a value above 3 reads as 3 (RND, what every build before OS-PERFMODES M3 played, the bank held it to 0..3), in 1.2 a value above 23 is held to 23. Defaults: slot i holds FX i + 1, row 0, and the three values the table of `docs/specs/OS-PERFFX.md` section 9 gives that FX (OS-PRFDEFAULTS: LOWPASS -30, -60, -90; STUTTER 11, 13, 15; 0 for the FX with no consumer yet; this OS's choice). **A project with no `PERF` chunk reads as these defaults** (maintainer decision 2026-10-23): every project saved before Perform was touched, and the OG, MOD, S3M and MED imports, which used to open with zeros. A chunk that is present keeps exactly the values it stores, 0 included. No byte of the format changes. Which tracks the layer affects, the held slots and the edit place are live state and are not stored; a loaded bank has every FX off (the values are clamped to each FX's own range when the bank takes them). A BITDEPTH value is how many bits are taken away (16 minus the bits that stay), so 0 is the clean sound and ends the FX like every other 0.

**`PERF` and `SCEN` 1.1 (OS-PERFFX P1, decision D5, maintainer 2026-10-19, option A).** The layout and the length are the same in 1.0 and 1.1; the version says which ids are valid. **The writer writes 1.1 only when a slot (for `SCEN`, a slot of a stored scene) holds the id 20 or 21, and 1.0 for every other bank, byte for byte as it always did** (the same pattern as `INST` 1.2: a project that never used the two FX is the file it was, and an older reader meets no newer minor in it). The reader accepts both: in 1.1 an id above 21 reads as none, in 1.0 an id above 19 reads as none (so 20 and 21 in a 1.0 chunk are none, as they always were), and in both the slot's row and values are reset to 0 with it. A 1.1 chunk that holds no 20 or 21 loads, and is written back as 1.0. **An older build** (every build before OS-PERFFX P1: it knows `PERF` and `SCEN` at 1.0 and its last id is 19) meets a 1.1 chunk as a newer minor (section 3, "Versions"): it does not refuse the project; the chunk has the length of 1.0 so it is read whole, every id above 19 reads as none with its row and values reset, `newer_minor` is set (the load line says "newer fields skipped"), and the next save writes the chunk as 1.0 with those slots empty. The other slots are as they were. Readers are safe, but a downgrade through a save is not lossless: the BITDEPTH and OVERDRV slots (and the same ids in the scenes) are lost.

**`PERF` and `SCEN` 1.2 (OS-PERFMODES M3, 2026-11-06).** Again no field, no length and no layout change: the version only says that a PLAYMODE slot (id 18) may hold 4..23, the custom play orders C1..C20 (the orders themselves are not in the file; nothing plays them yet, slice M2). **The writer writes 1.2 only when a slot (for `SCEN`, a slot of a stored scene) holds PLAYMODE with a value 4..23 in any of its three rows, 1.1 when it holds the id 20 or 21, and 1.0 for every other bank, byte for byte as it always did**, so the version written is the lowest that holds the data and a project that never used a C order is the file it was. The reader knows minor 2: in 1.0 and 1.1 a PLAYMODE value above 3 reads as 3 (RND), in 1.2 as it is, a value above 23 held to 23 (the bank holds it to 0..23); nothing is refused that was read before. **An older build** (minor 1 known, as every build before this one) meets a 1.2 chunk as a newer minor: same length, read whole, `newer_minor` set ("newer fields skipped" on the load line), the PLAYMODE value above 3 held to 3 (RND); its next save writes 1.1 or 1.0 with RND. Accepted: a downgrade through a save loses the order, nothing else. Tests: `tests/perf_playorder_format_test.cpp`, ctest `project_python` (the Python reference `tools/o3project.py` agrees on every case; the pinned fixtures keep their sizes and CRC-32).

`APPM` (3..1,015 bytes; **version 1.1** since OS-APPUX S3, 1.0 before): `u16 version`, `u8 count` (1..6 in 1.0, 1..12 in 1.1), then per app `str name` (the module's file stem, 1..31, a safe module name), `u8 abi_major`, `u8 abi_minor` (the ABI the module was built with), `u8 params` (1..32), `f32 value[params]` (finite). Keyed by the module name and its ABI: when an app is launched its entry is applied if the name matches and the ABI major is the same (values past the module's own parameter count are ignored, a missing one keeps its default, every value is clamped by the module's descriptor); an app that is not installed leaves its entry untouched (it is written back as it was). The project remembers the last twelve apps used (OS-APPUX S3: every shipped app stores its rows with `set_own_param`; it was six): a thirteenth drops the oldest, and so does any entry that would take the chunk past 1,015 bytes (one writer piece: six apps of 32 values and 31-byte names are 981 bytes, so a project of such apps keeps the six newest). **Version rule:** the layout of 1.1 is that of 1.0, only the count may be larger. The writer writes **1.0, byte for byte as before, while the project holds six apps or fewer** (an older OS opens such a project), and 1.1 from the seventh; the reader takes 1.0 with at most 6 apps and a length of at most 981 bytes, and 1.1 with at most 12 apps and at most 1,015 bytes (a 1.0 chunk that says seven apps is `Malformed`). An OS that knows only 1.0 reads a 1.1 chunk as a newer minor and refuses it with `APPM: bad app count`, and so refuses the whole project: such a project needs this OS or a newer one (maintainer decision 2026-10-19, option B: the format stays as it is, with no appended tail that would let an older OS skip it; with six apps or fewer stored nothing changes for an older OS). A newer minor (1.2) appends fields: the 1.1 part is read, the rest skipped. Tests: `tests/appm_format_test.cpp` (round trips, the exact bytes, 1.0 as an older OS wrote it, the counts and bounds of each version, the model's byte budget) and `tests/o3project_roundtrip.py` (the Python reference agrees on every case).

**Precedence and when it applies.** Opening a project applies its parts to the runtime from the main loop once the load has ended (`app_main.cpp`, never from an interrupt): MIXR and PERF always (a project without them sets the defaults, so the previous project's routing does not leak; for PERF the defaults are the section 9 values of `docs/specs/OS-PERFFX.md`), MIDI and USBS only when the project has them (without, the device's values stand). The device settings rows 7..11 (CLOCK MODE, MIDI IN, MIDI OUT, IN CHANNEL, OUT CHANNEL, `docs/formats/o3-settings.md`) stay device-level; the MIDI part is applied after them, so **a project's values win when it loads, and the last writer wins afterwards**: a later change of MIDI OUT or OUT CHANNEL in the Config screen overrides the project's out ports and channel until the next load, and every change made to the runtime while a project is open is stored in that project (it becomes unsaved, undo is not affected). **USB**: a project that has `USBS` asks the driver (`usb0::request_mode`, then the stem map once the new descriptor set is attached) for its profile and stem map, and for the **mode of the device setting USB AUDIO** (OS-USBAUDIO, `docs/formats/o3-settings.md` field 17: the unit enumerated in that mode at boot, so the stored `mode` byte no longer decides it: a project saved in AUDIO does not switch a unit whose USB AUDIO is Off, and one saved in STANDARD does not switch it away when it is On; the byte keeps recording the mode the unit was in when the project was saved, and the file is unchanged). A profile different from the boot's (8) re-enumerates the unit in AUDIO (not in STANDARD, which only remembers it), which is the cost of the maintainer's decision, so it is done from the main loop after the load and never twice. Whether the AUDIO descriptors carry the stereo return stream (USB RETURN, OS-USBRET) is **not** part of `USBS` (no byte of the chunk changed): it is the device setting of that name (`docs/formats/o3-settings.md`, field 13), because it depends on what the host and its hubs can carry, not on the song; a project's mode and profile are applied with the setting as it is. **The mode is the device setting's** (USB AUDIO, default On: the unit enumerated in AUDIO at boot; before OS-USBAUDIO every boot was STANDARD and a project's stored mode overrode it); a project without `USBS` leaves the profile and the map as they are. Reading the new chunks never touches the device.

**Older builds.** An older build reads a file with these chunks, keeps the five as unknown chunks (they fit the pool next to a full OG import: 1,152 bytes in at most five chunks against `OGPM` 970 + `OGPN` 12,822 of 16,384; the total with every later chunk is under "Older builds" of the session state) and writes them back byte for byte, in the order it read them; it meets `INST` 1.2 as a newer minor (the engines are lost on its next save). Checked against the build before OS-004d.

### The session state (OS-PERSIST2): `NOTE`, `MUTE`, `SCEN`, `SNFX`

The settings that were runtime only after OS-004d and that a musician sets up and expects to find again (maintainer decision 2026-10-13: persistence for all of them, one design, one format change, additive and backward compatible). **Four new chunks**, by the rule of section 10 ("a new persistent part is a new chunk"): no version bump of any existing chunk, no change to the meaning of any existing field, and an older build keeps them as unknown chunks and writes them back byte for byte. Each is version 1.0 (`0x0100`) and is **written only when the project has the part** (`Project::state_present()` bits 16, 32, 64 and 128, set by the first change of the runtime value or by a file that has the chunk), so a project that never changed any of them is the file it was (the default project is still the 186 bytes of section 4).

**Where each setting lives (the inventory, and why).** "Project" follows the OG file layout where it has an equivalent (`project.mt` holds that value); "device" would be a row of the settings file (`docs/formats/o3-settings.md`).

| Setting | Lived in | Closest field of an OG project file | Now | Where |
|---|---|---|---|---|
| per-track MUTE MODE (Immediate, Bar, Pattern) | `MixBoard::mute_mode[16]`, reset by nothing | none (new, OS-MUTE); the track's mute flag is `TRAK` | project: a property of how the song is played, next to the track's mute | `MUTE` |
| NOTE root, scale, octave, SCALE LOCK | `PatternEdit::entry` (`NoteEntry`, 4 bytes) | the OG project's pad board scale, root note and note offset | project: the key of the song | `NOTE` |

| PERFORM SCENES 1..3 and LATCH | `PerformBank::scenes_`, `latch_`, cleared by a load | none (new, OS-PERF2); the slots a scene snapshots are `PERF` (OS-004d) | project, next to the slots | `SCEN` |
| send effects: DLY PINGPONG, SYNC, RATE, TIME, FEEDBACK; RVB SIZE, DAMPING, PREDELAY, DIFFUSE | `MixBoard::fx[12]` | the OG project's delay feedback, time and parameters and the reverb block (`OGPM` group 3) | project | `SNFX` |
| send effects: DLY TONE, DLY MODE, RVB QUALITY (new in OS-SENDFX) | `MixBoard::fx[12]` | none (new) | project | `SNFX` |

| USB mode, profile, stem map | USB driver, `StemMap` | none | **already persisted** by OS-004d | `USBS` |
| mixer routing, returns, OUT MODE, CUE, IN level; Perform slots; SD app parameters | board, bank, `ModuleUi` | config and project | **already persisted** by OS-004d | `MIXR`, `PERF`, `APPM` |

Inventoried and **not** persisted by this slice: the pads' mode (NOTES, PIANO, TRACKS, ISO, STEP, PATS, VU: a performer's layout, not the song's; its home is a device row, but the device scope has three free rows of 16 and no page for it until the Config slice, so it waits for that); the recorder's configuration (source, gains, monitor, START ON, STOP AT, tap, region, FM frequency: an OG project file holds the source and gains, but they describe the hardware input and the radio region the device, so the project-or-device split is an open maintainer decision); the Sample load screen's wavetable preference (a screen preference); every cursor, page, selection, last-used value and play position (session state: the fields of an OG project file that the importer drops). The Amiga filter model has no control yet.

**`NOTE`** (7 bytes in 1.0): `u16 version`, `u8 root` (0..11, the pitch class C..B; default 0), `u8 scale` (0..11 in 1.0, an index of the note panel's twelve scales in `app/note_entry.h`: Chromatic, Major, Minor, Dorian, Phrygian, Lydian, Mixolydian, Pent. maj, Pent. min, Blues, Harm. minor, Whole tone; default 0), `u8 octave` (0..9; default 3), `u8 lock` (0 off, 1 on; default 0), `u8 jump` (0..32: the edit step, the distance the cursor moves after an entry; default 1).

**`NOTE` 1.1 (OS-SCALES28, 8 bytes, only for a scale outside the panel's twelve).** The scale is numbered in the official order 0..38 (the official firmware's 39 scales, `MAX_SCALE` 38; verified parity tracker-ce@7fd6c2c:core/source/scales.h:6-7 — the same order an OG project's pad board byte at 0x115 uses, `og.md`): `u16 version` (0x0101), `u8 root`, **`u8 scale` (the 1.0 field with its 1.0 meaning; 0, Chromatic, in a 1.1 chunk, so a 1.0 reader snaps no note outside the user's scale)**, `u8 octave`, `u8 lock`, `u8 jump`, then **`u8 scale11`** (0..38, the official index; it wins over the 1.0 byte). In memory the scale is the official index in both the model (`model::kNoteScaleMax` 38) and the runtime (`app::NoteEntry::scale`); only the codec knows the 1.0 byte's panel numbering (`model::kNotePanelScales`: pad of row 2 - 1 = the 1.0 byte). **The writer writes 1.0, byte for byte as before, for the twelve** (their byte is the pad - 1), and 1.1 only for the 27; a 1.1 chunk that holds one of the twelve loads and is written back as 1.0. **The reader:** 1.0 `scale` 0..11 maps through `kNotePanelScales` (above 11: Chromatic, counted); 1.1 `scale11` 0..38 wins (the 1.0 byte is still checked field by field, as every 1.0 field); 1.1 `scale11` above 38 falls back to the 1.0 byte's scale and is counted. A newer minor (1.2) is read as 1.1. An older build (v1.0.x, which knows NOTE 1.0) reads a 1.1 chunk as a newer minor: root, octave, lock and jump are kept, the scale is Chromatic (`scale` 0), the last byte is skipped, the load line says "newer fields skipped", and its next save writes 1.0 with Chromatic — the scale is lost (the documented price of a newer minor, as `PERF` 1.1).

**`MUTE`** (3 + n bytes, 19 written): `u16 version`, `u8 count` (1..16; writers write 16), `u8 mode[count]` (0 Immediate, 1 Bar, 2 Pattern; default 0). Tracks past `count` are Immediate.

**`SCEN`** (295 bytes): `u16 version`, `u8 latch` (0 off, 1 on; default 1, our choice), `u8 count` (3), then 3 scenes of 97 bytes: `u8 stored` (0 or 1), then 12 slots of `u8 fx`, `u8 row`, `i16 value[3]` (the layout of a `PERF` slot: `seq::PerfFx` ids, rows 0..3, values -100..100). **`SCEN` is version 1.2 when a slot of a stored scene holds PLAYMODE (id 18) with a value 4..23** (OS-PERFMODES M3), 1.1 when it holds the id 20 or 21 (ids 0..21), else 1.0 (ids 0..19); the rules, the writer's condition and what an older build does are those of `PERF` 1.2 and 1.1 above. A scene that is not stored holds 96 zero bytes. A scene is the slots as they were when it was stored: the FX, the selected row and the stored values (not the live values the encoder made, not the affected tracks, not the held pads); recalling it holds each value to its FX's own range, as a load does.

**`SNFX`** (3 + 2 rows bytes, 27 written): `u16 version`, `u8 rows` (1..32; writers write 12), then `u16 value[rows]`, one per row of the MASTER FX page's table (`app/send_fx_rows.h`, in this order; **a row is never renumbered, a new row is appended**):

| Row | Name | Range | Default |
|---|---|---|---|
| 0 | DLY PINGPONG | 0..1 | 0 |
| 1 | DLY SYNC | 0..1 | 0 |
| 2 | DLY RATE | 0..18 (this OS's 19 sync rates) | 0 |
| 3 | DLY TIME | 1..3500 ms | 500 |
| 4 | DLY FEEDBACK | 0..70 percent | 50 |
| 5 | DLY TONE | 0..100 percent | 100 |
| 6 | DLY MODE | 0 MONO, 1 STEREO | 0 |
| 7 | RVB SIZE | 0..100 percent | 50 |
| 8 | RVB DAMPING | 0..100 percent | 50 |
| 9 | RVB PREDELAY | 0..100 percent | 50 |
| 10 | RVB DIFFUSE | 0..100 percent | 80 |
| 11 | RVB QUALITY | 0 HALF, 1 FULL | 0 |

**Reading is tolerant and says so** (the rule of `SETS`, section "SETS and LRNB"; the strictness of the OS-004d chunks is for state that has no safe default). The shape of a chunk is the only error: a chunk version 0 or a newer major as always, a length outside the bounds below, a `count` or `rows` of 0 or above its maximum, a `MUTE` or `SNFX` whose length does not fit its count, a `SCEN` whose count is not 3 (`Malformed`). **A value outside its range reads as its default and is counted** (`Report::settings_skipped`, together with the entries `SETS` and `LRNB` skipped; `FormatReport::sanitised`; the app's load line says "N values reset"): `NOTE` field by field (in 1.1, the appended scale byte above 38 as well, falling back to the 1.0 byte's scale); a `MUTE` mode above 2; in `SCEN` a `latch` above 1, a `stored` above 1 (not stored) and, in a stored scene, an FX the chunk's version does not have (above 19 in 1.0, above 21 in 1.1 and 1.2: the slot is none, its row and values 0), a PLAYMODE value above what the chunk's version holds (3 in 1.0 and 1.1: RND; 23 in 1.2), a row above 3 (off) and a value outside -100..100 (0); in `SNFX` a value outside its row's range, and a row past the ones this version has (skipped; a row the chunk does not have is its default). A part that was read is present (the file said it), with the values that were taken. The 96 bytes of a scene that is not stored are ignored. A newer minor only appends: it is read as far as 1.0 goes, the rest is skipped at any length, `newer_minor` is set, and the appended fields are lost on the next save. Lengths: `NOTE` exactly 7 in 1.0 and exactly 8 in 1.1 (OS-SCALES28), `MUTE` 3..19, `SCEN` exactly 295, `SNFX` 3..67 (a newer minor: at least that many).

**When it applies.** Opening a project (and making a new one) applies the four parts from the main loop once the load has ended (`App::apply_project_state`, never from an interrupt): **a project without the part sets the defaults**, so the last project's key, mute modes, scenes and effect settings do not leak into the next (a change from the runtime-only days, when the MUTE MODEs and the send controls survived a load). `NOTE` fills the note-entry settings and the edit step and lays the pad board out again; `MUTE` the tracks' mute modes; `SCEN` the bank's scenes and LATCH (after the `PERF` slots, whose load clears the scenes); `SNFX` the board's values, and the engine is told of each that differs from what the board held, as the parameter change of kind Master that the page itself sends (the effects' own smoothing, no click). Afterwards **every change made to the runtime is stored in the project** (it becomes unsaved, undo is not affected), as for `MIXR` and `PERF` (`App::sync_project_state`); a value that is already what the project holds is not written, so a load does not make the project unsaved.

**Older builds.** An older build (the one before OS-PERSIST2) keeps the four chunks as unknown chunks and writes them back byte for byte, in the order it read them: 349 payload bytes in four chunks at their largest (OS-SCALES28: the NOTE 1.1 chunk is 8), which with the five of OS-004d (1,152 bytes), a full OG import (`OGPM` 970, `OGPN` 12,822) is 15,293 of 16,384 bytes of the pool and 11 of its 16 chunks; with the `LAW` chunk of OS-BUG-PASTE24 (3 bytes, one more chunk, only in the copy of an OG project below version 7) it is **15,296 of 16,384 bytes and 12 of 16 chunks** (`project_state_test.cpp`, `persist2_format_test.cpp` and `law_format_test.cpp` hold the arithmetic). A file from before this slice (none of the four) reads here as the defaults of the tables above and is written back as it was. **Checked against the build before OS-PERSIST2** (built from its sources): its C++ reader and writer (`o3pj_tool resave`) and its Python reference (`o3project.py rewrite`) read the file of the `persist2` fixture, keep the four chunks as its unknown chunks and write the file back byte for byte; its writer and this one give the same bytes for every fixture that has none of the four (`empty` 186 bytes, `small` 2,648, `settings` 2,720, `state` 3,372, `maximal` 1,888,426: `persist2_format_test.cpp` holds the size and CRC-32 of `empty`, `small` and `state` as regression constants). `tests/o3project_roundtrip.py` also reads the new file with the Python reference as that build has it (the four ids unknown to it).

### The `LAW` chunk (OS-BUG-PASTE24): the instrument volume law

An instrument stores a bare level 0..100 (`INST`, the sampler's `volume`). Which gain that level is depends on the **law**, and the law is data of the project: **0** the 1.2+ instrument law (level 50 is 0 dB, 100 is +24 dB, the law every native project plays at) and **1** the 1.1.14 table (level 100 is 0 dB), which this OS applies to the copy of an OG project of a structure version below 7 (`audio::LevelLaw`, `Project::volume_law()`; both laws are this OS's model, and whether the official firmware plays the same curves is an open research question: PAR-023, maintainer answer Q4 of OS-CLEANROOM). Without this chunk the copy of such a project, saved natively, would play 24 dB louder at VOLUME 100 when it is loaded again.

`LAW ` (the fourth character is a space, as in `CRC `): `u16 version` (1.0), `u8 law`. Exactly 3 bytes, 12 in the file with its header and pad byte. It sits after `SNFX` (`INSX`, when the project has inserts, follows it), before the unknown chunks and `CRC `.

- **Written only when the law is 1.** A file without the chunk is law 0, the law every file written until now plays at, so no file written before changes meaning. Every project that is not the copy of an OG project below version 7 is the same bytes as before (`empty` 186, `small` 2,648, `settings` 2,720, `state` 3,372, `midi13` 3,336, `persist2` 3,032, `maximal` 1,888,426: `tests/o3project_roundtrip.py` holds the size and CRC-32 of each, from the build before this chunk). A chunk that holds law 0 is accepted and written back without the chunk. A project that holds law 1 is 12 bytes longer.
- **Reading.** The shape rules of every chunk: version 0 or a newer major is refused (`NewerMajor` for the latter), the payload is exactly 3 bytes for 1.0 (a newer minor: at least 3, the rest is skipped and `newer_minor` is set), a second `LAW` or a `LAW` before a chunk of a lower rank is `Malformed`. **A `law` byte above 1 is `Malformed`, in a newer minor as well** (`LAW: unknown law`): it is not read as a default, because a law this version does not know would play its levels up to 24 dB wrong, and the tolerant rule of `NOTE` and `SNFX` is for state that has a safe default. (Default of the OS-BUG-PASTE24 spec, to confirm by the maintainer.) The reader holds the value and applies it with `Project::set_volume_law` **at Done**, after the CRC matched: a load that fails after the chunk commits nothing, and the held value is cleared at the start of every load, so a `Reader` used for two files in a row cannot carry the first file's law into the second.
- **Runtime.** The law is the document's (`Project::volume_law()`); `Project::reset()` puts it back to 0, except for a KEEP INSTRUMENTS reset. A new sample instrument in a project of law 1 is born at 100, the table's 0 dB (`app::unity_level`); in a project of law 0 at 50.

**Older builds, and a downgrade hearing risk (decision of the maintainer, 2026-10-16: no major bump).** An older build (any build before this chunk) opens a file with `LAW`, keeps it as one unknown chunk, and writes it back byte for byte; the chunk is the first of the unknown ones, and the older writer puts the unknown chunks after the known ones in the order it read them, so the order `LAW`, `OGPM`, `OGPN` is kept. **It does not act on it: an older build plays the levels of that file at the 1.2+ law, so the native copy of an OG project below version 7 sounds about 24 dB louder at VOLUME 100 than this OS's law for that copy (+24 dB instead of 0 dB).** Do not open a project saved with the `LAW` chunk in a build older than the one that wrote it, with the master up. This is the very defect of OS-BUG-PASTE24, met by a downgrade; it does not make an existing file worse (such a copy played +24 dB before this chunk existed). The alternatives (a `PHDR` 2.0 only in the files that carry `LAW`, so that an older build refuses them, or in every file) were weighed and not chosen: they strand older builds from files that have no problem or from a file that is otherwise fine. The pool arithmetic of an older build with every chunk is under "Older builds" of the session state (15,296 of 16,384 bytes, 12 of 16 chunks).

### The `INSX` chunk (OS-INSFX S3a): the inserts

An **insert** is an effect module (`.tmod`, kind effect) on a strip: INS A and INS B of each of the 16 tracks, and the master (`docs/specs/OS-INSFX.md`). The project names its modules in `MODR` (name and ABI), and `INSX` says which module sits where, whether it is bypassed, and the module's parameter blob. At most **4 inserts** in all (the cap of `audio::gov::kMaxInserts`, counted in effect instances: the master's insert is dual mono, two instances of its module, L and R, so a master record counts 2 of the 4 on the audio side (OS-INSFX S6; the file may still hold four records, and a load skips, counted, the record that does not fit); `app/src/module_binder.cpp` asserts it does not exceed `model::kMaxInserts`). Raising the cap needs a minor bump of `INSX` (1.1), because a 1.0 reader refuses a count above 4 as `Malformed`. Decision D2 of the maintainer, 2026-11-01: one new optional chunk, id `INSX` (fourth character `X`), version 1.0, **after `LAW ` and before the unknown chunks and `CRC `**, written only when the project has at least one insert. Evidence: new Community OS behaviour (the official firmware has no insert slots).

```
INSX payload (big-endian, like every chunk), 3 .. 535 bytes
u16 version = 0x0100
u8  count                 0..4 records
record x count, ascending (where, slot), no duplicates:
  u8  where               0..15 a track, 16 the master
  u8  slot                0 or 1 for a track, 0 for the master
  u8  module              index into MODR
  u8  flags               bit 0 bypassed; the other bits 0
  u8  n                   parameter count 0..32 (O3M_PARAMS_MAX)
  f32 param[n]            the module's parameter blob in its order, finite
(a later minor appends AFTER the last record)
```

The size is `3 + sum(5 + 4n)`: 3 with no record (never written), 535 at most (four records of 32 parameters). The chunk is padded to an even length in the file like every chunk.

- **Written only with an insert.** A project that never had an insert is **the file it was**: no byte of any other chunk changes (`empty` 186, `small` 2,648, `settings` 2,720, `state` 3,372, `midi13` 3,336, `persist2` 3,032, `maximal` 1,888,426: the size and CRC-32 pinned in `tests/o3project_roundtrip.py` are unchanged by this chunk). The records are written in ascending `(where, slot)` order, which the model keeps.
- **`MODR` is not pruned.** `Project::add_module` only appends, so removing an insert (`clear_insert`) leaves the effect module's `MODR` entry, and a project whose last insert was removed differs from the file that never had one by that entry; it has no `INSX` chunk. Documented, not changed. The module table is shared with the instruments (16 modules in all). The model refuses `clear_modules` while an insert exists.
- **Reading, 1.0.** The same shape rules as every chunk: version 0 is `Malformed`, a newer major is `NewerMajor`, the payload is at least 3 bytes and at most 535, a `count` above 4 is `Malformed`, and the records must fit the length exactly (a missing or a surplus byte at 1.0 is `Malformed`). **Records are read tolerantly (the `LRNB` rule: the project still opens):** a record is skipped and counted (`Report::settings_skipped`) when its module index is past `MODR`, its `where` or `slot` is out of range (a track slot above 1, a master slot above 0, a `where` above 16), its `n` is above 32 (its `4n` bytes are still its own), a parameter is not finite (NaN or an infinity), or an earlier record has the same `(where, slot)`; flag bits other than bit 0 are cleared and counted. Records may come in any order; the model stores them sorted. A chunk of `count` 0 reads as no inserts.
- **Newer minor (1.x).** At least the 1.0 minimum; the records are read as far as 1.0 knows (`count` above 4 is still `Malformed`), whatever follows the last record is skipped, `newer_minor` is set, and the appended data is lost on the next save, as for every chunk.
- **A file without the chunk** has no inserts, and loading it **clears** the inserts the document held (`Project::reset`, the `MIXR` rule): none leak from the previous project.
- **Model.** `model::InsertState` (`model/project_state.h`: `count`, 4 records of 136 bytes, 548 bytes, no padding), `Project::inserts()`, `find_insert`, `set_insert` (validates: `BadValue` for a record the format cannot hold, replaces the same `(where, slot)`, `Full` beyond four), `clear_insert` (`NotFound`, `BadIndex`), `clear_inserts`. The part is present when `count` is not 0 (every bit of `state_present()` is a part already). Not undoable (spec decision D9). `check_invariants` checks the table against `MODR`.
- **Arena.** `kModelArenaBytes` 1,933,760 to **1,934,312** (+552: 548 bytes of state and 4 of alignment; since OS-MIDICCMAP S1: **1,934,344**, +32 for the settings block's raise to 32 fields).

**Older builds.** An older build (any before this chunk) reads `INSX` as an unknown chunk, keeps it (one of 16, at most 535 bytes of the 16 KiB pool; a full pool, which `OGPN` can fill, drops it and counts it as any unknown chunk) and writes it back byte for byte, in the order it read them. **The project plays without the inserts** (the sound differs; the file is not refused), and the `MODR` entry does not make the older build load the effect module (only a Module instrument's module is loaded). A save in the older build keeps the chunk and the entry. `tests/o3project_roundtrip.py` emulates that reader (its chunk table without `INSX`, the `CRC ` rank 19) and checks the byte-for-byte write back, before and behind the unknown chunks.

### The `MEVT` chunk (OS-MIDIREC-P1 S1): the MIDI take lanes

A **lane** is the MIDI events recorded on one track of one pattern (`docs/specs/OS-MIDIREC-P1.md`, A1-A3): notes, controllers, program changes, channel and poly aftertouch and pitch bend, each at a tick of 1/48 of a step in the track's own timeline. The lanes of a project live in the app's lane store (`model/lane_store.h`), **outside `Project` and `ModelArena`** (no pinned size moves), and this chunk is their only persistent form. New Community OS behaviour; the official firmware has no such chunk.

```
MEVT payload (big-endian, like every chunk), 4 .. 208,900 bytes (the pool caps it; see Limits)
u16 version = 0x0100
u16 lane_count            0..2048
lane x lane_count, ascending (pattern, track), no duplicates:
  u8  pattern             the pattern ID 1..255 (the ID PATT and SONG carry, not the pool slot)
  u8  track               0..15
  u16 event_count         1..4096
  u8  event_size          8 (a later minor may write more; a reader takes the first 8 bytes of each event)
  u8  reserved            0 (a reader tolerates any value)
  event x event_count, ascending by tick (ties in the order recorded):
    u16 tick              0..6143
    u16 len               notes 1..6144, every other kind 0
    u8  kind_channel      kind << 4 | channel: kind 0 note, 1 CC, 2 program, 3 channel AT, 4 poly AT, 5 pitch bend; channel 0..15
    u8  port              0..3 (the value `midi_route.h` uses: DIN, USB)
    u8  a                 0..127: note, controller, program, pressure, note of a poly AT, pitch bend LSB
    u8  b                 0..127: velocity, controller value, pitch bend MSB
(a later minor appends AFTER the last lane)
```

The size is `4 + sum(6 + 8n)`. The lane key is `(pattern - 1) * 16 + track` (4080 keys); **spec deviation:** the spec says "pattern 0..127", which is the pool slot; the file carries the pattern ID, so a lane survives a reordering of the pool and a pattern copied to another ID is a new lane.

- **Written only with a lane.** A project that never had a lane, or whose store is empty, is **the file it was**: no byte of any other chunk changes (`tests/o3project_roundtrip.py` pins `lanes-empty` equal to `small`, and the sizes and CRC-32 of every earlier fixture are unchanged). The chunk is written after `INSX` and before the unknown chunks and `CRC `. The Writer writes a store only when it belongs to the project being written (the store's epoch is the project's `load_epoch()`); a store of an earlier project is empty to it.
- **Limits.** 4,096 events in one lane, 24,576 in all lanes of a project (the 192 KiB pool, decision 6a), 2,048 lanes with events, 6,144 ticks (the longest pattern, 128 steps), 6 kinds. The biggest chunk is `4 + 2048 x 6 + 24576 x 8` = 208,900 bytes; the biggest file (the `maximal` fixture with a full pool) stays under the 4 MiB the reader accepts.
- **Reading, 1.0.** The same shape rules as every chunk: version 0 is `Malformed`, a newer major is `NewerMajor`, a payload shorter than the 4-byte head is refused, a `lane_count` above 2,048 is `Malformed`, and a lane header or lane data that runs past the chunk is `Malformed`. **Lanes are read tolerantly (the `LRNB` rule: the project still opens):** a lane is skipped and counted (`Report::mevt_skipped`) when its key is invalid (pattern 0, track 16), its `event_size` is below 8, its count is 0 or above 4,096, its key is not above the previous lane's (unsorted or a duplicate), the project has no such pattern, the store has no room (pool full), or any of its events is invalid or out of tick order (the lane is dropped whole). Trailing bytes after the last lane are skipped.
- **Newer minor (1.x).** Read as far as 1.0 knows it (the `event_size` byte is the extension point; whatever follows the last lane is skipped), `newer_minor` is set, and the appended data is lost on the next save: the chunk is written back as 1.0.
- **A file without the chunk** has no lanes, and loading it **clears** the store: none leak from the previous project. The Reader adopts the loaded project's epoch into the store; the Editor calls `LaneStore::sync` before a lane edit and the app should call it after a load or a new project.
- **Model.** `model::LaneStore` (a directory of 4,080 `{offset, count}` slots plus a pool of 24,576 events, 212,928 bytes, lanes packed in key order), `Editor::lane_replace` / `lane_clear` (undoable, one unit per take commit), and the length rules of `docs/specs/OS-MIDIREC-P1.md` A16 and A17: `delete_pattern` and `clear_pattern` free the pattern's lanes in the same undo unit, and **shortening** a track (`set_track_length`, `set_pattern_length`) deletes the lane events at or past the new length (`length x 48` ticks) in the same unit, whereas lengthening does not. Nothing plays or records a lane in S1 (S2 and S3).
- **Rank.** `CRC ` was rank 20 and is now rank 21; `MEVT` is rank 20. The rank is internal to the reader and the Python reference (`RANKS` in `tools/o3project.py`), not a field.

**Older builds.** An older build (any before this chunk) reads `MEVT` as an unknown chunk. **A chunk of 16 KiB or less** (one of 16 in the 16,384-byte pool, with the other unknown chunks) is kept and written back byte for byte, in the order it was read; **a bigger one is dropped and counted** (`unknown_dropped`), and the lanes are gone from the next save of that build (decision 3a of the maintainer, 2026-11-10: a take of more than about 2,000 events is lost by an older build). The older build plays the project without the lanes. The Python reference simulates it (`tests/o3project_roundtrip.py`, "old reader"), and `tests/mevt_format_test.cpp` does the same with a null store.

Caveat of the checker: `Verifier` (the Writer's self-check) shares the rank table with the Reader and always treats `MEVT` as a known chunk; a Reader without a store treats a misplaced `MEVT` as unknown instead of refusing it.

### CRC

`u16 version`, `u32 crc` (section 2). Payload 6 bytes.

### Unknown chunks

Any other id (printable ASCII) is kept: up to 16 chunks and 16,384 payload bytes in all. Each is written back byte for byte (id, length, payload, pad) after the known chunks. A chunk that does not fit is skipped and counted: `Report::unknown_dropped` and `Project::unknown_dropped_chunks()` / `unknown_dropped_bytes()` tell the UI to say so; the load still succeeds.

### `OGPM` and `OGPN`: what an OG import carries (OS-004b)

Two chunks that the OG readers (`formats/og`) put in the pool of unknown chunks, so that a native project holds what an OG project held and the model has no field for, and Export -> OG can write it back (ADR 0006: OG -> OS -> OG is lossless for OG-only content). The core neither reads nor checks them: they are kept, re-emitted and counted like any unknown chunk, `o3project.py` decodes them in its dump, and `formats/og` validates them when it uses them (an invalid one is ignored and counted at Export, never a load error). Both begin with a chunk version (`0x0100`, 1.0; OGPM is 1.1, `0x0101`, when it carries the byte of a v17 project, below) and use the chunk conventions of this format (big-endian integers); the bytes of a group are OG file bytes, copied as they are (their integers and floats are little-endian). Full description: `docs/formats/og.md` sections 3 and 6.

**`OGPM`, the project settings.** `u16 version`, `u16 groups` (a bit set), then the groups whose bit is set, in bit order, each of a fixed length. A group is present only when it differs from the default Export writes. Valid: major 1, no bit outside the table, and a length of exactly the sum for version 1.0 (a newer minor may only append). At most 969 bytes for 1.0, 970 for 1.1.

| Bit | Group | Length | Bytes (project.mt file offsets) |
|---|---|---|---|
| 1 | delay | 4 | 0x11A, 0x11C-0x11D, 0x11E |
| 2 | limiter | 9 | 0x120-0x121, 0x124-0x127, 0x128-0x129, 0x12A |
| 3 | reverb | 16 | 0x418-0x427 |
| 4 | inputs | 10 | 0x134-0x139, 0x13C-0x13F |
| 5 | performance | 144 | 0x142-0x1BD, 0x2F5-0x308 |
| 6 | MIDI velocity | 16 | 0x309-0x318 of a version 2-7 project |
| 8 | 1.3-1.6 block | 306 | 0x4DE-0x5FF, then 0x309-0x318 of a version 13+ project |
| 9 | 1.7-1.9 block | 460 (1.1: 461) | 0x600-0x602, 0x643-0x80B (1.1: and 0x80C of a version 17 project, the last byte of the chunk) |

**OGPM 1.1** (OS-004c). Project.mt version 17 (official 1.9.2; open research question, unverified: no file backs it) is assumed to have a new one-byte field at 0x80C whose meaning is not known (`docs/formats/og.md` section 3). Zero is its default and is not carried; a non-zero value makes the chunk version 1.1, in which group 9 is one byte longer and that byte is the value. Group 9 is the highest group, so the byte is the last of the chunk, and a 1.0 reader skips it as it skips anything a newer minor appends. In 1.1 a chunk that has group 9 must have its byte (length at least the sum for 1.1, more is appended); a chunk without group 9 has no extra byte and is the same as in 1.0. A chunk that does not need the byte stays 1.0, so a project that was never a v17 one writes the chunks it always did.

**`OGPN`, the pattern names file.** `u16 version`, `u32 length` of the PAMD file (16..12,816), then the file's bytes without its trailing zeros (the first four are `PAMD`; the kept bytes are no longer than the file). Written back as `length` bytes: the kept bytes, then zeros. At most 12,822 bytes: with it in the pool little room is left for other unknown chunks.

**Versions.** A known chunk's version is read first, before its length is judged:

- **Newer major** (a larger high byte): the file is refused with `NewerMajor`, whatever the chunk's length or layout (the reader cannot know either). Version 0 is `Malformed`.
- **Newer minor** (same major, larger low byte than the reader knows for that chunk: 9 for `INST`, 2 for `PERF` and `SCEN` (OS-PERFMODES M3; 1.1 was OS-PERFFX P1), 1 for `APPM`, `USBS` and `NOTE` (OS-SCALES28), 0 for the others): the new version only appends fields, so the chunk must still be at least as long as version 1.0 requires (`PHDR` 19, `TRAK` 3, `MODR` 3, `SONG` 3, `PATT` 7, `INST` 310 (1.1), `SETS` 4, `LRNB` 4, `MIDI` 20, `USBS` 5, `MIXR` 25, `PERF` 99, `APPM` 3, `NOTE` 7, `MUTE` 3, `SCEN` 295, `SNFX` 3, `LAW ` 3, `INSX` 3, `CRC ` 6 bytes, else `Malformed`); there is **no upper bound**. The reader parses the part of the version it knows (INST: 1.9 (no byte beyond 1.8; the CC bytes of a non-MIDI instrument are kept), so including the rate, the engine, the twelve MIDI bytes, the stereo flag, the twelve WT bytes, the play-thru flag and the module RATE; PERF and SCEN: 1.2, so including the PLAYMODE values 4..23; NOTE: 1.1, so including the appended scale), skips whatever follows (it may be any size: a chunk read whole buffers at most the version 1.0 maximum and the rest is skipped in pieces; `PATT` is parsed as it streams and its tail skipped) and sets `Report::newer_minor`. Those appended fields are **lost on the next save**: the file is written back as the smallest version that holds the data this reader has (1.0; INST 1.1, 1.2, 1.3, 1.4, 1.5, 1.6, 1.7 or 1.8 by the write condition in the INST section; PERF and SCEN 1.2 only when a slot holds PLAYMODE 4..23, 1.1 only when a slot holds the id 20 or 21; APPM 1.1 only when more than six apps are stored; USBS 1.1 only for 4 or 6 outputs; NOTE 1.1 only for a scale outside the panel's twelve), which is why the report says so. This holds for the `CRC ` chunk too: version 1.x with any number of bytes after the CRC value is a valid CRC chunk (the CRC value itself is still checked).
- **Same version (1.0; INST 1.0, 1.1, 1.2, 1.3, 1.4, 1.5, 1.6, 1.7, 1.8 or 1.9; PERF and SCEN 1.0, 1.1 or 1.2; APPM, USBS and NOTE 1.1)**: the exact bounds of that version apply (for example `CRC ` is exactly 6 bytes, `PHDR` 19..51) and unused bytes after the fields are `Malformed`. USBS 1.1 is exactly `5 + 2 * slots + 1` bytes (22): profile byte 1 (P8), 8 slots, then the count, 4 or 6; anything else is `Malformed`. A USBS newer than 1.1 is read leniently: the count is used only when profile byte 1, 8 slots and a count of 4 or 6 are all present, else the chunk is read as 1.0 (never refused for another profile or extra bytes). NOTE 1.1 is exactly 8 bytes. PERF and SCEN are exactly 99 and 295 bytes in every minor 0..2.

## 5. The model and its arena

`o3os::model::Project` holds everything above with no knowledge of a screen, file or device: name, tempo, swing, default pattern length, active tracks, master, 16 track slots, a module table, the song, a pool of patterns, 64 instrument slots, and the unknown-chunk pool. Reads are free (`const` accessors). Writes go through the mutators (`set_step`, `set_track_length`, `set_order`, `create_pattern`, `set_instrument`...), which check the value, change it and bump the generation counters; a rejected mutation changes nothing and says why (`Status`). Undoable edits go through `model::Editor` (OS-002c), which calls the same mutators and journals what they changed in an in-RAM ring (not part of any file); a change made without it (a load, an import) clears that history.

**Generations**: `generation()` (any change), `tracks_generation()` (header, tracks, master), `song_generation()`, `pattern_generation(id)`, `instrument_generation(slot)`. Free-running u32, compare for equality.

**Storage.** No heap. The project lives in one `ModelArena`, a typed object the platform provides (a static in the host tests; on the MK66 the same object placed in the SDRAM section by the linker script). All limits are constants in `model/limits.h`; the layout is declared (alignment and size `static_assert`ed, identical on the 64-bit host and on the MK66 because the build proves it).

| Part | Bytes |

| instrument pool: 64 x 720 (OS-STEREO step 2: the stereo byte, +4 each) | 46,080 |
| unknown-chunk pool | 16,384 |
| header, tracks, song (255), id map (256), modules, tables, generation counters | 2,520 |

That leaves 14.2 MiB of SDRAM, 2.9 MiB beyond this OS's sample memory budget of 11.25 MiB. The largest possible file is about 1.82 MiB (the maximal test fixture is 1,888,426 bytes); the reader refuses a `FORM` over 4 MiB.

**Why 128 patterns, not 255.** Pattern ids are 1..255 (the OG numbering, and what the song refers to) but at most 128 patterns exist at once. A full pool of 255 would be 3.5 MiB (21 % of the SDRAM) and squeeze the sample memory (the pool is 1.76 MiB at 128); the 8 OG fixture projects hold 104 patterns in all (`docs/formats/og.md` section 10). A file or an import that needs more than 128 is refused with "limit exceeded" (never silently trimmed). Raising `kMaxPatterns` to 255 costs another 1.76 MiB and changes nothing else (the `PHDR` count is a u16). The limit lives in `model/limits.h` and, for the check, in `o3project.py`.

## 6. Reading and writing

Both work over `core::ByteSource` / `core::ByteSink` (`core/byte_io.h`) and do no file I/O: the platform wraps an SD file or a test buffer. A source or sink may move fewer bytes than asked or answer `WouldBlock`; `End` (source) means the stream is over; a count above what was asked or `Ok` with no bytes is treated as a failure.

```cpp
formats::native::Reader r;                 // 2.7 KB: put it in a job slot or a static
r.begin(source, arena);                    // resets the arena's project
while (r.step(4096) == Progress::Running) {}   // at most 4096 bytes read per call; resumable
r.report();                                // error, detail, offset, chunk, counts, unknown kept/dropped
```

`Writer` is the same shape (`begin(project, sink)`, `step(budget)`). `begin()` touches nothing: the first steps run a budgeted sizing pre-pass (the `FORM` length is written first, so the whole project is measured before the first byte; it writes nothing, costs a pattern track the steps it scans against the budget, and does at least one item per call, so even `step(1)` returns promptly). `sized()` says when it is over and `total_bytes()` is valid. The project must not change while the writer runs, pre-pass included: it checks `generation()` at each step of the pre-pass and at each piece boundary and fails with `Modified`. A file written is a function of the model alone (canonical chunk order, minimal stored steps, zero pads), so saving twice, with any step budget, gives the same bytes, and `load` then `save` of a file this version wrote gives the file back byte for byte.

**A failed load leaves a valid empty project** (the arena's project is reset), never a half-filled one. The reader holds at most one 1 KiB piece of a chunk and one 7 x 128 byte pattern row at a time.

## 7. Errors

| Error | When |
|---|---|
| `Truncated` | the source ended before the `FORM` did (at any offset) |
| `BadMagic` | not `FORM` + `O3PJ` |
| `BadCrc` | the `CRC ` chunk does not match |
| `NewerMajor` | a chunk version with a larger major |
| `LimitExceeded` | more patterns, instruments or modules than the model holds (announced in `PHDR` or found while loading), or a `FORM` over 4 MiB |
| `Malformed` | anything else wrong: a length that does not fit, a value out of range, an unsafe path, a duplicate, a chunk out of order, a bad pad byte, a missing or misplaced `CRC `, counts that differ from `PHDR`... `Report::detail` says which |
| `SourceFailed`, `SinkFailed` | the byte stream failed or broke its contract |
| `Modified` | writer only: the project changed under it |
| `Internal` | writer only: its size formulas disagree with its output (a bug, never input) |

Chunks are parsed as they arrive, before the CRC is known (it is last), so a file with a wrong CRC is also validated; the CRC verdict wins only for files that parse cleanly. `Report` carries the byte offset and chunk id of the first problem.

## 9. Samples

Samples are standard WAV files next to the project file; an instrument stores the relative path. A path is `""` or components separated by single `/`, none empty, `.` or `..`, no leading or trailing `/`, no `\`, no `:`, no control characters. The reader and the model refuse anything else, so a project can never point outside its folder. The PCM itself is not in the project file; the instrument records the sample's rate (`sample_rate`, INST 1.1) and the OG's positions (start, loop, end, slices) in the sampler block. An imported WAV makes such an instrument (`samples/instrNN.wav`, the rate of the file, its `smpl` loop and `cue` points as positions): `docs/architecture/os-tree.md`, "WAV as a registered format".

## 10. Evolution

- A field appended to a chunk is a **minor** bump: old readers skip it and say so.
- A new chunk kind needs no bump: old readers keep it as unknown (within the pool) and write it back. (`SETS` and `LRNB` of OS-002d are the first: they sit where the unknown chunks are written, so a reader that does not know them preserves them.)
- A change of meaning, or a removed or reordered field, is a **major** bump: old readers refuse the file, and the new reader gets a loader for the old major.
- OS-004d, the first use of these rules after the format was written: five new chunks (no bump: an older build keeps them as unknown chunks, see "Older builds" in section 3) and one new field (`INST` 1.1 to 1.2, a minor bump with a loader for 1.1: engine 0). Compatibility, both ways: an older file in a new build reads as the defaults, and the new build writes the file it always wrote for a project that has none of the new state (the default project is still 186 bytes, a small fixture is byte-identical); a new file in an older build loads, keeps the chunks, loses only the engines (a newer minor of `INST`). Round trips: `tests/project_state_test.cpp` (the exact bytes written from the description, the older file, the strict reader), ctest `project_python` (C++ against `o3project.py`, both ways, the same verdict on damaged state chunks).
- OS-INSTUI S8b + S9: `INST` 1.2 to 1.3, twelve appended bytes (the MIDI instrument's VELOCITY, PROGRAM, OUT, PB RANGE, OFFSET, CC A..F and a sample instrument's VEL>), the engine byte always present in a 1.3 chunk. Compatibility, both ways: an older file (1.1, 1.2) in the new build reads as the defaults and the new build writes the file it always wrote for a project that never used the fields (byte for byte, size and CRC-32 pinned against the build before INST 1.3); a new file in an older build loads, keeps the instrument whole and loses only the twelve bytes (a newer minor of `INST`). Round trips: `tests/inst_midi_format_test.cpp` (exact bytes, the write condition, the older files, damaged values, the length), ctest `project_python` (the `midi13` fixture: C++ against `o3project.py`, both ways).
- OS-LFOSINE: `INST` 1.3 to 1.4, no appended byte: the version says that an LFO shape of 5 (Sine) is valid; written only for an instrument with a Sine LFO; an older chunk's shape of 5 or more reads as Triangle (`docs/specs/OS-LFOSINE.md`).
- OS-STEREO step 2: `INST` 1.4 to 1.5, one appended byte (the instrument's stereo flag); written only for a Sample instrument with the flag set; an older chunk and a value above 1 read as 0; a flag on a MIDI or Module instrument reads 0. Compatibility, both ways: an older file in the new build reads mono and the new build writes the file it always wrote for a project without a stereo instrument (size and CRC-32 of every fixture pinned); a new file in an older build loads, keeps the instrument whole and loses only the flag (a newer minor of `INST`). Round trips: `tests/inst_midi_format_test.cpp` (the 1.5 cases), ctest `project_python` (the `stereo` fixture: C++ against `o3project.py`, both ways).
- OS-CEWTENV W1: `INST` 1.5 to 1.6, twelve appended bytes (`wt_bend`, `wt_sust` of the six LFO slots, in slot order); written only for an instrument with a WT slot (a loop of 2 or 3) or a non-zero WT byte. Compatibility, both ways: an older file in the new build reads the WT bytes as 0 and a loop of 2 or 3 as 1 (an LFO: what those files played), and the new build writes the file it always wrote for a project without WT bytes (size and CRC-32 of every existing fixture pinned); a new file in an older build loads, keeps the instrument whole and loses only the twelve bytes (a newer minor of `INST`, which are its payload's tail). A WT slot's shape reads verbatim (the contour 0..255) in a 1.6 chunk and as Triangle (above the last shape) in an older one. Round trips: `tests/native_format_test.cpp` (the 1.6 cases), ctest `project_python` (the `wt` fixture: C++ against `o3project.py`, both ways).
- OS-CEPLAYTHRU P1: `INST` 1.6 to 1.7, one appended byte (the play-thru flag, `Instrument::slice_thru`, the OG instrument file's byte 279, verified parity tracker-ce@7fd6c2c:core/source/mtStructs.h:653-654); written only for a Sample instrument with the flag set. Compatibility, both ways: an older file in the new build reads the flag as 0, and the new build writes the file it always wrote for a project without the flag — 1.6 and older byte for byte, size and CRC-32 of every existing fixture pinned; a new file in an older build loads, keeps the instrument whole and loses only the flag (a newer minor of `INST`, the byte being its payload's tail). A value above 1 reads as 0 (as the stereo byte does). Round trips: `tests/native_format_test.cpp` (the 1.7 cases), ctest `project_python` (the `playthru` fixture: C++ against `o3project.py`, both ways).
- OS-MODRATE S3: `INST` 1.7 to 1.8, one appended byte (the module instrument's RATE, `Instrument::rate`, 0 FULL, 1 = 1/2, 2 = 1/4; one of the struct's two reserved bytes, so 720 bytes still); written only for a Module instrument with a RATE other than 0. Compatibility, both ways: an older file in the new build reads the RATE as 0, and the new build writes the file it always wrote for a project without a RATE — 1.7 and older byte for byte, size and CRC-32 of every existing fixture pinned; a new file in an older build loads, keeps the instrument whole and loses only the RATE (a newer minor of `INST`, the byte being its payload's tail). A value above 2, and a 1.8 chunk of a Sample or MIDI instrument, read as 0. Round trips: `tests/native_format_test.cpp` (the 1.8 cases), ctest `project_python` (the `modrate` fixture: C++ against `o3project.py`, both ways).
- OS-PARAMAUTO S1: `INST` 1.8 to 1.9, no byte appended (the six CC A..F bytes of a Sample or Module instrument become CC letters; section 3, INST 1.9); written only for a non-MIDI instrument with a non-zero CC byte, so every file without a letter is written as before; a non-MIDI instrument read from an older chunk gets its CC bytes as 0. The struct and the arena do not change.
- A new persistent part is a new chunk written only when the project has it, and a new field a minor bump written only when it is not its default: that keeps every file that never used it as it was.
- OS-PERSIST2: four new chunks (`NOTE`, `MUTE`, `SCEN`, `SNFX`; no bump of any chunk, no field changed) for the settings that were still runtime only. Compatibility, both ways: an older file in a new build reads as the defaults and is written back as it was; a new file in an older build loads, keeps the four as unknown chunks and writes them back byte for byte (the pool arithmetic is in section 3). New is the tolerant reading of a value out of range (its default, counted), which `SETS` already had. Round trips: `tests/persist2_format_test.cpp` and `persist2_app_test.cpp`, ctest `project_python` (the `persist2` fixture, both ways, the same reading of damaged chunks).
- OS-SCALES28 S1: `NOTE` 1.0 to 1.1, one appended byte (the scale in the official order 0..38, verified parity tracker-ce@7fd6c2c:core/source/scales.h:6-7), written only for a scale outside the note panel's twelve (the writer writes 1.0, byte for byte as before, for the twelve, whose byte stays the pad - 1; the 1.0 byte is 0 in a 1.1 chunk); in RAM the scale is the official index (`model::kNoteScaleMax` 38, `app::NoteEntry::scale`), and the codec maps the 1.0 byte through `model::kNotePanelScales`. Compatibility, both ways: every existing file is the bytes it was (the `persist2` fixture's size and CRC-32 do not move: its Blues is one of the twelve, byte 9); a 1.1 file in an older build (every published build, which knows NOTE 1.0) loads as a newer minor — root, octave, lock and jump kept, the scale Chromatic, the last byte skipped, "newer fields skipped" on the load line — and its next save writes 1.0 with Chromatic, so a downgrade through a save loses only the scale (the documented price of a newer minor, as `PERF` 1.1). Round trips: `tests/note11_format_test.cpp` (every scale, the exact bytes, the 1.0 files, the damaged 1.1 chunks, the shape errors), `tests/persist2_app_test.cpp` (a 1.1 project sets the runtime and lays the pads out), ctest `project_python` (the `scales` fixture, both ways, the same reading of the damaged NOTE cases).

- OS-PERFFX P1: two new Perform FX ids, 20 BITDEPTH and 21 OVERDRV, in the byte of `PERF` (and `SCEN`) that was always there; **`PERF` and `SCEN` 1.0 to 1.1, a minor bump with a loader for 1.0** (decision D5, maintainer 2026-10-19, option A: no field, no length and no layout changes, the version only says that the ids 20 and 21 are valid). The writer writes 1.1 only when a slot holds one of the two ids, so a project that never used them is the bytes it always was. Compatibility, both ways: an older file in a new build reads as it always did (ids 20 and 21 in a 1.0 chunk are none); a new file in an older build loads, reads the chunk as a newer minor ("newer fields skipped" on the load line), reads the two ids as none (the slot's row and values reset) and writes the chunk back as 1.0 with those slots empty, so a downgrade through a save is not lossless (see `PERF`). Tests: `tests/project_state_test.cpp` (PERF: 1.0 byte for byte without the ids, 1.1 round trip, a 1.1 and a 1.0 chunk read), `tests/persist2_format_test.cpp` (the same for SCEN), ctest `project_python` (C++ against `o3project.py`, both ways, the same reading).
- OS-BUG-PASTE24: one new chunk, `LAW ` (the instrument volume law; no bump of any chunk, no field changed, no major bump: maintainer decision 2026-10-16), written only when the law is the 1.1.14 table, so every other file is the bytes it always was. Compatibility, both ways: an older file in a new build is law 0 and is written back as it was; a new file in an older build loads, keeps the chunk as unknown and writes it back byte for byte, **but plays the levels at the 1.2+ law (a downgrade hearing risk, section 3, "The `LAW` chunk")**. Round trips: `tests/law_format_test.cpp`, ctest `project_python` (the `law` fixture: C++ against `o3project.py`, both ways, the same reading of damaged chunks). Checked against the build before this chunk (built from its sources, see the commit of the slice): its C++ reader and writer and its Python reference keep the `LAW` chunk of the `law` fixture and write the file back byte for byte.

- OS-INSFX S3a: one new chunk, `INSX` 1.0 (the inserts; no bump of any chunk, no field changed: decision D2 of the maintainer, 2026-11-01), written only when the project has an insert, after `LAW `, so every file that never had one is the bytes it always was. Compatibility, both ways: an older file in a new build has no inserts (and loading it clears the document's); a new file in an older build loads, keeps the chunk as unknown and writes it back byte for byte, and plays without the inserts (section 3). `MODR` is never pruned.
- OS-MIDIREC-P1 S1 (2026-11-10): one new chunk, `MEVT` 1.0 (the MIDI take lanes; no bump of any chunk, no field changed), written only when the lane store has a lane, after `INSX`; `CRC ` moves from rank 20 to 21 in the reader (internal); a project with no lane is the file it was; an older build keeps a chunk of 16 KiB or less as unknown and drops a bigger one (section 3, "The `MEVT` chunk"). Lane key by pattern ID, not pool slot (a spec deviation recorded there).
- OS-APPUX S3: `APPM` 1.0 to 1.1, the same layout with a count of up to 12 apps (it was 6) and a payload of up to 1,015 bytes; written as 1.0 while six apps or fewer are stored (every file that never used more is the bytes it always was), as 1.1 beyond; a loader for 1.0 (at most 6) stays; the model arena grows by 984 B (six more 164-byte sets: 1,933,416 B). An older OS refuses a 1.1 `APPM` (`APPM: bad app count`) and with it the whole project (maintainer, 2026-10-19, option B: no appended tail); no other chunk changed.
- OS-PRFDEFAULTS: no bytes change and no version moves. The defaults of the `PERF` values (what a project with no `PERF` chunk reads as, and what a new project holds) are the table of `docs/specs/OS-PERFFX.md` section 9 instead of 0 (maintainer decision 2026-10-23); a chunk that is present loads exactly as stored, and a project that never touched Perform is still written without the chunk.
- OS-PERFFX P1 + OS-APPUX S3 together: the two version gates are independent. `PERF` and `SCEN` are 1.1 only with the Perform FX 20 or 21 in a slot (of a stored scene for `SCEN`); `APPM` is 1.1 only with more than six apps stored; every other chunk stays 1.0. A project that uses neither is the file it always was; one that uses one feature bumps only that feature's chunks; one that uses both writes all three as 1.1. Every combination is read (a 1.1 `PERF` with six apps, a 1.0 `PERF` with seven apps, and so on) and written back as the versions its content needs. An older OS opens the file when no `APPM` is 1.1 (it reads the two FX ids as none) and refuses it when `APPM` is 1.1. Tests: `tests/project_state_test.cpp` ("the version gates are independent"), ctest `project_python` ("PERF/SCEN 1.1 ... and APPM 1.1 in one project", C++ against `o3project.py`).
- OS-PERFMODES M3 (2026-11-06): `PERF` and `SCEN` 1.0 to 1.2, a minor bump with a loader for 1.0 and 1.1: no field, no length and no layout change (99 and 295 bytes in every minor 0..2), the version only says that a PLAYMODE slot (id 18) may hold 4..23, the custom play orders C1..C20 (not in the file; nothing plays them yet, slice M2, and the screen does not offer them, slice M4). The writer writes 1.2 only when a slot (of a stored scene, for `SCEN`) holds PLAYMODE with a value 4..23 in any of its three rows, 1.1 when it holds the id 20 or 21, and 1.0 for every other bank, byte for byte, so the version written is the lowest that holds the data and every project that never used a C order is the file it always was (the pinned fixtures of ctest `project_python` keep their sizes and CRC-32). Compatibility, both ways: an older file in a new build reads as it always did (a PLAYMODE value above 3 in a 1.0 or 1.1 chunk reads as RND, 3, what every build before this one played); a 1.2 file in an older build loads as a newer minor ("newer fields skipped"), the value above 3 is held to 3 (RND), and its next save writes 1.1 or 1.0 with RND — a downgrade through a save loses the order, nothing else. In 1.2 a value above 23 is held to 23. Tests: `tests/perf_playorder_format_test.cpp`, ctest `project_python` (C++ against `o3project.py`, both ways, the same reading of every version).

## 11. Known gaps (for the slices that need them)

- Per-pattern tempo and swing of the OG pattern header are not stored (the project has them).
- An OG step has six bytes and no volume byte; the model's step has a volume byte of its own, and Export writes it as FX type 18 (`og.md` section 4). The mapping is OG import's.
- Engine FX parameters of the master section (the limiter's), automation lanes (ADR 0009: open) and module state beyond the blob arrive as new chunks. The send effects' controls are `SNFX` since OS-PERSIST2; the OG's own delay and reverb values (`OGPM` groups 1 and 3, kept verbatim by the importer) are not mapped into `SNFX` yet (open: an import would fill it, an Export would read it back), and until they are `SNFX` takes precedence over `OGPM` when both exist.
