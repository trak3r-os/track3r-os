# Parameters, settings and MIDI Learn: the `SETS` and `LRNB` chunks and the device settings file (`O3ST`), version 1

Status: specified and implemented with OS-002d, 2026-10-11 · Decisions: ADR 0009 rev 1 (parameters are descriptors; settings are parameters with scope device or project; default-fill for old or unknown data; MIDI Learn; ParamChange at block boundaries), ADR 0007 (IFF-style chunks, versioned, CRC), ADR 0011 (declared layout), `docs/design/product-ux.md` decision 8 and the maintainer's answer to Q4 (two Learn stores, pickup by default), the OG feature triage D-1 (the settings the official 1.9.2 manual describes under Project Settings are stored per project: documented, not verified).

## 1. What a parameter is

Every automatable value has a **`ParamId`**, 32 bits: owner kind (8), index (8), field (16). A value of an id is never renumbered: Learn bindings and settings files hold them.

| Kind | Id | Index | Where the value lives | Scope |
|---|---|---|---|---|
| `Instrument` | 1 | slot 0..63 | `Instrument::sampler` (INST chunk) | project |
| `Track` | 2 | slot 0..15 | `TrackSlot` (TRAK chunk) | project data, **device** Learn store |
| `Master` | 3 | 0 | `MasterSettings` (PHDR chunk) | project data, **device** Learn store |
| `Project` | 4 | 0 | the project's settings block: the `SETS` chunk of the project file | project |
| `Device` | 5 | 0 | the device's settings block: the `SETS` chunk of the settings file | device |

Each has a **descriptor** (`core::ParamDesc`, constexpr, one row per field in `model/params.cpp`): name (12 characters), unit text, range, default, number of encoder detents across the range and a coarse multiplier, a curve (linear, log, exp, or a table of knots), a unit that decides how a value is shown and typed back (whole number, distance from the middle, percentage of the range, seconds with three decimals, enumerated name: the displays the rows use; a Hz, dB or note display is one more case when a row needs it), flags (modulatable, learnable, smooth) and the page of a generated edit page it belongs to. Values are floats at this level, in the descriptor's units, which are the model's: a cutoff is 0..1 as the instrument stores it. An integer field holds the nearest whole value, a switch is 0 or 1. A value outside `[min, max]`, or NaN, is refused (`BadValue`), never clamped by the model; the actions clamp, because an encoder turn wants to stop at the end.

The generated page, MIDI Learn, the settings files and the undo journal all read the tables; a new parameter is one row. The descriptors show a value in these forms (plain integers for volume, tune and fine tune, the pan as its distance from the centre, envelope times as `%.3f` seconds, cutoff, resonance, sustain and amount as a percentage of their range; the encoder step is one percent a detent for cutoff, resonance, sustain and amount, and for the envelope times 100 steps of 10 ms up to one second and 90 of 100 ms up to ten). The envelope time is one table curve with a knot at 100/190, so that every detent is 1/190 of it (the second is at 52.6 % of it).

### 1.1 The instrument, track and master tables (project data, not in these chunks)

Instrument fields 0..12: volume, panning, tune, fine tune, glide, filter (off, on), filter type (Low-pass, High-pass, Band-pass), cutoff, resonance, delay send, reverb send, overdrive, bit depth. Envelope `e` (0..5: Volume, Panning, Cutoff, Wavetable Position, Granular Position, Finetune), field `f` (enable, amount, attack, decay, sustain, release) is field `0x20 + 8 e + f`. 49 per instrument, in four pages: VOICE (volume, panning, tune, fine tune, glide), FILTER (filter, type, cutoff, resonance), ENV (the six fields of one envelope), SENDS (delay, reverb, overdrive, bit depth). Ranges and defaults: `model/params.cpp`. **Every default is this OS's default instrument parameter set** and the value `init_instrument` gives, which a test holds, so that reset is what a new instrument is: volume 50, panning 50 (centre), cutoff 1.0 (so that switching the filter on does not silence the instrument), bit depth 16, and in every envelope amount 1.0, sustain 1.0, decay 0, release 1000 ms; the volume envelope (0) is on with a 10 ms attack, the other five are off with a 3000 ms attack. Track fields: volume, pan, mute, solo, bus; master: volume, dry, reverb, delay, dry mute, reverb mute, delay mute, limiter.

## 2. Settings: the two scopes

A settings block (`model::Settings`, 428 bytes since OS-MIDICCMAP S1 and unchanged by OS-MTC A3 and B3; 396 since E-CFG-03; 388 since OS-006e; 348 before) holds the values of one scope, a generation counter for each, and the Learn store of that scope (section 6). The values are bytes, in the order of the fields; the block has room for 32 fields (`Settings::kMaxFields`, `kValueBytes`; 26 until OS-MIDICCMAP S1, 24 until E-CFG-03, 16 until OS-006e, which needed the 17th: in memory only, the files hold entries, not this block) where the device scope has 30 (7 when this was written; the room is 17 of 24 since OS-LIVEREC and OS-006e, 18 of 24 since OS-USBAUDIO, 20 of 24 since OS-METRO, 22 of 24 since OS-RECMICRO, 23 of 24 since OS-PADOFFSET, 25 of 26 since E-CFG-03, which kept id 25 for row 58, PAT SWITCH; OS-MIDICCMAP S1 raised the room 26 -> 32 and appended CC MAP, id 26, so the scope was 27 of 32 and OS-MTC A3 appended MTC OUT and MTC START, ids 27 and 28, making it 29 of 32: the spec's ids 26..28 became 27..29 because CC MAP took 26 first) and the project 3, so a scope can grow by rows without the block changing.

**Project settings** (kind 4; the project file; triage D-1):

| Field | Name | Values | Default | Source |
|---|---|---|---|---|
| 0 | ANTI-ALIAS | Off, On | On | the anti-aliasing switch; the default On is our choice (the official manual lists a setting of this name under Project Settings: triage D-1; what the official firmware defaults to is an open research question) |
| 1 | LIMITER | Subtle, Extreme | Subtle | the limiter mode. (The catalog says "Subtle/Hard" for 1.2.0: the name is to be confirmed) |
| 2 | SENDS | Pre-fader, Post-fader | Pre-fader | PAR-024; Pre-fader is our default (what the official firmware does is an open research question, triage section 5) |

Only settings whose default is decided are in this table: the project file leaves `SETS` out when every setting is its default, so an unsourced default would become part of every project written without it, and could not be changed later without changing what those files mean. **SNAP TO ZERO** (PAR-111, 1.7.0 release note; the manual puts it under Project Settings) is therefore not a project setting yet: its default and its threshold wait for a sourced contract (open item below). Adding it later is a row at field 3, with no version bump.

**Project overrides (OS-004d).** The MIDI settings below (fields 7..11: CLOCK MODE, MIDI IN, MIDI OUT, IN CHANNEL, OUT CHANNEL) stay **device-level rows**: nothing was added to or removed from this table for them. A project may also carry the routing that has no row (CLOCK OUT per port, the notes' ports and channel, the offsets, FOLLOW, the CC numbers) in its `MIDI` chunk (`docs/formats/o3-project.md` section 3): when a project that has one is loaded its values are applied after the device's, so they win until the settings are changed or another project is loaded; a project without it leaves the device's as they are. No row was appended, so the row-append rule did not apply and the device file is unchanged.

Fields 7..12 were **appended** by OS-011a, the way this section says a row is added: no new chunk, no version bump. A file written before them (7 entries) reads with no entry skipped and these six at their defaults; a file written after, read by the previous build, has six entries that build does not know (skipped and counted: `skipped_entries`), so saving over it there drops them. The Config screen shows them in two pages: MIDI (fields 2, 3, 6, 7..11) and DISPLAY (0, 1, 4, 5, 12); the page is a descriptor group, not part of the file.

Field 13 (USB RETURN) was **appended** by OS-USBRET by the same rule, and the file of the build before it (13 entries, 142 bytes) is the test's literal for it: it reads with no entry skipped and USB RETURN On, the layout every unit had; a file with the setting written by this build and read by the previous one has one entry that build does not know (skipped and counted). Config gets a fifth page, USB (group 2), for it. Changing it while the unit presents AUDIO makes it re-enumerate on the host (`app_main.cpp` `sync_usb_return`; the `usb return` and `usb profile <n> out|duplex` console commands write the same setting). Since OS-USBAUDIO the Config row is **press to apply**: the encoder only changes a pending value (shown starred) and a confirmed press of F7 writes the setting.

## 3. The two chunks

Both begin with the chunk version (`0x0100`) and are the same in the project file and the settings file; one codec (`formats/src/settings_chunks.cpp`) reads and writes both.

**`SETS`**: `u16 version`, `u16 count` (0..64), then `count` entries of `u32 ParamId` and `f32 value` (8 bytes). The writer writes **every** setting of the scope, in field order; the length is exactly `4 + 8 count` (a newer minor may append). Payload 28 bytes for a project, 252 for a device (244 before OS-LEDBPM appended STATUS LED, 236 before OS-MTC B3 appended MTC IN, 212 before OS-MTC A3 appended MTC OUT and MTC START, 204 before OS-MIDICCMAP S1 appended CC MAP, 188 before E-CFG-03 appended TRANSPORT IN and OUT, 180 before OS-PADOFFSET appended PAD OFFSET, 164 before OS-RECMICRO appended REC MICRO and REC VELOCITY; 148 before OS-METRO appended METRO and COUNT-IN, 140 before OS-USBAUDIO appended USB AUDIO, 132 before OS-006e appended RETURN LEVEL, 116 before OS-LIVEREC appended REC POLY and REC QUANTIZE, 108 before OS-USBRET appended USB RETURN, 60 before OS-011a appended six settings; 148 once OS-USBAUDIO appended USB AUDIO).

**`LRNB`**: `u16 version`, `u16 count` (0..64; this version keeps 32 bindings, the rest of a longer one is skipped and counted), then `count` entries of `u32 ParamId`, `u8 cc`, `u8 channel`, `u8 mode`, `u8 flags` (8 bytes): the bindings in use, packed in slot order. `cc` 0..127; `channel` 0 (every channel) or 1..16; `mode` 0 pickup, 1 jump, 2 relative; `flags` bit 0 follow (the id's index is 0 and only its kind and field count: the binding acts on whichever instrument is selected). The length is exactly `4 + 8 count`. **Insert parameters (OS-INSFX S7, new Community OS behaviour):** a binding may name `ParamKind::Insert` (kind 6) in a project file: the id's index is `track * 2 + slot` of the insert (0..31; the master insert is 32, the project record `where` 16 slot 0) and its field the module's parameter (0..31); the store is the project's, and a binding never follows. The version of the chunk does not change (an older reader's rule below skips what it has no kind for).

**Reading is tolerant and says so** (ADR 0009: default-fill for old or unknown data). The shape of a chunk is the only error: a count above 64 or a length that does not fit it (`Malformed`; a chunk of a **newer minor version** with a count above 64 is not an error: its first 64 entries are read as far as they are known and the rest is skipped and counted), a major version above 1 (`NewerMajor`; version 0 is `Malformed`). An *entry* that this version cannot use is skipped and counted, and the setting keeps its default:

- SETS: the id is of another kind or has an index, the field does not exist, the value is NaN or outside the range of the descriptor. A value that is in range is stored as the descriptor's storage holds it (an integer field rounds). The same id twice: the later entry wins.
- LRNB: the binding is not valid (a controller above 127, a channel above 16, an unknown mode or flag, an unbindable kind (an older firmware: every Insert binding, kind 6; skipped and counted, lost on its next save, the project opens), an Insert id this version has no row for (index above 32, field above 31), a follow binding with an index or on an Insert, an empty parameter), or belongs to the other store (a track, master or device parameter in a project file; an instrument or project parameter in a settings file). A valid binding goes into the store by `core::learn_plan`: the same parameter again takes its slot; every other binding that listens to the same message (the same controller on channels that meet, 0 meeting all) is displaced, the first of them giving its slot to a new parameter; otherwise the first free slot; a full store skips it.

A setting the file does not mention is the default. The counts are `Report::settings_skipped` (project) and `settings::Report::skipped_entries` (settings file); the project reader copies the first into `FormatReport::sanitised`.

## 4. The device settings file (`O3ST`)

One small file, at most **1,024 bytes** (today 286, and 554 with every setting and all 32 bindings), read and written whole from and to a buffer: the platform reads it into 1 KiB and calls `formats::settings::read()`, calls `write()` into 1 KiB to save it. No file I/O, no heap, no state. Where it lives on the SD card and when it is saved (when a generation moved) are the platform's. It is a registered format like the others: `register_builtin_formats()` adds `settings` (`.o3st`, `FormatKind::Settings`, read and written, sniffed by `settings::sniff()`), whose strategies read into `ReadParams::settings` and write from `WriteParams::settings` (a `model::Settings` of kind Device) and touch no project (1 KiB buffer each, inside `BuiltinFormats`); `FormatReport::sanitised` is the number of entries skipped and `unverified_version` says a newer minor was read.

```
"FORM"  u32 length   "O3ST"   [SETS] [LRNB] ... "CRC "
```

Chunks: `SETS` (written always), `LRNB` (written when a binding is in use); on reading each at most once, in either order; any other chunk (a printable id) is skipped and counted (`unknown_chunks`); **unlike the project file they are not kept**, so saving over the file of a newer OS drops them. `CRC ` is last and covers every byte before its header, as in the project file (CRC-32/ISO-HDLC); a newer minor of the CRC chunk may carry more bytes. Bytes after the `FORM` are ignored. `length` is even, at least 4 and at most 1,016.

Errors (`settings::Error`): `Truncated` (fewer bytes than the `FORM` says, or than its header), `BadMagic`, `BadCrc`, `NewerMajor`, `Malformed` (odd or short length, a chunk that overruns the `FORM`, a pad byte that is not zero, a chunk twice, no CRC chunk or a chunk after it, an id that is not printable, a `SETS` or `LRNB` of the wrong shape), `TooBig` (over 1,024). **After any error the block is the defaults and valid**: a missing, damaged or newer file never leaves the device unusable (ADR 0009's standalone principle); the platform notifies. The container is checked first, the CRC included, then the chunks are decoded: no setting of a file that fails is applied.

Versions follow the project format's rules (`o3-project.md` section 3): a newer minor is read as far as this version knows it (`newer_minor`; the fields it appends are lost on the next save), a newer major is refused.

## 5. In the project file

`SETS` and `LRNB` come **after the last `INST` chunk and before the unknown chunks and the `CRC ` chunk** (ranks 7 and 8, `CRC ` 9). `SETS` is written when a project setting is not its default (then all three are written), `LRNB` when a binding is in use; so a project that uses neither is the file it always was (186 bytes for the default project, byte for byte). A reader from before this slice keeps both as unknown chunks, which is why adding them needed no version bump (`o3-project.md` section 10): it writes them back after the known chunks. The Python reference (`o3project.py`) applies the same rules, entry by entry, and `project_python` compares what C++ and Python make of 21 damaged or foreign `SETS` and `LRNB` chunks and that both refuse 8 malformed ones.

Memory: the project's settings block (348 bytes) and one generation counter per parameter of the instruments, tracks and master (3,224 x 4 bytes) are part of the arena: **`kModelArenaBytes` 1,905,112 -> 1,918,360** (project region 1,920 KiB, slack 46.6 KiB).

## 6. MIDI Learn

A control change message binds to the parameter under the cursor and moves it from then on.

**Two stores** (maintainer decision 8): the **device** store holds what is about the controller and the mixer (kinds Track, Master, Device), the **project** store what is about the music (Instrument, Project): the kind decides (`core::learn_scope`). "Follow the selected instrument" is the `follow` flag of a binding, not a third store. A store is 32 slots of 8 bytes: `{param, cc, channel, mode, flags}`, an empty slot all zero. One controller moves one parameter in a store, so binding takes over the message (section 3). A message moves the bindings of both stores.

**Modes** (per binding, default **pickup**, maintainer answer Q4): *pickup*: an absolute controller value does nothing until the knob has reached the parameter (within one step of its 0..127 position, or it crossed it since the last message), so a parameter never jumps; when anything else changes the parameter (the screen, undo, another binding: its generation moved) the knob must catch it again. *Jump*: the parameter takes the knob's position at once. *Relative*: the controller is an increment, 1..63 up by that many detents, 65..127 down by 128 - v, 0 and 64 nothing (**PROVISIONAL**: this is the common encoding; whether the official firmware has such a mode is an open research question).

**The action** `midi.cc`, argument `(channel << 16) | (cc << 8) | value` (channel 1..16, 0 unknown; `cc` and `value` 0..127; anything else is refused whole). **MIDI input (OS-013a)**: the render parses the control changes of both ports (running status, real-time bytes inside a message, SysEx skipped; controllers 120..127, the channel mode messages, are dropped) into a 32-entry ring (`midi::CcInput`, kept in SDRAM) and the main loop takes up to 16 a pass (`App::poll_midi_cc`), drops what the device settings MIDI IN (ports) and IN CHANNEL exclude, and runs this action; it never runs in an interrupt, because a parameter is written through the editor and the ParamChange ring has the main loop as its one producer. Messages that arrive while a project loads are discarded. A knob sweep is one undo unit per message (the journal's coalescing is an open item). Notes in are not routed yet (open item). With the Learn overlay up it binds the controller to the target (the parameter under the cursor of the screen below) in the store of its kind; otherwise it moves what is bound. In the overlay F1 unbinds the target and F2 steps its mode; the list under the target shows every binding of both stores (the project's, then the device's), the arrows or the encoder choose one, F3 deletes it and F4 clears all of them (pressed twice: the key's label asks); the chord FX1 + FX2 or F8 closes it. Project-store edits go through the editor (`Editor::set_learn_slot`), so each is an undo unit, a bind that displaces others is one unit; the device store is not part of the project's undo. Scenario word: `midicc <channel> <cc> <value>`.

## 7. ParamChange, generations, undo

The main loop tells the audio side with `core::ParamChange {ParamId, f32 value, u32 ramp_samples}` (12 bytes) over `core::ParamRing`, an SPSC ring of 256 (ADR 0013 D6) drained in the graph's pass, after the block's voices, at most 64 a block. `ramp_samples` 0 means the engine's own smoothing for that parameter (descriptor flag `smooth`). The value is the one that was **stored**. The producer is the main loop: edits, Learn, and undo and redo (the parameters a unit set by value, `Editor::applied()`; a unit that replaced a whole instrument, track or master is counted in `Session::param_resyncs` for the engine to re-read). A full ring drops the push and counts it (`Session::param_drops`); values are absolute, so the next change of the parameter catches up.

**Generations**: `Project::param_generation(id)` and `Settings::generation(field)` are free-running 32-bit counters that advance when *that* parameter's value changes, by `set_param` or by a whole-object mutator for the parameters whose value it changed, and by nothing else (setting a value to what it is changes nothing); `reset()` and `Settings::init()` advance all of them; none ever repeats. Screens poll them on redraw; there are no observers.

**Undo**: `Editor::set_param` journals the id with the new and the old value (40 bytes of journal), `set_learn_slot` the slot with the new and old binding (48 bytes). A knob sweep is one unit per message (a coalescing rule would need a journal feature and is an open item).

## 9. Open items and follow-ups

- **SNAP TO ZERO** (PAR-111, 1.7.0; improved in 1.8.0, PAR-133): not a project setting until its default and its zero-crossing threshold are decided (open research question: the official firmware's values are not known here). It would be project field 3, an Off/On choice; nothing in a file changes when it is added.
- **Provisional values** (device settings, which are written whole, so a later change of a default does not alter a file that has them): the defaults of NUMBERING and MIDDLE C and the names of NUMBERING; the relative encoding; the clock sync range (PAR-119, not specified yet).
- **Undo granularity**: each encoder turn and each controller message is one undo unit; coalescing consecutive edits of one parameter needs the journal to rewrite its newest record (OS-002c's journal) and a rule for what "consecutive" is.
- **Whole-object undo** gives the audio side no values (`param_resyncs`): the engine's re-read protocol is OS-005b's.
- **Learn**: no per-binding range ("the encoder sets the range", `product-ux.md` workflow 3); no UI to make a follow binding (the data, the resolution and the tests exist); the device store has no screen but the overlay (the Config page, P3, is a second consumer of the generated page for kind Device).
- **Not parameters yet**: the LFO block (its speed list differs for the amplitude envelope: 24 of the 29 labels, offset 5) and the envelopes' `loop` flag (the instrument file's "envelope or LFO" flag), granular and wavetable fields, sample points and slices (the Wave screen's), tempo and swing, theme.
- **Instrument defaults**: this OS's default instrument has more than the parameter tables hold (LFO amount 0.5, loop points 1 and 65534, a wavetable window size of 2048); the parameter tables carry the parameters only. The rest is the instrument slice's (OS-004).
- **Runtime-only settings (OS-PERSIST2)**: the settings that the 2026-10-12 notes called "not persisted (format change)" (MIDI CLOCK OUT, offsets, routing; USB mode, profile, stem map) are the project's since OS-004d, and the ones that came after (the MUTE MODEs, the note-entry settings and JUMP, the Perform scenes, the send effects' controls) are project chunks too (`o3-project.md`, "The session state"): **this slice added no device row and changed nothing in this file**. The device scope has 18 of its 24 fields (USB AUDIO, OS-USBAUDIO, is the 18th, id 17; RETURN LEVEL, OS-006e, is the 17th; REC POLY and REC QUANTIZE, OS-LIVEREC, are 15th and 16th: ids 14 and 15); the two things that belong to the device and are still runtime only (the pads' mode, the recorder's configuration) wait for the Config slice, which owns the page that shows them, and for a maintainer decision on the project-or-device split of the recorder.
- **Platform**: where the settings file is on the card, when it is saved and the notification of a bad file are the platform's; the MK66 image does not attach a document yet, so its PARAMS page shows the descriptors' defaults and says "NO PROJECT OPEN".
