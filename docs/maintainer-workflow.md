# How the maintainer works (the agent set-up behind this repository)

This page is the maintainer's own way of running the project with Claude Code: roles, lanes, agents, skills and the build machines. It is one working set-up, not a rule of the project. The project's rules are in `CLAUDE.md` (hard rules, layout, standards, branches); you can follow them with any tool, or with none. To use this set-up on your own machine, or to drop it, read `docs/agent-setup.md`: what to change is listed there.

The root `CLAUDE.md` imports this page at its end, so a Claude Code session in this repository loads it. Delete that one import line to work without it.

## The maintainer's machines

The operating parameters (lane count, CI rules and job counts, agent context caps, backlog limits) live in one file, `.claude/ops-params.ini`; the SessionStart brief prints it. Change a number there, not in the prose.

- **Never max out the machine:** `nice -n 10 taskset -c 2-19` (cores 0-1 always stay free for the system), 18 jobs in total at most. Job counts (`local_jobs`, `local_ctest_jobs`) are in `.claude/ops-params.ini`. Whoever holds `flock "$(git rev-parse --git-common-dir)/../.claude/worktrees/.ci.lock"` (a full `tools/ci.sh` run, or an `mk66`/`qemu` run) uses `O3OS_CI_JOBS=10`, which sets build and ctest parallelism.
- **Remote build machine first.** Every agent sends its `tools/ci.sh` runs (scoped or full `host`, `e2e`, `qemu`, `mk66`) to the remote build machine with `tools/remote_ci.sh` (remote threads per lane count: `ops-params.ini`; the full log back in `build-remote/`); so does the edit-compile loop (maintainer, 2026-10-22: locally only the cmake configure for the LSP and the hooks); image builds and image gates stay local. It is named by `O3OS_REMOTE_CI`, set locally only; exit 3 or 255 (no remote) means the local rules above. Details: `docs/toolchain.md`.

## How work is organised

- **Sessions by role** (names change after a restart; use ListAgents). Two sessions run standing: the **orchestrator** (Opus) runs the backlog (specs → worktree → engineer → review → merge → image) in as many lanes as `[lanes] engineers` of `.claude/ops-params.ini` says (the fast lane is in `fw-feature`; lane files do not overlap; the maintainer's latest word wins; reviewers, verifiers and doc agents are not lanes), keeps a recurring keep-alive ping every 30 min so its context never goes an hour idle, and only moves the queue (routine in the `fw-feature` skill); the **tester** (Sonnet) installs gated images on the unit and runs the HIL scenarios when the orchestrator asks, and the orchestrator pings it when it shows idle. Other sessions run only when the maintainer opens them: a **spec session** writes specs and ADR amendments and takes delegated product/UX decisions; a backlog session may own `BACKLOG.md` and relay the maintainer's decisions.
- **Subagents** (`.claude/agents/`): `firmware-engineer` (Sonnet) implements one scoped change; `firmware-reviewer` (Sonnet, read-only) reviews; `build-verifier` (Haiku) does the mechanical build/test/budget gate; `doc-keeper` (Haiku) updates status docs; `radar-researcher` (Sonnet) researches ideas; built-in `Explore` for searches and `Plan` for designs. The project agents take their model from their frontmatter; pass `model` explicitly to built-in agents, which otherwise inherit the orchestrator's model. Keep token spend low: brief agents with a short packet (not CLAUDE.md or whole specs), fold through the same engineer, cap agent reports. The harness enforces the budgets: `maxTurns` in each agent's frontmatter, and the PreToolUse hook `.claude/hooks/ctx_cap.py` denies a subagent's tools (git wrap-up and `build-remote/STATE.md` excepted) past `hard_ctx`, or past `stop_ctx_no_commit` for an engineer with no commit (`.claude/ops-params.ini`, `[agents]`). The PreToolUse hook `.claude/hooks/git_guard.py` denies a subagent any git command that changes the main checkout's state (checkout, switch, merge, commit, reset and the like) and any push to dev or main; the SessionStart brief warns when another `claude` process runs the same resumed session (an orphan after a reload).
- **Skills** (`.claude/skills/`): `fw-feature`, `decide`, `rt-optimize`, `tmod-perf`, `dsp-port`, `fw-build`, `fw-gate-check`, `hw-session`, `sd-module`, `radar`, `handoff`.
- **Backlog states** (`docs/roadmap/BACKLOG.md`): IDEA → APPROVED → QUEUED → IN PROGRESS → DONE, plus PARKED and DROPPED. The limits on in-progress and queued rows are in `.claude/ops-params.ini`; a batch of one lane counts as one.
- **QA catalogue** (`docs/qa/catalogue/<screen>.md`): every merged item adds its rows (function, gesture, expected result, sim scenario, unit scenario, spec). It feeds the test battery and the user manual (`docs/manual/`).
- **Landing on dev:** `python3 -I tools/land.py <branch>...` is the only path from a reviewed, pushed branch to `dev`: it merges in the `land` integration worktree, runs CI on the merge result, fast-forwards `dev` in the main checkout only when green and pushes (`tools/o3merge.py` stays for merging `dev` into a branch).
- **CI break:** a trivial, isolated CI break (one obvious edit, one test proves it) is fixed by the orchestrator itself on a `fix/` branch, landed with `tools/land.py`; it opens no lane and spawns no agent.
- **Agent reuse:** an engineer is reused only for related items and below the context caps in the `[agents]` section of `.claude/ops-params.ini`; otherwise a fresh agent is briefed with a short written state (a "state for implementer" section in the spec).
