# SID-style instrument — radar card
Maintainer's words: "podemos abrir SID, es facil?" then, after being told a .sid file is 6502 code and a SID-style instrument makes more sense: "si, quiza convierte el instrumento chip en SID, tiene sentido?" · 2026-10-30 · Status: planned

Related card: `goattracker-import` (depends on this one). Backlog row: OS-SID (QUEUED 2026-10-30; spec `docs/specs/OS-SID.md`).

Scope notes. The NES engine is out of scope by maintainer decision and this card does not propose one. Chip already exists and stays as it is. Playing `.sid` files (6502 code plus the chip) is not proposed here: the maintainer agreed a SID-style instrument makes more sense.

## What it is
A new loadable instrument module `sid.tmod` (`/modules/instruments/sid.tmod`, kind instrument, one mono voice an instance like Chip) that sounds like the MOS 6581 / 8580 voice: saw, triangle, pulse with width modulation, noise, the combined waveforms, hard sync and ring modulation, the stepped ADSR, and the multimode resonant filter. It is built from the structure of `modules/chip/` (control-rate pitch with arpeggio, sweep and vibrato; the module's pages and views), not by changing Chip.

Verdict on the two options (the question "convert Chip into SID?"): **confirm A (new `sid.tmod`, Chip unchanged); refute B (a SID mode inside Chip).** Reasons, in order of weight:

1. **The ABI ceiling makes B impossible and A tight.** `module/sdk/o3module.h` allows at most 32 parameters (`O3M_PARAMS_MAX`), 4 pages (`O3M_PAGES_MAX`) of at most 8 parameters (`O3M_PAGE_PARAMS_MAX`), 16 labels per enum (`O3M_LABELS_MAX`), 8 views (`O3M_VIEWS_MAX`). Chip already uses 20 parameters on 4 pages (TONE 8, ENV 4, PITCH 5, ARP 3). A SID voice needs about 31 (proposal below), so a SID mode inside Chip would need 11 more on top of 20 = 51: it does not fit. Raising the ceiling is a published-ABI change (Level C). A fresh module fits in 31 of 32.
2. **Persisted data.** A preset is twenty little-endian float32 values in a fixed order (`modules/chip/README.md`), stored in projects. B changes either the meaning of existing slots or the length of the blob; both touch the persistent-format rule (version bump, backward-compatible loader, round-trip test; maintainer decision). A touches no existing project.
3. **Cost lands on everyone.** Chip's hot part is 2,096 B of the 14 KiB SRAM_L slab shared by all modules (README). A SID mode would grow it for every Chip user; as a separate module the slab is used only when a SID instrument is loaded. Chip's measured cost (2.3 to 2.8 % of a block) would also rise with the branches.
4. **Identity.** Chip is the NES / Game Boy voice (4 duties, 15-bit LFSR, 4-bit volume steps). The SID voice differs in nearly every part (12-bit pulse width, 23-bit noise, combined waves, 8-bit ADSR with a rate table, a filter). Two clear instruments are easier to explain than one with a mode switch.
5. **Cost of A is only duplication.** The control-rate pitch code, parameter clamping and views pattern are small (a few hundred lines) and written by the same author under MIT; copy then diverge. Do not refactor Chip to share a header (no drive-by refactors).

"Converting" has one honest reading: a later optional tool that maps a Chip preset to a SID preset (pulse duty to pulse width, triangle to triangle, noise to noise, ADSR times to the nearest SID rate). It is a table of a dozen lines and not needed for v1.

### What a SID voice is (facts from public documentation; see Prior art for the sources)
- **Three voices** per chip, each with an oscillator, a waveform selector, an envelope generator and a gate bit; one filter shared by the three, one master volume ([C64-Wiki SID](https://www.c64-wiki.com/wiki/SID)).
- **Waveforms:** sawtooth, triangle, pulse (with a variable width, so pulse-width modulation), noise; triangle, sawtooth and pulse can be selected together for further "combined" waveforms, noise cannot be combined usefully ([Wikipedia, MOS 6581](https://en.wikipedia.org/wiki/MOS_Technology_6581); [C64-Wiki SID](https://www.c64-wiki.com/wiki/SID)). On the 8580 the combined waveforms are louder and clearer than on the 6581 (same Wikipedia page).
- **Sync and ring modulation** use the neighbouring voice: voice 1 with voice 3, voice 2 with voice 1, voice 3 with voice 2 ([C64-Wiki SID](https://www.c64-wiki.com/wiki/SID)). In a mono instance there is no neighbour, so the module carries an **internal modulator oscillator** (own phase, pitch = note + a "Mod Pitch" offset in semitones, a parameter that can be modulated). Sync resets the main oscillator's phase when the modulator wraps; ring modulation replaces the triangle with the triangle multiplied by the modulator's sign.
- **Envelope:** attack, decay, sustain, release; attack / decay / release are 4-bit rate indices, sustain a 4-bit level. Published times run from 2 ms (attack 0) to 8 s (attack 15) and from 6 ms to 24 s for decay and release, at a 1 MHz clock ([C64-Wiki ADSR](https://www.c64-wiki.com/wiki/ADSR)). The mechanism: a rate counter (a table of 16 periods in clock cycles, from about 9 to about 31,250) steps an 8-bit envelope counter; in decay and release a second divider stretches the period at the levels 93, 54, 26, 14, 6 so the fall is a piecewise-linear exponential; the rate counter is not reset by the gate, which gives the "ADSR delay" ([reSIDfp EnvelopeGenerator docs](https://sidplay-residfp.sourceforge.io/docs/classreSIDfp_1_1EnvelopeGenerator.html); the same numbers appear in an LMMS-bundled copy of reSID, <https://sources.debian.org/src/lmms/1.1.3-8.1/plugins/sid/envelope.cc/>; the period list was read only as a search-result snippet, the full table is to be taken from the Programmer's Reference Guide or a datasheet, not from source).
- **Filter:** one state-variable style filter with low-pass, band-pass and high-pass outputs that can be combined (LP + HP is a notch), a digitally set cutoff and a 4-bit resonance, with a per-voice routing bit; low-pass and high-pass 12 dB per octave, band-pass 6 dB per octave ([Wikipedia, MOS 6581](https://en.wikipedia.org/wiki/MOS_Technology_6581); registers: [C64-Wiki SID](https://www.c64-wiki.com/wiki/SID)). reSID models it as a summer and two integrators in a loop, a biquadratic filter, which Bob Yannes confirmed per a comment in a Java port ([Wikipedia, ReSID](https://en.wikipedia.org/wiki/ReSID), which also cites the 6581 filter distortion work of Antti Lankila that became reSIDfp).
- **6581 against 8580:** the 6581's cutoff range is non-linear, differs from chip to chip and often distorts; the 8580's is linear, consistent, nearly distortion-free and reaches higher resonance; filter capacitors 470 pF against 20 nF; the 6581 lets the volume register play digital samples audibly ([Wikipedia, MOS 6581](https://en.wikipedia.org/wiki/MOS_Technology_6581); [C64-Wiki SID](https://www.c64-wiki.com/wiki/SID)).
- Register widths used in this card (frequency 16 bit into a 24-bit accumulator, pulse width 12 bit, noise LFSR 23 bit, cutoff 11 bit, resonance 4 bit, envelope counter 8 bit) are common knowledge of the chip but were **not confirmed by the pages read here** (C64-Wiki and Wikipedia do not state them). Verify against the MOS 6581 datasheet or the Commodore 64 Programmer's Reference Guide before coding: open research question.

## Approach
**inspire, written from scratch; chip documentation as the specification; GPL emulators only as listening references.** Not a port: a faithful emulator runs at about 1 MHz per voice and resamples (Teensy64's own note on reSID's CPU cost on this very MCU is the warning), and its code is GPL while Chip and the SDK are MIT.

Design (all float, block based, like Chip):
- **Oscillator:** a phase accumulator in float (24-bit-like resolution is enough in single precision for audio: 2^-24 of a period). Saw and pulse are band-limited with PolyBLEP exactly as Chip's pulse is (`blep()` in `modules/chip/chip_dsp.h`, one step of height 2 per edge); triangle is left raw (as in Chip); noise, combined waveforms and the triangle are the "raw" character of the chip. Pulse width is a 12-bit-like value (1..99 %), modulated at control rate by a built-in PWM triangle LFO (PWM Depth, PWM Rate) and by the host modulation target.
- **Noise:** a 23-bit LFSR (feedback and the 8-bit output tap pattern to be verified from the datasheet) clocked at 16 x the oscillator frequency, as Chip's noise is (the same sample-and-hold idea, `kNoiseClock = 16`); output is a multi-level 8-bit value (not +-1).
- **Modulator oscillator** for sync and ring: its own phase and increment (the note's increment x 2^(ModPitch/12)). Sync: on the modulator's wrap, the main phase is reset to the fraction of the sample that remains, and a PolyBLEP residual of height equal to the jump is added (sub-sample accurate hard sync without aliasing). Ring: the triangle output is multiplied by the modulator's sign.
- **Combined waveforms:** three-bit selection (saw + triangle, pulse + saw, pulse + triangle, all three): a table indexed by the phase. Real chips give measured, chip-dependent tables. Plan for v1: **own approximate tables of 256 entries x 8 bit, 4 combinations x 2 models = 2 KiB**, generated by a documented formula (bitwise AND of the waveform bits followed by a smoothing step), stored in the module's hot part, with linear interpolation between entries. A full 4,096-entry table per combination would be 4 x 4,096 B = 16 KiB per model, 32 KiB for both *estimate*, in the module's SDRAM, with the risk of slow reads in the hot loop (hot code should not read big tables: `o3module.h`). Do **not** use reSID's or reSIDfp's table data or fitted parameters (GPL data; see Licence).
- **Envelope:** the SID's rate counter and exponential divider reproduced with integer counters: per sample the chip's clock advances by 985,248 / 44,117.6 = 22.3 cycles (PAL clock, *estimate of the exact ratio*; the 1 MHz figure gives 22.7), so the fastest attack (period 9 cycles) takes 2.5 counter steps a sample, and the slowest rate (about 31,250 cycles) a step every 1,400 samples. Attack, Decay and Release are exposed as the 16 stepped values with labels showing the time; Sustain is 16 levels. The ADSR delay bug is an option only if a parameter slot remains; default off. The output level is the 8-bit counter, optionally smoothed over 32 samples to remove the zipper.
- **Filter:** own code in the module (see "can the module reuse the core's filter" below). A topology-preserving (zero-delay-feedback) state-variable filter, one pass per sample, no oversampling: it stays stable up to the cutoffs needed here, and gives LP, BP and HP simultaneously for the mode mix. Cutoff 0..100 % maps through a model-dependent curve (6581: compressed and non-linear at the low end; 8580: close to linear in log frequency), resonance 0..15 to Q. Per-sample mode mix with the chip's convention (notch = LP + HP).
- **Character, not emulation:** the Model parameter switches the combined-wave tables, the cutoff curve and a mild saturation in the filter for the 6581. The analogue non-linearity of the real 6581 (filter distortion, non-monotonic DAC, DC drift, oscillator leak: the things reSIDfp models) is **out of scope for v1**.
- **Per-track filter instead of one shared filter:** the chip has one filter for three voices; an instance here is one track. For a linear filter (8580 style, no saturation) filtering each voice with the same cutoff and resonance then summing equals filtering the sum, so the difference is small; with Drive on or the 6581 curve it is a different sound. State this in the manual as new Community OS behaviour.
- **Pitch, arp, sweep, vibrato:** as Chip (control rate every 32 samples, `exp2_f` from the host, 3-step arpeggio, sweep, vibrato with delay, host slide / glide via `O3M_NOTE_RAMP`). Pitch is MIDI-note based, not register based.

### Can the module reuse the core's filter?
No; the module must carry its own. `audio/include/o3os/audio/svf.h` is in the core (GPL-3.0-or-later per its SPDX line, uses OS headers and the engine's `hot.h`) and is not offered through the module ABI: `o3m_host` gives a module only `exp2_f`, `log2_f`, `sin_f`, `cos_f`, the draw table and, for apps, read / edit / io tables (`module/sdk/o3module.h`), and the SDK is MIT and must stay free of OS headers (`module/CLAUDE.md`). Adding a filter service to the host is an additive ABI minor (a published ABI: Level C) and not worth it for 40 lines. The core's filter is also the wrong shape: a Chamberlin loop at 2x oversampling with `Q` held to 0.7..5 and a cutoff law of 20 Hz x 2^(i/50) (comments in `svf.h`), while the SID filter needs LP / BP / HP mixing, resonance up to a self-oscillation-near-edge setting and a model-specific cutoff curve. Cost comparison below.

## Cost on MK66 (estimate until measured)
Basis, measured: 180,000,000 / 44,117 = 4,080 cycles a sample; a 64-frame block = 4,080 x 64 = 261,120 cycles. Chip costs 2.8 % of a block per sounding voice on 0.4.9 = 0.028 x 261,120 = 7,311 cycles a block = 114 cycles a sample, and 2.3 % = 5,938 cycles = 93 cycles a sample on fqa.14 (`docs/architecture/cpu-budget.md`, lines 9 and 393). The reference voices measured there: FM 11.7 %, TB-303 21.6 %.

*Estimate*, cycles a sample on top of Chip's 114 (the upper of the two Chip figures):

| Part | Arithmetic | Cycles a sample (*estimate*) |
|---|---|---|
| Chip-like base: oscillator with PolyBLEP, envelope, gain, output | measured | 114 |
| Modulator oscillator (add, wrap) | ~4 flops + wrap | +10 |
| Sync test and phase reset (event cost spread; the BLEP only at a reset: a master at 4 kHz resets 4,000 x ~60 = 0.24 M cycles/s = 0.13 %) | compare + branch | +10 |
| Ring (multiply by sign) | 1 mul, 1 select | +8 |
| Stepped ADSR with rate counter and exponential divider (integer, per sample), against Chip's float ramp | ~25 against ~15 | +10 |
| Combined-wave table with linear interpolation (table in the hot slab) | 2 loads, 1 lerp | +8 |
| Filter: zero-delay-feedback state-variable, per sample (about 8 multiplies and 8 add / subtract on the FPU plus loads) | ~30 | +30 |
| Cutoff / resonance coefficients: `sin_f` and `cos_f` from the host (about 100 cycles each *estimate*) and one divide (~14), once every 32 samples when the cutoff moved | (2 x 100 + 14 + ~20) / 32 | +8 worst case, 0 when static |

Total with the filter: 114 + 10 + 10 + 8 + 10 + 8 + 30 + 8 = 198 cycles a sample *estimate*. 198 x 64 = 12,672 cycles a block = 12,672 / 261,120 = **4.9 % of a block per sounding voice**; 198 x 44,117 = 8.7 M cycles/s = 4.9 % of 180 MHz. With Chip's lower base (93): 177 x 64 = 11,328 = 4.3 %. Filter off (mode OFF skips it): 160 x 64 = 10,240 = 3.9 %. So expect **about 4 to 5 % a voice** (against Chip 2.3 to 2.8 %, FM 11.7 %, TB-303 21.6 %). Three SID tracks = 3 x 4.9 = 14.7 %; eight would be 39 %, too much on a song that already runs 70 to 95 % (`cpu-budget.md`). A silent voice costs nothing.

Using the core's loop for comparison only: 40 cycles a sample (the maintainer's figure) = 40 x 44,117 = 1.76 M cycles/s = 0.98 % of the CPU per voice, 1.1 % of a block. The zero-delay-feedback filter without oversampling is estimated at 30 cycles, 0.7 % of a block, and is stable where a single Chamberlin pass at 1x is not (a Chamberlin loop is commonly quoted as stable only up to about a sixth of the sample rate, 7.3 kHz, which would be why the core runs it at 2x; not verified here).

Levers if the measurement is worse: envelope at control rate with per-sample slope (saves ~10), cutoff recompute only when changed, drop interpolation on the combined tables (saves ~8), mode OFF bypass. Bench items for the first unit session: B1 each wave alone (saw, triangle, pulse, noise, combined), B2 filter on and off, B3 sync and ring active with a swept modulator, B4 held chord of three tracks, all with `diag mod` and the `tmod-perf` skill's procedure.

Memory (*estimate*; Chip as the yardstick: image 6,272 B, hot 2,096 B, instance 192 B, `modules/chip/README.md`):
- Hot part (SRAM_L slab, 14 KiB shared by all modules): five oscillator loops, modulator, ADSR, filter: about 3.5 to 4.5 KB, plus 2 KiB for the combined tables if kept hot = 5.5 to 6.5 KB, 40 to 46 % of the slab (Chip 2,096 B = 15 %). Needs a check that the slab can hold a SID next to Chip, TB-303 and FM; if not, the hot part must be split or the tables read from SDRAM.
- Image on the card: 14 to 18 KB (code, parameter table with labels, three views); with full 32 KiB tables in SDRAM it would be about 50 KB.
- Instance: about 320 B (two phases, LFSR, ADSR counters, filter, PWM and vibrato state, arp; Chip is 192 B for 20 parameters), manifest reservation 336.
- Core flash: 0 B. SDRAM: 0 B (v1 tables hot) or 32 KiB (full tables).

## Fits
- **Layers:** `modules/sid/` (new; `module.json`, `sid_dsp.h`, `sid.cpp`, `sid_gen.h` from `tools/o3m_gen.py`, tests `modules/sid/tests/`), packed by `tools/o3m_pack.py`. No core change if the existing ABI 1.8 services are enough (host `exp2_f`, `sin_f`, `cos_f`, draw API, parameter pages and labels, `pitch: true`, `mod: true` targets, host slide / glide). Skills: `sd-module`, `tmod-perf`, `dsp-port` (reference, not a port).
- **Parameters and pages (proposal, 31 of the 32 allowed; four pages of eight):**

| Page | Parameters |
|---|---|
| OSC (8) | Wave (labels, 8: SAW, TRIANGLE, PULSE, NOISE, SAW+TRI, PULSE+SAW, PULSE+TRI, PULSE+SAW+TRI), Pulse Width (mod target), PWM Depth, PWM Rate, Sync (bool), Ring (bool), Mod Pitch (semitones, mod target), Mod Fine (cents) |
| ENV (8) | Attack, Decay, Sustain, Release (the 16 stepped values; labels carry the time), Volume (dB, mod target), Vel Sens, Transpose, Fine |
| FILTER (7) | Mode (OFF, LP, BP, HP, NOTCH, ...), Cutoff (mod target), Resonance (0..15), Key Track, Env Amount (from the voice envelope, signed), Model (6581, 8580), Drive |
| PITCH / ARP (8) | Sweep (mod target), Sweep Time, Vib Depth (mod target), Vib Rate, Vib Delay, Arp 1, Arp 2, Arp Speed |

One slot is open (candidate: Raw Edges as in Chip). A parameter added later has nowhere to go without raising the ABI ceiling (Level C): list the cuts before building.
- **Views (draw API, at most 256 points a frame, record-then-replay):** Wave (two periods of the chosen waveform with its pulse width, the combined waves from the table), Envelope (the stepped attack, the piecewise-exponential decay and release, in the labelled times), Filter (the response curve of the mode at the cutoff and resonance, as the TB-303's page draws its filter curve).
- **Depends on:** nothing in the core. Interacts with: the host modulation matrix (targets above), the Instrument page's ENGINE selection (as Chip), MIDI Learn.

## UX sketch
Instrument page F1 ENGINE, pick SID. Page OSC: choose the waveform, move the pulse width and the PWM; turn on SYNC and sweep Mod Pitch with an LFO or envelope (the classic C64 sync sweep needs the mod target). Page ENV: the sixteen stepped times shown in seconds beside the value, so people who know SID values can type them. Page FILTER: Mode, Cutoff with the response curve on the right, Resonance, Model toggles 6581 / 8580 and the curve and the combined waves change. PITCH / ARP: the arpeggio (the C64 chord arpeggio sound) and sweep for drums (noise with a fast sweep down is the classic hit). Presets (a few: bass, lead, pulse pad, noise hat, sync lead, kick) in a data pack so the first sound is good.

## Risks / open questions
- **Parameter budget:** 31 of 32 used; any later wish (a filter envelope with its own ADSR, PWM shape, the ADSR bug, a second modulator) costs an ABI change or a cut.
- **CPU:** 4 to 5 % a voice is nearly twice Chip's; a song with many SID tracks hits the 80 % rule (`cpu-binding-constraint`). Measure before merge (`tmod-perf`).
- **Combined waveforms:** need tables; accuracy against a real chip is limited by the licence choice above; by-ear check only.
- **Filter accuracy against cost:** the 8580 filter is close to a linear two-integrator filter and cheap; the 6581 character (non-linear cutoff, distortion) is approximated by a curve and a soft clip, not modelled. Resonance mapping (4-bit value to Q) and the cutoff curve are to be measured or fitted by ear.
- **Hot slab:** whether a 6 KB hot part fits next to the other modules is unchecked (SRAM_L budget).
- **Sync and ring in float:** sub-sample hard-sync BLEP is more code than Chip has; test for aliasing against a naive reset (as Chip's test does for the pulse).
- **Per-track filter:** differs from the shared filter in the saturating case; document it.
- **Verify before coding:** register widths and noise taps (datasheet), the 16 rate periods (Programmer's Reference Guide), the PAL / NTSC clock to use.
- **Not proposed:** `.sid` playback (a 6502 core plus the chip emulation, then still without the original timing for non-PSID-friendly tunes); a NES engine.
- Evidence rule: everything above is `new Community OS behaviour` or `open research question`; there is no parity claim with any original firmware.
