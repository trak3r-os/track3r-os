# QA catalogue: Config

Screen: Config (`Config` button, pages F1 MIDI, F2 DISPLAY, F3 SD, F4 INFO, F5 USB, F6 PATTERN; F7 APPLY; F8 UPDATE on INFO only). Table format: `docs/specs/OS-FINALQA.md` section 1. This file holds the rows added by the items that touched Config since the rule of section 2; the rows of the other Config pages are drafted in the final batch (section 3).

Sim scenarios are `sim/scenarios/qa/qa_config.txt` (goldens `config/qa_cfg_NNN` in `sim/goldens.txt`) and, for the firmware update dialog, `qa_config_update.txt` and `qa_config_update_refused.txt` (OS-FWCONFIG, the section at the end); unit scenarios are `platform/mk66/tools/hil/qa_config.json`. A unit step compares the body of the screen with the simulator's snapshot (soft) and reads the USB state over the console. **The unit rows that need the host side** (a re-enumeration, a reboot) cannot be driven by `o3hil`: the second F7 re-enumerates the USB port, the CDC console goes with it and the runner holds one open port. They are the checklist rows AUD-12, AUD-13 and AUD-14 of `platform/mk66/README.md`, done by hand with `lsusb`, `dmesg`, `arecord -l`, `diag log`.

## USB page (OS-USBAUDIO)

USB AUDIO (Off: STANDARD, MIDI and serial only; On: the audio device too, the default) and USB RETURN are press to apply: the encoder and Delete only change a pending value, shown starred; F7 says what will happen and arms; the second F7 writes the settings. The message says the port reconnects only when the apply re-enumerates it: a USB AUDIO change always, a USB RETURN change only while AUDIO is presented. RETURN LEVEL is live.

## PATTERN page: recording microtiming and velocity (OS-RECMICRO)

REC MICRO (Off, On) and REC VELOCITY (Off, External) follow REC QUANTIZE; the page has eight rows. **New Community OS behaviour** (docs/specs/OS-RECMICRO.md): PAR-037 / PAR-064 give no rule beyond the release notes, so nothing here is a parity claim; the scaling `ustep * 100 / 47` of the microstep onto Micro-move's 0..100 is our own choice (what the official firmware writes is an open research question). With REC MICRO On a live-recorded note also writes its offset from the step to FX 2 as a Micro-move (only when more than 0, only when FX 2 is empty or already a Micro-move; an early note, rounded up to the next step, has none); with REC VELOCITY External the velocity of a MIDI keyboard note goes to the volume column (pads have none). Host tests: `rec_test.cpp` (the value for every microstep, the Playing / Nearest truth table, the FX 2 rule, the velocity mapping, the actions), `settings_format_test.cpp` (the files of 13..20 settings read both Off, the 214-byte default file, round trip, an older reader skips both), `config_screen_test.cpp`. The recorded notes in the grid are QA-PAT-059..061 (`pattern.md`).

## PATTERN page: the pads' row offset (OS-PADOFFSET)

PAD OFFSET, the eighth and last row of the PATTERN page, sets where each row of the NOTES pads starts on the row below it: 0..12, step 1, default 12. **New Community OS behaviour**: the official manual names a row offset among Config's pad options (`docs/ui/official-manual-map.md`) and nothing here claims its range. At 12 every row continues right after the row below it (the layout of every unit before the row); at N (0..11) a row starts on the Nth note of the row below it (the scale's notes when SCALE LOCK is on), so the rows overlap by 12 - N; 0 puts the same twelve notes on every row. The board takes 13 too (a fourth up: it lays out as 5), so the row stops at 12. It is a **device setting** (how the pads sit under the hand), the 23rd field of the settings file, appended with no version bump (`docs/formats/o3-settings.md`, "Field 22"): an older file reads 12, an older build skips the entry. Root, scale, octave and SCALE LOCK stay the held Note panel's, per project. Host tests: `settings_format_test.cpp` (the 214-byte file of the build before reads 12, the 222-byte default file, every value round trips, 13 and -1 refused, an older reader skips the entry), `config_screen_test.cpp` (the row, the range, Delete, the board laid out again at once, a loaded file), `pad_board_test.cpp` (every offset of the board against the reference vectors, unchanged).

## USB page: CARD AS DISK and READ ONLY (OS-USBDISK U2b)

The running mode (docs/specs/OS-USBDISK.md section 9): the card goes to the computer while the unit plays on. The Config > USB page ends with two rows that are not settings: CARD AS DISK (an action row: F7 twice shares the card, F7 twice again takes it back) and READ ONLY (a choice for the session, On at the start, not saved: the encoder moves it, Delete puts On back). The simulator has no USB: its `disk idle|working|out|audio` word stands for the platform, and the goldens show the page and the strips only. The unit cells drive the same states from the diag console: `disk share [ro]` (the console port re-enumerates: open it again), `disk` (the state), `disk eject`. **Everything here is more testing needed**: the running mode has not run on a unit.

## MIDI page: TRANSPORT IN and TRANSPORT OUT (E-CFG-03)

**New Community OS behaviour, Level C (a device setting and the MIDI render path).** Two rows after CLOCK MODE on the MIDI page (`F1`), captioned TRANSP IN and TRANSP OUT (a caption holds 12 characters), Off or On, **On** by default, which is what every unit did before them. TRANSPORT OUT Off: the unit sends no Start, Continue, Stop or Song Position Pointer; the clock still goes out (CLOCK MODE Master) or is relayed (Slave). TRANSPORT IN Off: Start, Continue, Stop and Song Position from the followed port are ignored; the clock is still followed, so the Play key starts on the master's next clock, and a Stop from the master does not stop the unit (only a master that goes quiet does). Both do nothing while CLOCK MODE is Off. A change takes effect at the next Play; a run keeps the setting it began with, so its Stop is always sent after its Start. Device settings 23 and 24 of `settings.o3st` (appended, no version bump: a file without them reads On / On; `docs/formats/o3-settings.md`). The page holds ten rows since OS-MIDICCMAP S1 added CC MAP (`ParamView::kConfigRows`; nine before it); the data pane has room for sixteen.

## INFO page: firmware update from the unit (OS-FWCONFIG)

**New Community OS behaviour, Level C (the update path); the branch `feat/OS-FWCONFIG` does not merge before the maintainer's hands session** (`docs/specs/OS-FWCONFIG.md`). `F8` (**UPDATE**) on the INFO page opens one modal dialog over `Firmware/*.ptf` of the card: the list, question 1 (F1 **YES**), the check with a bar, question 2 (F1 **INSTALL**, good for 30 s), then the hand-over (`UPDATING: DO NOT POWER OFF`). Each question is answered by `F1` alone; any other control, `F8` or the 30 s takes it back. A failure or a refusal that comes after the dialog opened shows on the dialog's own line; a refusal that stops it from opening shows on the strip. Nothing is written to the card before INSTALL, and the hand-over is the console's own (`fw update`: the same code, `mk66_update_client_test`).

The simulator has no flash and no card for this: `firmware on` (`sim/README.md`) puts the fake port of `platform/host/fake_firmware.h` behind the dialog with four scripted files, `TRACKER_1.PTF` (the reset target; a good image; its hand-over is not taken), `SLOW_CHECK.PTF` (a good image whose check takes 600 passes), `BAD_IMAGE.PTF` (the check fails at byte 1104) and `NEVER_ENDS.PTF` (a good image whose hand-over never ends). The sizes and the CRC in the pictures are the script's, not an image's. **Nothing in the simulator proves an image flashes**: that is the hands session. The unit cells below are its steps, never run by an agent (`install()` is not called on hardware by an engineer):

|---|---|---|
