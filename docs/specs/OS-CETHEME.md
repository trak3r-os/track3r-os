## 1. Goal

Let users of tracker-ce's web theme and font editor (F14) use what it exports on this OS: a theme JSON in `/Themes/` recolours our screens (its colour roles mapped onto our 17 tokens), a `.ptfont` in `/Fonts/` replaces our Data and Label faces. The files stay valid for tracker-ce on the same card. The built-in themes and faces always exist (ADR 0009); a missing, broken or unreadable file falls back to them with a notice. Everything runs in the main loop; nothing touches the audio path.

## 3. Design

### 3.1 Files and the list (main loop)

`/Themes/*.json` and `/Fonts/*.ptfont`, the same folders as tracker-ce (F1, F10: one card serves both). A list is a `DirScan` of the folder (`.json` / `.ptfont`, hidden and macOS files skipped), **sorted by name, case-insensitive** (tracker-ce lists in directory order: new Community OS behaviour, so a choice saved by index does not move when the card is defragmented), at most 32 themes and 30 fonts, names cut at 31 characters. A missing folder is an empty list; this OS does not create the folders. The lists are rebuilt at every card mount (boot, `CARD READY` after USB disk mode) and when the Config DISPLAY page opens.

### 3.2 The theme reader (pure, `ui`)

`ui::read_ce_theme(const char* text, size_t length, CeTheme& out)`: the subset of F3 with the same tolerance (unknown keys skipped at every level, a later duplicate wins, case-insensitive keys, `"#RRGGBB"` only, F4), plus bounds tracker-ce has implicitly: input at most 8,191 bytes (F2: a longer file is read to that length, as tracker-ce does), nesting at most 8 levels (deeper values skipped), keys and strings cut at 31 bytes. `"base"` is read first (F5). Output: `std::uint32_t rgb[kColorCount]` (0xRRGGBB), a `given` bit mask, the base `ThemeId`, counts of keys read and skipped, and an error (`Empty`, `NotAnObject`, `Truncated`: an unclosed object still yields the colours read before the cut, as tracker-ce's reader does). No allocation, no I/O, no recursion (an explicit depth counter).

**The mapping onto our tokens** (one table, `ui/src/ce_theme.cpp`; a section given as an array is read by position, F6):

**What does not map** (read and skipped, counted in `keys_skipped` only when unknown): `songTimer`, `labels` other than `inactive.text`, `bottomButtons`, `songPlayer`, `frames`, `lists`, `bars`, `popups`, `blankSpace`, `battery`, `waveform`, `shadows`, `moreButton`, `editBox`, `keyboard`, `performance`, `dialog`, `miniMenu`, `accents.orange|yellow|cyan|grey`, and in `patternTracker`: `trackName`, `inactiveInstrument`, `inactiveFx1`, `inactiveFx2`, `gridDivider`, `inactiveTrack`, `verticalDivider`, `greenMode`, `unfocusedTrack`, `activeTrack`, `trackEnd`. Our Song, Sample, Mixer and every other screen draw with the 17 tokens, so they follow the mapped colours. The derivations of F7 are not needed: none of the mapped keys is derived there. Faces and metrics are not in the file: they stay the base theme's (fonts are 3.6).

**The `"o3os"` object** (Q1 a): a root key `"o3os"` holding our tokens by name (`chrome`, `chromeText`, `chromeDim`, `pane`, `text`, `textDim`, `empty`, `instr`, `vol`, `fx`, `sel`, `selText`, `accent`, `accentText`, `play`, `playText`, `rec`) overrides the mapped values, whatever its position in the file. tracker-ce skips it (F3).

### 3.3 Making the theme (`ui/src/themes.cpp`, the one place colours are built, O2)

`make_sd_theme(const CeTheme&, Theme& out, SdThemeReport&)`: start from the built-in that `base` names (Q2 a: Original -> Amiga, Monochrome -> White, Anniversary -> Black, else Amiga), overwrite every `given` token, keep the base's faces and metrics, name `"sd"`. Then the **contrast repair** (Q3 b): for each pair of `kContrastPairs` in table order that fails, move the pair's ink (`fg`) by the smallest blend `t` in steps of 1/16 toward black or white (the end that gives the higher ratio against `bg`) until it passes; a Dim pair that is too strong moves toward `bg`. Two passes over the table, then a final check of every pair: still failing, the theme is refused (`LowContrast`). The report counts the tokens moved. Luminance and ratio in float (WCAG 2.x, `pow(x, 2.4)` as `exp2_fast(2.4 log2_fast(x))`, O8); the host test holds it to `tests/theme_test.cpp`'s double reference within 0.01.

### 3.4 On the device (main loop)

- **ThemeId::Sd** (3): `ui::theme(ThemeId::Sd)` returns the one loaded SD theme (a `Theme` in SRAM, about 72 bytes), or Amiga while none is loaded. `kThemeCount` stays 3 (the built-ins; the gallery and the contrast test loop over them).
- **Loading** is a job (`core::Job`): open, read at most 8,191 bytes into an 8 KiB `O3OS_SDRAM_NOINIT` buffer, `read_ce_theme`, `make_sd_theme`, then the new theme is published between two frames (the next frame draws it). About 5 to 20 ms of card time and under 1 ms of parsing for a 4 KB file [est]. A failure (no card, no file, read error, `NotAnObject`, `LowContrast`) leaves the current theme, selects Amiga when the failed one was being applied at boot, and posts a notice: `THEME: <name> NOT READ` or `THEME: <name> LOW CONTRAST`. Requests are coalesced: only the latest choice is loaded (a MIDI controller bound to THEME cannot queue loads).
- **Choosing** (Q4 a): THEME's values become 0..34: 0-2 the built-ins, 3 + n the n-th file of the sorted list. Shift + Master cycles Amiga, Black, White, then each SD theme, then Amiga. The Config DISPLAY row shows the name (the row's first 12 characters; the info line shows the whole name and, after a repair, `3 COLOURS ADJUSTED`). At boot the settings file is read from the card and the list is built, then the saved index is loaded; until it is, the screen is Amiga (the boot screen has its own fixed look anyway). A value past the list's end is Amiga (F9's rule).
- **The card leaves**: a loaded theme stays (it is in RAM); the list is rebuilt at the next mount and the index is re-resolved only at the next boot or choice.
- **Not touched**: the boot screen (`boot_theme()`), module views (their 16 colour ids map to the same tokens, `app/src/module_ui.cpp:27`).

### 3.5 Settings (T3, Level C)

Device setting id 12 THEME: range 0..2 -> 0..34, same id, same storage (U8), same default (Amiga). Values 0..2 keep their meaning; 3..34 were invalid before. A file with THEME 0..2 reads the same; a file with 3..34 read by an older build has the value refused and the entry skipped and counted (the documented rule: a value out of range is refused by the block and skipped by the reader, `o3-settings.md:19`, `:81`), so the setting is Amiga there and a save drops the choice. No chunk, no version bump, no size change; the default file stays 246 bytes. The descriptor's names come from a RAM table of 35 pointers (the three built-in names, then the list's names, `"-"` past its end), filled by the list (the descriptor itself stays constexpr: it holds the table's address). Learnable as before.

### 3.6 Fonts (Q5 a; slices F1 to F4)

- **Which slot plays which role**: Data (10x20) <- slot 0 (size 14 regular); Label (8x16) <- slot 4 (size 12 regular). Display (16x32) and Micro (6x12) keep the built-in faces (no slot is near 32 or 12 rows). Slots 1 to 3 are read and checked, not used.
- **Reading** (pure, F1): the header, entries and metric blocks of F11 and F12, with the checks tracker-ce does not make: offsets and sizes inside the file, stride x height x count + 148 equal to or below the entry's size, stride >= ceil(width / 2), the glyph range inside 32..126, the total inside our region. Per glyph it finds the ink box (rows and columns with a non-zero nibble) and per face the baseline (the lowest ink row of `H`, else of the digits).
- **Fit rule** (per role): with the baselines aligned (the built-in face's ascent, O5), every printable glyph's ink lies inside the role's cell widened by the row pitch's margin (Data: 2 rows above and below, inside the 24-pixel pitch), and no glyph's ink is wider than the cell. A face that fails keeps the built-in face for that role, and the info line names it (`FONT: DATA TOO LARGE`).
- **Drawing**: the face is drawn as L4 (anti-aliased) on the same bitmap handle (2 for Data, 3 for Label) with its own stride and box; each glyph at `x + x_off[c]` (its ink centred in our monospace cell; a proportional font therefore looks evenly spaced) and `y + y_off` (the baseline). `FontFace` gains `format`, `x_off` (a pointer to 96 signed bytes, in SDRAM) and `y_off`; `ui::font_face(Font)` returns the override while one is set. The display-list words of a frame do not change (the same `VERTEX2II` per glyph; `BITMAP_LAYOUT` already emitted per handle), so the budget tests hold unchanged.
- **The grid's tiles** (F4): the hex-pair, note and zoomed-grid tile sets made from the Data and Label faces (`assets.h:11-20`) are composed at run time from the loaded faces as L4, in the main loop, one 4 KiB chunk at a time, and bound with the L4 layout. The Micro face's tiles stay.
- **RAM_G** (O6): a new region at the front of the spare region: faces 2 x 24 KiB (tracker-ce's per-entry limit, rounded to pages) and tiles about 132 KiB (hex pairs 256 x 200 B, note tiles 133 x 300 B, Label hex pairs 128 x 128 B, Label note tiles 128 x 192 B, at L4), 180 KiB in all, 4 KiB aligned; the screenshot region shrinks from about 476 to about 296 KiB (the shot takes more bands; `mk66_shot_stream_test` follows `kRamGShotBytes`).
- **Loading and switching**: a job reads one entry at a time into a 22,528-byte SDRAM buffer, checks it, uploads it in chunks of at most 4 KiB (ADR 0010), composes and uploads the tiles, and only then switches the override (the region is never on screen while it is written; switching from one custom font to another draws the built-in faces for the frames in between). About 180 KiB at 20 MHz SPI is about 75 ms of transfer over some 45 main-loop passes [est].
- **FONT** (F3, Level C): a device setting appended by the documented rule: 0 Built-in, 1..30 the n-th file of the sorted `/Fonts` list; default 0; on the Config DISPLAY page after THEME (the page has seven rows). Its id is the next free device id when it merges: the block is full (O7), so whichever of this slice and OS-MTC A3 merges first raises `Settings::kMaxFields` / `kValueBytes` 26 -> 32 (and `kModelArenaBytes`, the `mem_map.h` mirror) as OS-MTC 3.7 describes, and ids are never renumbered after a merge. Default file +8 bytes.

### 3.7 Simulator

`o3sim --theme-file <path.json>` and `--font-file <path.ptfont>` (ADR 0010: the simulator stands in for the SD slot), the scenario commands `theme_file <path>` and `font_file <path>`, and the gallery rendering one CE fixture theme (our own fixture files under `sim/fixtures/themes/`, written for the tests: no file of the editor or of tracker-ce is copied).

### 3.8 Budgets [est]

Flash: T1 +2.2 KiB (reader 1.2, mapping and token names 0.5, repair 0.5), T2 +1.2 KiB, T3 +0.4 KiB, F1 +1.0 KiB, F2 +0.8 KiB, F3 +1.0 KiB, F4 +1.2 KiB: about **+7.8 KiB** in all (+3.8 KiB without fonts). SRAM: +0.1 KiB (the SD theme, the override pointers). SDRAM static (no-init): 8 KiB (theme text) + 22 KiB (one font entry) + 4 KiB (tile chunk) + 2 KiB (two name lists) + 0.2 KiB (offsets): about 36 KiB. RAM_G: 180 KiB from the spare region (fonts only). Render CPU: 0 (main loop only). Main loop: a theme load under 25 ms of card and parse time; a font load about 45 passes of at most 4 KiB.

## 5. Assumptions (decided here; each local, testable and reversible)

- A-1 Same folders as tracker-ce; lists sorted by name, case-insensitive; this OS does not create the folders.
- A-2 Reader bounds: 8,191 bytes (F2's), depth 8, keys and strings 31 bytes; a truncated file keeps what was read (F3's tolerance).
- A-3 The mapping of 3.2 (Vol <- `fx2`, Fx <- `fx1`, Sel <- `playhead`, SelText <- `accents.white`, PlayText <- root `background`); faces and metrics are never taken from a theme file.
- A-4 The repair moves only the ink of a failing pair, in 1/16 steps toward black or white, two passes, then refuses (Q3 b).
- A-5 One SD theme in RAM at a time (`ThemeId::Sd`); the built-ins stay `kThemeCount` 3.
- A-6 Shift + Master cycles the built-ins, then the SD themes; a bound controller's loads are coalesced.
- A-7 Fonts: slot 0 -> Data, slot 4 -> Label; Display and Micro keep the built-ins; the fit rule of 3.6; glyphs centred in our monospace cell.
- A-8 Custom faces and tiles are L4 in a 180 KiB RAM_G region at the spare region's front; the screenshot takes more bands.
- A-9 FONT takes the next free device id at its merge; the first slice past 26 settings does the raise (shared with OS-MTC A3).
- A-10 A loaded theme and font stay when the card leaves; the lists are rebuilt at every mount; a saved index is re-resolved at boot or on a choice.
- A-11 Test fixtures (themes and fonts) are written by us (`sim/fixtures/themes/`, `tools/ptfont_make.py`); no file of the editor or tracker-ce is copied.

## 6. Risks

- R1 **The editor's real output** (F13, F14): the cell sizes of its fonts and whether it keeps `"o3os"`; the unit checks of T2 and F3 use an editor-made theme and font. If slot 0 does not fit 10x20, F3 shows the notice and the Data face stays: the fit rule's margin is then the knob.
- R2 **Contrast repair changes a designer's colour**: the info line says so; the `"o3os"` object lets a user give passing tokens directly.
- R3 **Index drift** (Q4 a): adding a file before the chosen one moves the choice at the next boot; documented in the manual; Q4 b is the fallback.
- R4 **The settings block raise** shared with OS-MTC (A-9): the static asserts, the older files as literals, `qemu` before merge.
- R5 **RAM_G**: the shot region shrinks by 180 KiB; a further screen that needs RAM_G competes with it (O6).
- R6 **Proportional fonts** look evenly spaced, not as in the editor's preview (our layout is a monospace grid); the manual says so.
- R7 **Flash**: +7.8 KiB [est] with flash at 94-97 %: F4 (+1.2 KiB) and the font slices can be dropped by Q5 if the image is short.
