# OS-UPDPAD: pad an unpadded image on install, after asking

Level C (the firmware update path). New Community OS behaviour (maintainer decision, 2026-11-01). No persistent format changes: the files the OS writes are Intel HEX images of the same format as `fw put` writes, no on-disk layout, bootloader, linker script or image layout is touched, and nothing is on the audio path. Follows OS-GATE-BOOTCRASH, whose rule it keeps: nothing that is not padded to a 4 KiB sector is ever armed.

## Intent

Since OS-GATE-BOOTCRASH every door of the update path refuses an image whose end is not a multiple of 4096 (`Fault::NotPadded`, the LAST verdict of `HexValidator`). That is right for a build that can be fixed, but it also blocks going back from v1.1.0 to v1.0.1 or v1.0.0 (both published unpadded) and installing anyone else's unpadded build from the Update screen. The SD bootloader leaves a short final sector unwritten (`docs/hw/tracker-hardware-notes.md` section 3); zero bytes up to the boundary are what our own `.flashpad` uses (verified on the unit with `v1.0.1-cosm.3`).

This slice lets the Update screen (and `fw arm` with an explicit option) install such an image after asking: track3r-os writes a padded COPY on the card, validates the copy from the start, and arms the copy through the normal path. The original is never changed.

## Rules

- The offer is made only when the validator's ONLY fault is `NotPadded`. `NotPadded` is the last verdict of `HexValidator::finish()`, so every earlier check has passed: record syntax and checksums, address range, contiguity, SP, reset vector, every vector, and the flash configuration field (a wrong value there can lock the MCU). Any other fault refuses exactly as before, with no offer. The re-check inside `ui_install` / `fw update` has no offer either: it still refuses an unpadded file.
- No offer for an image that reaches the last flash sector: the device validator also refuses an end above `0xFF000` (`Fault::LastSector`, "image reaches last flash sector", OS-BUG-LASTSECTOR), tested before `NotPadded`. An unpadded image ending in `0xFF001..0xFFFFF` therefore fails with `LastSector` (Update screen: Failed; `fw arm ... pad`: refused), never `NeedsPad`: its padded copy would end at `0x100000`.
- Screen: the check ends in a new state (`CheckStatus::State::NeedsPad`, the file's length in `image`) and the dialog asks question "NOT PADDED. TRACK3R-OS WILL PAD A COPY OF IT?", answered by F1 alone like the other questions (any other key, F8, the timeout or the card going to a computer takes it back; nothing was written). F1 starts the pad job (`FirmwareSink::pad()`); its bar and "do not remove the card" line follow; when the copy has passed it, the existing INSTALL question is asked for the copy (its name on the second line), good for 30 s, and INSTALL is the unchanged hand-over.
- The pad job writes the copy into `Firmware/_o3up.tmp` (the upload's temporary file: never a `.ptf`), reading the original again: its bytes up to the last record start (the EOF record), then padding records, then the original's tail (the EOF record and whatever line ends follow it). Padding is zero bytes from the image's end to the next 4096 boundary as Intel HEX text: one extended linear address record (`:02000004<upper 16 bits>` + checksum) followed by data records of 16 bytes (the last one shorter), upper-case hex, LF line ends, offsets from the address's low 16 bits. The extended record is always written: the original's active base (a type 02 base, or none) is then irrelevant. The pad never crosses a 64 KiB line (4096 divides 65536). Added text is at most 16 + 255 x 44 + 44 bytes.
- The copy is then read back from the start through a fresh validator (the upload's read-back: length and CRC against what was written, every check, `sector_end` included), renamed to its name, and read once more by the normal arming check (`begin_check`: the same code `fw arm` and the screen run). A copy that does not pass is not left behind as a `.ptf`: before the rename it stays in the temporary file that is deleted; after it, a failed arming check removes the copy. The removal goes through the store's guard, which can refuse it (`LastPtf` if the original vanished meanwhile, an I/O error): the failure is then reported as usual, nothing is armed, and the log says `fw pad: failed copy not removed`; the copy is a valid-looking `.ptf` that failed only its second read, so it is a rare, logged case, not a silent one.
- The original file is read only. Its size and bytes may change on the card meanwhile, so the job holds it to what the check saw: the size (checked when it is opened again) and its CRC-32. The check's CRC of the original (`v_.crc()`, for the console the CRC the user announced, already compared by the check) is kept in `offer_pad`, and `pad_slice` CRCs the original's bytes as it copies them (head and tail). If they differ at the end of the tail (`Fault::Crc`, `crc mismatch`), nothing is renamed, the temporary copy is deleted and nothing is armed. The copy is also validated on its own afterwards, so a changed original can only produce a refused copy.
- Main loop only, sliced: one pass of the main loop reads at most 2 KiB and writes at most 2 KiB (`kTransferBuffer`). No SD I/O in a key handler (the key only asks the port; the work is `ui_slice()` / the console stream). No heap: the buffer and the validator are the service's own.
- The hand-over, `_fwinfo`, the reset-button path and the official update menu are untouched.

## Decisions

| # | Question | Default | Why |
|---|---|---|---|
| 1 | Name of the copy | `pad-` + the original's stem cut to 22 characters (trailing dots dropped) + `.ptf`: at most 30 characters, so `update_name_ok` holds. Never starts with `Polyend` (the original may), so the copy is removable by the writer's own guard. | Deterministic, recognisable, inside the OBSERVED name limit. |
| 2 | A copy of the same name that is already there | Refused, never replaced or removed: `begin_upload` answers `Exists` before anything is touched and the job fails with `Fault::CopyExists` (text `copy exists, pick it from list`; the dialog reads `PADDING FAILED: COPY EXISTS, PICK IT FROM LIST`, 46 characters, inside the strip's 48 and the dialog line's 86). Nothing is written, the existing file is as it was; the user picks it from the list (a valid earlier copy is installed like any file; any other file of that name stays theirs). The same refusal covers an original whose own name equals the copy's (FAT is case-insensitive; a periodic `pad-pad-...` name of 30 characters), so the original can never be touched. Two originals that share a 22-character stem share a copy name: the second pad is refused until the first copy is deleted. | A pad must not delete a file of the user's, and must not leave nothing when the card is full: an old copy is only ever removed by the user. |
| 3 | Console syntax | `fw arm <name> <crc32hex> pad` (`pad` is the optional 4th argument). Without it `fw arm` refuses as before. `<crc32hex>` is the ORIGINAL's. With it: the same rule (only `NotPadded` is padded; any other fault refuses), then `padded <copy> <bytes> <crc32> image <length>` and `armed <token>` (for the copy: `fw update <token>` installs the copy). An image that is already padded is armed as it is. Usage text and `platform/mk66/README.md` say so. | The explicit word is the confirmation; no new command. |
| 4 | `o3console.py` | `--put FILE --pad`: pads on the host with the same algorithm (check_image.py `sector_end` verifies the result) before the file is sent; the unit's `ok` line then carries the padded file's CRC. `--update NAME --crc C --pad` sends `fw arm NAME C pad`. | `fw put` still refuses an unpadded stream, so a host pad is the only way to put one. |
| 5 | Card full | The job's first slice reserves the copy's room (`begin_upload`: `NoSpace`); the dialog shows `PADDING FAILED: NO SPACE`, nothing was written (the temporary file is dropped), nothing is armed, nothing was removed. | The reservation is up front, so a full card says so at once. |
| 6 | Write-protected card | Cannot occur after a check (the check needs a writable path). If the protect switch moves meanwhile, the first slice answers `PADDING FAILED: WRITE PROTECTED`. | |
| 7 | Interrupted copy | F8, a key that takes the question back, the card removed or put in, the screen leaving, the console terminal closing: the job stops, the temporary file is deleted, nothing is armed. A power loss leaves `_o3up.tmp` (not a `.ptf`); the next upload or pad replaces it. A cancel after the rename leaves the validated copy on the card. | |
| 8 | Timeout | The offer (`NeedsPad`) is good for `kArmLifetimeMs` (30 s) like a check, and lapses by the clock, on a hand-over to a computer, and on a console command. The copy itself has no deadline (every slice is bounded); once it has passed, INSTALL is good for 30 s as always. | One lifetime for every question. |
| 9 | Directory order | A new copy may take a free directory slot before the first `.ptf` and so become the reset button's target. It is a valid padded image of the same content, so this is harmless; it is the same behaviour as any `fw put`. | Recorded, not changed. |
| 10 | Where the logic lives | The pad is `HexPadWriter` (pure, `update/hex_pad.h`); the job is `FwService` (client and console share it); the port gets `State::NeedsPad`, `CheckStatus::copy` and `pad()`. The fake port (`platform/host/fake_firmware.h`) can script them. | One implementation for the screen and the console. |

## Cost

About 4 passes over the file on top of the check (read the original, write the copy, read the copy back, arm: read again): for a 2.6 MB HEX that is several times the time of the check, to be measured on the unit. Flash: the target was under 2 KiB of `.text`; measured over `e938d9ad` (mk66 image): +2688 B `.text` (952936 to 955624; the pad job, the padder, the console `pad` option, the client states and the screen's two states; the review folds removed the replace-an-old-copy code, kept a CRC of the original while it is copied and shortened the log lines), FLASH 960 to 964 KB (the table's rounding), SRAM_U unchanged (137296 B), SDRAM_STATIC +64 B (160320 to 160384). The target was missed; what remains is the job's four steps and their error paths, which no longer have anything cheap to trim. SRAM: a few dozen bytes of service state.

## Tests

- `mk66_update_hex_test`: the padder's exact HEX output (the extended record, full records, the short last record, checksums) for lengths +1, -1 and exactly on a boundary (no pad); the padded text validates and its length is the boundary; the added size equals `text_bytes`.
- `mk66_update_client_test`: a NotPadded-only check ends in `NeedsPad` and writes nothing; every other fault (a wrong flash configuration byte above all, SP, reset, vector, record checksum) gets no offer; nothing is armed on cancel, on a lapse, on a hand-over to a computer, on a console command; the copy is validated and armed, the original is byte for byte unchanged, a second pad replaces the first copy; a full card, a failing write, a corrupt read-back and a name equal to the original arm nothing and leave no `.ptf` behind; a second pad is refused (`CopyExists`) with the existing copy, or a file of the user's with that name, untouched and nothing removed; an original changed under the job with its size kept is refused by its CRC (`Crc`); a failed copy whose removal the store refuses is reported, logged and not armed; a console command during the offer kills it; install of the copy hands over the copy; install of the unpadded original is still refused.
- `mk66_update_transfer_test`: `fw arm ... pad` (padded, armed, the original unchanged, the usage line); without `pad` it still refuses; any other fault with `pad` still refuses; a CRC that does not match refuses before anything is written.
- `firmware_update_test` / `fake_firmware_test`: the dialog's walk (question, bar, INSTALL for the copy), the texts fit the line, cancel and every other way out call `cancel()` and arm nothing.
- `o3console.py --self-test`: the host pad agrees with `check_image.py`.
