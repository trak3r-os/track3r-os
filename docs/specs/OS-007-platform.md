# OS-007 — Platform layer: QEMU target tests, MK66 skeleton image

Status: 007a and 007b specified 2026-10-11 · Decisions in force:
- ADR 0011: declared alignment, diagnostics, crash record, bootloader facts, driver licences.
- ADR 0013: `mem_map.h`, NVIC priority table, DWT per stage.
- ADR 0002: containment, fault handlers.
- the flashing-safety rules and the firmware gate check.

**Hard rule:** these slices produce images and run QEMU only. Nothing is flashed, copied to removable media or handed over as a candidate without the firmware gate check and the maintainer's decision.

## 007a — Target test layer on QEMU (V3)
- **Platform `platform/qemu`** for `mps2-an386` (Cortex-M4F). It provides:
  - startup: vector table and reset handler that copies `.data`, zeroes `.bss` and enables the FPU;
  - a linker script;
  - a minimal `hal` for Clock (SysTick) and a console (semihosting or the CMSDK UART);
  - exit codes through semihosting `SYS_EXIT_EXTENDED`.
- **Test runner.** Cross-build the pure unit-test suites for the Cortex-M4F with the same flags as the MK66 build (`-mcpu=cortex-m4 -mfpu=fpv4-sp-d16 -mfloat-abi=hard`): `core`, `eve` encoders, and later `usb`, `ui::plot` kernels and `model`/`formats`, each as it merges.
  - Prefer doctest if it fits in the AN386 memory with newlib-nano; otherwise use a small first-party runner with the same `TEST_CASE`/`CHECK` macros for the target build only.
  - A suite that does not fit is split, never trimmed silently.
- **CMake.** `-DO3OS_PLATFORM=qemu` builds the target suites. Each suite is registered as a ctest that runs `qemu-system-arm -machine mps2-an386 -nographic -semihosting-config enable=on,target=native -kernel <elf>` with a timeout. A host build skips them, so the existing host ctest is unchanged.
- **Done when:**
  - `cmake -S . -B build-os-qemu -DCMAKE_TOOLCHAIN_FILE=$PWD/cmake/mk66-toolchain.cmake -DO3OS_PLATFORM=qemu && cmake --build build-os-qemu && ctest --test-dir build-os-qemu` passes the `core` and `eve` suites under QEMU, with a deliberately failing probe proving that a failure propagates as a non-zero exit. The probe is registered as an inverted ctest (`qemu_probe`) that passes only on the expected failure, so it runs in the default run (accepted at review, 2026-10-11).
  - Host ctest and the MK66 build are unchanged and green, with 0 warnings.
  - `docs/architecture/os-tree.md` documents how a new library adds its target suite (one CMake line).

## 007b — MK66 skeleton image
- **`platform/mk66`:**
  - **Memory map.** `mem_map.h` holds the ADR 0013 D7 regions as `constexpr` with `static_assert` sums. The linker script (`mk66.ld`) is generated from it or checked against it by a test: flash, SRAM_L, SRAM_U and SDRAM regions; sections for `.ramfunc_l` (hot code in SRAM_L) and SDRAM `.noinit`.
  - **Startup:**
    - Vector table with every handler named.
 - Reset sequence: watchdog unlock and disable, then a deliberate re-enable point for later; clocks to 180 MHz HSRUN (PLL setup from the K66 reference manual, written fresh); FPU enable; `.data`/`.bss`/`.ramfunc_l` init.
    - SDRAM controller init with the board timings established from the SDRAM data sheet and the K66 reference manual (the values are in `sdramc_config.h`).
  - **Flash configuration field (0x400–0x40F):** bytes must be exactly `ff ff ff ff ff ff ff ff ff ff ff ff de f9 ff ff`, the value the gate requires. A wrong value can permanently lock the MCU. Add a `static_assert` or a post-link check, plus a ctest that reads the HEX and fails on any difference.
  - **NVIC:** `hal::irq` priority table from ADR 0013 D1 in one header, applied at boot.
  - **Timing:** SysTick at 1 kHz backing `hal::Clock`; DWT CYCCNT enabled and `hal::cycles()`.
  - **Fault handling:** HardFault, MemManage, BusFault and UsageFault enabled. They write a crash record (CFSR, HFSR, BFAR, MMFAR, PC, LR, xPSR and a module id slot) into the VBAT register file or a `.noinit` SRAM block that survives reset, then reset. Boot reads the record and exposes it to a future `diag crash`.
  - **Firmware info:** an `_fwinfo`-compatible version block if ADR 0011 or `docs/hw/tracker-hardware-notes.md` define one. Otherwise record it as an open item.
  - **`main`:** brings up the above and idles in WFI with a heartbeat counter. No display, audio or SD yet; those are later 007 slices: Riedel EVE driver adaptation, `diag` CDC, SD.
- **Build:** `-DO3OS_PLATFORM=mk66` additionally links `o3os.elf` and produces `.hex`/`.bin` and a size report (flash, SRAM_L, SRAM_U, SDRAM `.noinit`).
- **Static checks:** a ctest with stdlib-only Python checks:
  - the HEX parses;
  - every address is ≤ 0x000FFFFF;
  - the initial SP lies inside SRAM;
  - the reset vector is Thumb and inside the image;
  - the flash config bytes match exactly.

  The engineer also runs the static checks of the firmware gate check where they apply to an `os/` image, and reports the result. No candidate is handed over.
- **QEMU smoke:** the vector table and C++ init path are exercised on `mps2-an386` through the 007a layer, as far as they are not MK66-specific, for example `.data`/`.bss` init and the fault-record encoder as a pure function.
- **Done when:**
  - The image builds with 0 warnings.
  - The static checks and the flash-config ctest pass.
  - Sizes are reported.
  - Host and QEMU ctest are green.
  - The reviewer approves, with a dedicated review angle on clock, watchdog, SDRAM and flash-config safety.
  - A hw-session checklist item lists what the first boot must observe: heartbeat via debug pin or LED, crash-record round trip, SDRAM pattern test.

## 007c — FT812 display on the MK66 (boot to the pattern view)
Builds on OS-007b. This is the first visible milestone: the image boots, initialises the FT812 and shows the OS-002b pattern view with demo data, rendered through the same `eve` display lists the simulator checks.
- **Driver sources.**
  - Adapt Rudolph Riedel's EmbeddedVideoEngine (FT800-FT813, MIT, radar card `eve-driver-libraries`): only what we need (register and command definitions, the init sequence, host commands, the coprocessor FIFO helpers). Vendor it under `third_party/eve-riedel/` with its licence and an `THIRD_PARTY.md` entry, pinned to a tagged release with its SHA-256, and wrap it behind our HAL.
  - The FTDI "FT81x simple library for PIC MCU" (FTDI-only-use clause) and Bridgetek EVE-MCU (proprietary headers) are references for board facts only (ADR 0011 amendment 1). Copy no code.
- **SPI.**
 - DSPI master on the board's FT812 bus: pins and chip select from and, cited.
  - Clock ≤ 20 MHz for data. Init runs at ≤ 11 MHz until the FT812 clock is up, as the datasheet requires.
  - eDMA for display-list and RAM_G uploads, with buffers declared-aligned in SRAM_U, and the channel taken from the ADR 0013 ownership table.
  - The SPI interrupt priority comes from the ADR 0013 D1 table.
- **Init.**
  - The FT812 warm-reset-safe sequence (ADR 0011 lesson 3): PD# low pulse, then the host commands (CLKEXT if the board uses an external crystal; ACTIVE), then wait for `REG_ID` 0x7C and `REG_CPURESET`.
  - Display timing registers for the 800×480 panel from the panel and FT81x documentation (OS-HW1 confirmed them on the unit).
 - `REG_ROTATE` from a HAL orientation setting, defaulting to 1 (180°; upright on the maintainer's unit in OS-HW1, ADR 0011).
  - Backlight PWM ramp-up only after the first frame is ready, so there is no garbage flash.
- **`hal::Display` implementation:**
  - `begin_frame`/`commit_frame` write the DL words into RAM_DL through DMA. Choose the double-buffering scheme (`REG_DLSWAP` frame swap, or the coprocessor `CMD_APPEND`) with its word budget, and document it.
  - `upload(addr, bytes, count)` honours the 4 KB cap and the result codes (OS-003a).
  - The UI asset uploads (fonts, tiles, icons, from OS-003b) go to their RAM_G regions at boot, through the same path as the simulator.
- **Boot app.**
  - `main` runs the OS app loop with the pattern view, demo data, the default theme and a fixed frame tick from SysTick.
  - There is no input yet (007d); an `O3OS_DEMO_CYCLE` build option cycles the cursor and the three themes every few seconds for the hw-session.
- **Tests:**
  - host unit tests for the pure parts: the command-FIFO wrapper against a fake SPI, init sequence ordering against a recorded transcript, timing register values;
  - a QEMU suite for the same pure parts;
  - image static checks as in 007b, contiguous and reproducible.
- **Done when:**
  - ctest passes on host, QEMU and MK66 with 0 warnings.
  - Image sizes are reported: flash grows with the fonts, ui, app and model libraries now linked.
  - The reviewer approves, with a hardware-safety angle on SPI clock limits, PD# and power sequencing, and backlight.
  - The hw checklist gains: display shows the pattern view, orientation, warm reset after the bootloader, SPI clock margin, frame rate, `VERTEX_TRANSLATE_X` on VERTEX2II (OS-003b), and the CMD_SNAPSHOT2 golden calibration.

## 007d — Input on the MK66: buttons, pads, encoder, pad LEDs
Builds on OS-007c. The device becomes interactive: the pattern, Song, Navigator and Learn screens respond to the real controls through the OS-002a/b pipeline (HAL event → gesture → binding → action).
- **Board facts** (the Tracker pin map, the key matrix, the encoder and the I²C bus) are established from the K66 reference manual and on the board, written fresh; no original code is copied:
  
  Establish which buses carry what (GPIO matrix, I²C expanders or a pad controller), the pad count and layout (48 = 12×4), whether the pads report velocity or pressure, and the LED type (RGB, PWM driver).
- **`hal::Input` implementation** (`platform/mk66/input/**`):
  - scanning at a fixed rate from a PIT or SysTick slot, using a timer not reserved by ADR 0013 (PIT0 is MIDI out);
  - debounce;
  - a quadrature encoder decoder with detent handling;
  - timestamped `InputEvent`s into the core SPSC ring, never blocking.
  
  Button names and ids match `docs/design/product-ux.md` §3 and the OS-002a button enum. There is no encoder push (maintainer).
- **`hal::Leds` contract + MK66 implementation** for pad backlight and button LEDs, if the board has them:
  - a frame-based API where the app writes a colour or level per LED and the driver flushes changed LEDs within a bounded time;
  - a theme-aware default palette for pads (instrument colours) drawn from theme tokens, not literals.
- **Pure parts with host and QEMU tests:** the debounce state machine (bounce patterns), the quadrature decoder (all transitions, illegal ones, fast spin), the matrix or expander decode, LED frame diffing, event timestamp monotonicity, and a ring-full policy (drop newest and count).
- **Boot app:** input events drive the app. The `O3OS_DEMO_CYCLE` variant stays as it is. A new hidden diagnostic screen ("INPUT TEST", reached by a boot chord defined in the spec) shows every button, pad and the encoder live; it is useful for the hw-session.
- **Done when:**
  - ctest passes on host, QEMU and MK66 with 0 warnings; the images pass the static checks and are reproducible.
  - The reviewer approves, with a hardware-safety angle: pin modes (no output fighting an input), I²C bus recovery and timeouts, LED current limits, and IRQ priorities and timer ownership per ADR 0013.
  - The hw checklist gains: every control registers once per press (no bounce), encoder direction and detent count, pad mapping order, LED colours and brightness, and latency from press to screen.

## 007e — Read-only SD card storage, and a project loaded from it (as built)
Builds on the OS-005c merge. **The slice's hard requirement: the firmware cannot write to the card.** The test card is the maintainer's, with their projects. Nothing here has run on a unit; the register-level SDHC code is the one part QEMU and the host cannot run, so the hardware checklist (`platform/mk66/README.md`, "Hardware-session checklist: the SD card", rows SD-1 to SD-12) is the next session's.

- **`hal/storage.h`** (`hal/include/o3os/hal/storage.h`): the read side of the contract and nothing else: `mount`, `mounted`, `card_present`, `volume`, `exists`, `open` (for read), `read`, `seek`, `size`, `close`, `opendir`, `readdir` (name, size, is_dir), `closedir`; typed `Status` results; handles are slots of a fixed pool (2 files, 2 directories) so nothing allocates; `valid_path()` shared by every implementation (UTF-8, `/`, no `.` or `..`, none of `\ : * ? " < > |`). It declares **no write function**, and says a write side is a later item with its own header.
- **FatFs R0.15a** vendored under `third_party/fatfs/` (ChaN, BSD-style licence, one condition; the archive's SHA-256, the file hashes and the licence are in `THIRD_PARTY.md`). Read-only (`FF_FS_READONLY 1`), long names with the **static** buffer (no heap), UTF-8, CP437, exFAT on (+1,480 B code, +608 B `.bss`, measured), one volume, no re-entrancy. **R0.15b is not used**: R0.16's history lists "f_readdir cannot detect end of directory and leads into an infinite loop (appeared at R0.15b)", which is the call the loader and `ls` depend on; R0.15a is the last of the R0.15 line without it, R0.16 is the upgrade path. The `o3os_fatfs` target is built with `-w` (third-party code only, as stb_image_write is; documented in `THIRD_PARTY.md` and the target's CMake); the project now enables C (`project(... LANGUAGES C CXX)`) and `-fno-rtti` / `-fno-threadsafe-statics` became C++-only.
- **The MK66 SDHC driver** (`platform/mk66/storage/`): **polled**, no ADMA2, no interrupt, no eDMA channel (the reasons are in `sdhc_bus.h` and the README: the main loop waits for the data anyway, a block is 23 us on the wire and 7 us to read out, DMA would add a descriptor table, an alignment rule on FatFs's buffers, error recovery, a SYSMPU grant and an interrupt for no wall-clock gain; `resources.h` records that the SDHC claims nothing and its line stays in the Completion row, disabled). 4-bit bus, CMD0, 8, 55 + 41, 2, 3, 9, 7, 55 + 6, high speed by CMD6 (50 MHz asked, 45 MHz made, `-DO3OS_SD_HIGH_SPEED=OFF` for a session that sees errors), reads by CMD17 and CMD18 with the controller's auto-stop, chunked at 32 blocks; SDSC (byte addressed) and version 1 cards too. Pins, clock source and dividers are our driver's own values (PTE0-5 ALT4, card detect PTD0, 180 MHz core clock source, 400 kHz identification), recorded in `sdhc_facts.h`; no line is copied or translated (`THIRD_PARTY.md`). Every wait is a `Deadline` from `sd_policy.h`; the bounds are tested (`worst_init_us` < 3 s, `worst_read_call_us` < 0.5 s).
- **Read-only, four layers** (README "How read-only is guaranteed"): (1) `hal/storage.h` has no write call; (2) FatFs is read-only and the glue defines no `disk_write` (and no `disk_ioctl`), so a write reference would not link; (3) the `BlockDevice` has no write call; (4) the SD driver's command type `sd::Cmd` is an allowlist of 15 read-side commands, there is no WRITE_BLOCK (24), WRITE_MULTIPLE (25), PROGRAM_CSD, write-protect, erase, LOCK_UNLOCK or GEN_CMD (56) anywhere, `SdhcBus` refuses a value that is not `known()`, a test walks all 256 values of the type, and another checks every command of a card's whole life. The host backend opens files `O_RDONLY` only, and the load test requires the card tree byte-identical afterwards.
- **Host backend** (`platform/host/dir_storage.h`): a directory as the card, the same contract, names matched without regard to case like FAT. It is what the host tests use; wiring it into `o3sim` as `--card <dir>` is a follow-up.
- **Project load** (`app/og_folder.h`, driven from `appimg::pass()`): at boot, after audio and USB, the card is mounted (`boot: sd mounted, FAT32, <MB>` or the failure) and, if `Workspace/project.mt` exists, the OG project in `Workspace/` is loaded with the existing `formats/og` readers, a slice (16 KB) per pass of the main loop. **The path is the one an OG card holds** (`Workspace/project.mt`); since OS-QAFIX-E-FILE-10 (maintainer, 2026-10-22; new Community OS behaviour) the project that was open last comes first: the newest entry of `Settings/recent.o3rc` (or its `.bak`, only when the file itself is missing) that is still in `Projects/` with a `project.o3pj` or `project.mt` and no `.deleted` marker (`app::boot_recent_project`, `appimg::boot_open_last_project`, `App::boot_open`), opened through File's own load, so the verify of OS-QAFIX-4 runs first. No such entry (list missing, empty, unreadable, entry 0 gone or hidden): the Workspace as before. An entry 0 that is on the card but cannot load (cut, bad checksum, newer version) is NOT skipped: the document stays as it booted and the strip says `PROJECT <name> FAILED: <why>`; it fails the same way on every boot until another project is opened (it is then entry 0). The strip shows only the end of the load (the app's frames are held while the boot gate and the load run). The open writes nothing (the project is already first in the list). A card that is not mounted at power-on, and the USB disk boot, open nothing; a card put in later opens nothing either; `diag load Projects/<name>` loads any folder, which is how a card without a Workspace is tried. Loaded: the project file, every `patterns/pattern_NN.mtp`, every instrument's metadata (`instrument_NN.mti`, `NN name.pti`, `instrument_NN.pti`; the `.pti` PCM is skipped using the file size; a `.pti` beside an `.mti` of the slot wins). **Not loaded by this slice: the sample PCM into SDRAM** (the log said how many frames the `.pti` files declare; OS-007f loads them, see its section). Also not loaded: pattern metadata (names; not in this slice's scope). Bad files are counted and the load goes on; a card error ends it. While loading, the app's frames are held (the screen keeps its picture, the display is serviced); at the end the undo history is reset and the app re-attached.
- **`diag`**: `sd` (slot, mount, card identity and raw CID/CSD, speed, counters, the last load; `sd mount` mounts again), `ls [path]` (a pager), `load [folder]`. The table test and the stage text test were updated; `diag stage` lists "sd card (not mounted)" when a card is in the slot and did not mount.
- **Tests**: host (ASan, UBSan) and QEMU: `mk66_storage_{soc,protocol,card,fat}_test` (register facts against the NXP header, the clock search against NXP's dividers for the same two clocks, the allowlist, CSD/CID against known cards, the init sequence against a software card with every fault, a FAT32 and an exFAT image built in the test from byte maps and read through FatFs, `diag sd` and `ls` through the real shell); host only: `og_folder_test` and `og_folder_fat_test` (the OG folder through the host directory and through FAT32 and the whole card stack, compared with the model the readers make from the same bytes). ASan found and the slice fixed a dangling FatFs volume pointer after a `FatStorage` was destroyed.
- **Size** (image `o3os.hex`, `-Os`, the default build): see the report in the commit message and the README ("Cost of the whole slice").
- **Open decisions for the maintainer:** R0.16 instead of R0.15a (drop-in); whether exFAT stays on (+2.1 KB) since the OG needs FAT32; the Workspace-first policy (README "What is loaded at boot").

## 007f — The project's samples into the SDRAM arena (as built)
Builds on the OS-007e merge. Nothing here has run on a unit; hardware rows SD-13 to SD-15 of `platform/mk66/README.md` are the next session's.

- **Where an OG card keeps a sample** (file layout, from the fixtures): `Workspace/samples/instrNN.wav` (NN = slot + 1) beside `instruments/instrument_NN.mti`, the 1.1 pair; and, since 1.5, `instruments/instrument_NN.pti` (`NN name.pti` in `Projects/`), the 392-byte head followed by mono signed 16-bit PCM at 44.1 kHz. An official 1.9 Workspace holds both for each slot (the maintainer's fixture: the WAV is the `.pti`'s PCM under a 44-byte head, sample for sample). **In the fixture the Workspace WAV is already 16-bit mono.** **Whether the official firmware converts at import, or again when it loads, is an open research question (Q).** This loader accepts only 44,100 Hz (any other file makes the instrument unusable; whether the official firmware does the same is Q). So a project's WAVs are normally already mono 16-bit.
- **`app/og_samples.h`, `src/og_samples.cpp`** (`OgSampleLoader`, `make_sample_desc`, `describe_samples`, `describe_problem`): after `OgFolderLoader` is Done, every sample instrument of the document gets its PCM. A slot a `.pti` was applied to (`OgFolderLoader::pti_slots()`, new) reads it from that file straight into the arena, 16 KB a read, in the directory's listing order; every other sample instrument opens its `sample_path` (`samples/instrNN.wav`) through the existing WAV importer (`formats/wav`: 8/16/24-bit and float, mono or stereo, resumable, nothing is written before the data is known to fit). Slices of the main loop (default 16 KB a pass, at most 32 opens or entries), no heap, READ ONLY (the storage calls of `og_folder.h`). The voices' table is written with `VoicePool::set_sample`, one slot as each sample lands.
- **What is bound:** the instrument's `start` and `end` (0..65535, converted by `floor(point * length / 65535)`; 65535 is the end exactly; whether the official firmware converts the same way is Q) cut the window the voices see; play mode 1 (forward loop) becomes the voices' loop over `[loop1, loop2)` inside it under the conditions of `og_samples.cpp` (a loop that fails them is a one shot); volume 0..100 becomes the voices' 0..127 (100 is 127); `tune` and `fine_tune` go to the voices. Pan, sends, filter, envelopes are not pushed (005d-lite). **Play modes the voices lack** (backward, ping-pong, granular: 2, 3, 7) play the window as a one shot and are counted (`approximated`, logged). **OS-007h, the OG's slice modes are bound as the engine plays them**: *slice* (4) is the selected slice as the window, at the note's pitch, `start`/`end` unused; *beat slice* (5) is the whole sample plus a table of the slice boundaries (`slice_count + 1` offsets, two 16-bit halves each, in the arena after the PCM, `slice_table_samples`) and the voices play slice `note - 24` (clamped; 24 is the OG's pad-board root note, the same in every file seen) one shot **at note 60's pitch whatever the note**, tune and fine tune still applying; *wavetable* (6) is the current window (of `wavetable_window_size` frames, 2048 unless it is none of 32..2048 in powers of two) looped, with the wavetable pitch law `notes[i] x window x 523.2511306 / 44100`. Before this the three were bound as plain windows: in a v16 project from 1.9.0 the 9 beat slice instruments played their whole break one shot from notes 24..40 (three octaves low) and the 2 wavetables played their whole stack of cycles: the unit's "very low, garbled noises". The FX Slice (a slice chosen by a step) and the wavetable position envelope are not pushed. `diag inst <n>` (n = 1..64) prints what is bound for instrument n: mode, window start and length, loop, root, rate, volume and gain, slice count or window size, and the 16-bit sum of the first 64 samples of the window. Test: `og_sample_fidelity_test.cpp` (an independent RIFF decode and a double reference of the play modes against the real loader and voices: a synthetic project in CI, the maintainer's Workspace locally).
- **Tune in the voices** (`audio/voices.h`, `tuned_inc_q32`; closes the tune half of 005d open item V4): `SampleDesc` gets `tune` and `fine_tune` (in the struct's padding: the table is still 20 B a slot). The tune shifts the note index, clamped into the table; the fine tune moves the pitch `|fine| / 100` of the way to the neighbouring semitone, linearly in the pitch, nothing past either end of the table. The fraction is a multiply and a shift (no division in the render context). The 44100 / 44117.65 correction is still not applied. Both functions are `O3OS_AUDIO_INLINE` (the hot path may not call flash: `check_ramfunc` caught the first version); `.ramfunc_l` +284 B.
- **A file that is not there, or not usable, never fails the load.** That instrument stays silent: a missing file, one that would not open or read, one the importer refused, not 44,100 Hz (whether the official firmware refuses other rates is Q), no audio, or a window with start >= end. The first 8 are logged by name (`load: instrument 07 sample not found`), the rest as a count. **An instrument that does not fit what is left of the arena stays silent (`no room`) and the next one is tried** (a smaller one may fit; the importer and the file size say so before a byte is read): a literal "the rest stay silent" would let one corrupt header with a huge size silence every instrument after it. A card error ends the loading; what had not had its turn counts as missing.
- **The load, as a sequence in `app_main.cpp`** (`LoadPhase`): `start_project_load` stops the transport (a Stop on the sequencer's ring, a Play still waiting for the outputs forgotten, the badge says STOP: `App::transport_stopped()`, new) and the app's frames stay held for the whole load; **Settle** waits at least 4 ms and at most 250 ms for the voices to die away; **Project** is 007e's; **Samples** clears the voices' table (the demo kit's sounds or the last project's) and loads. Nothing runs in the audio interrupt; the table is the main loop's, and with the transport stopped and the voices quiet no note can read a slot while it changes (a voice that outlived the timeout has latched its data pointer: it reads arena memory that is changing, a glitch and never a fault). The display is serviced every pass, as for 007e.
- **The demo kit** is for when no project is loaded (a failed load leaves the document and the table as they were: the kit, its instruments and its pattern stay; only the transport has been stopped) or the loaded project has **no sample or module instrument anywhere and no instrument of any kind in instruments 1-48** (`app::demo_kit_fits`; OS-BUG-DEMOKIT: before, only "no sample instrument" was tested and the kit overwrote the instruments 1-4 of a project of modules or MIDI instruments; only MIDI instruments in 49-64, the 16 channels that every OG project holds, do not stop it, so a MIDI-only project with an instrument anywhere in 1-48 keeps its slots, tempo and pattern 1; new Community OS behaviour, a default for the maintainer to confirm; latent, not fixed here: a project whose only instruments are the OG MIDI channels 49-64 and whose pattern 1 is empty still gets the kit and its tempo): the kit goes into the empty arena again and its four instruments and pattern 1 into the project, as at boot. `app::install_demo_kit` refuses a project the kit does not fit. A project whose sample instruments are all missing, or that holds only module or MIDI instruments, stays as it is (the log says so for the first); it does not get the kit over its own instruments. A successful load replaces the kit and its pattern (the project reader resets the document; the table is cleared).
- **Logs and `diag`:** `boot: samples N loaded, M missing, K KB` (K in KiB, rounded; ", X no room" and the card's error when there were any), one line per problem (8 at most), `load: sample arena full, instruments silent N`, `load: instruments played one shot ...`. `diag sd` prints the same figure on a `pcm:` line under `load:`.
- **Our choices, for files that are not mono 16-bit:** a stereo WAV is mixed (L + R) / 2 by the importer and 24-bit and float are dithered (TPDF); what the official firmware does with them is an open research question (Q; **a maintainer decision whether `og_samples` should take the left channel**).
