## 0. What exists (verified 2026-10-17)

- **The OS never reads the power switch.** It is on Teensy pin 9 = **PTC3**; the early-boot table lists it as an input, not driven (not read) **[code]** `platform/mk66/README.md` ("Pins driven or read in the first boot steps"); "not handled ... left alone, an open question" **[code]** `README.md` ("The input hardware as found"); question 9 **[code]** `README.md`, open questions. `input/src/device.cpp` says the same. So holding the button does nothing; the only way off is to pull the power.
- The pin facts of the board: audio mute key PTD6 (LOW = muted), SDRAM power key PTA24 (HIGH powers the SDRAM, LOW removes its power), status LED PTC19, FT812 CS PTD15 and PD# PTD11, radio reset PTE27, input select PTE26, MIDI TX PTE24, the bootloader request PTA1 **[code]** `include/o3os/platform/mk66/board.h:26-114`. **No pin of the table is a power latch, an enable or a kill line.**
- Shutdown pieces that exist: `appimg::stop_transport()` (a Stop on the sequencer's ring) and `Mk66Audio::mute()` (the amplifier key LOW first, then the codec's `kMute` plan) are what `fw update` calls as `quiesce()` **[code]** `update/src/fw_host_mk66.cpp:60-64`, `src/app_main.cpp:1582`, `src/audio.cpp:359`; `storage::device::release()` is the unmount **[code]** `storage/include/.../device.h:41`; `card_busy()` and the claims list who holds the card **[code]** `device.h:44-47`, `app_main.cpp:1523-1529`, `storage_in_use()` at `app_main.cpp:1743`; `usb0` has a detach (pull-up off, streams stopped) inside `request_mode` **[code]** `usb/include/.../usb0.h:77`; `Ft812Display::hold_dark()` (backlight off and held) **[code]** `display/include/.../display.h:108`; the pad LED chip has a software shutdown register **[code]** `input/include/.../pad_leds.h:43`; the Si4703 is held in reset from boot **[code]** `board.h:101-108`.
- Reset causes are decoded (RCM_SRS0 and SRS1) **[code]** `include/o3os/platform/mk66/platform.h:33-42`; `boot::init_clocks()` writes `SMC_PMPROT` once with AHSRUN, AVLP, ALLS and AVLLS allowed, so VLPR can be entered later without a boot change **[code]** `src/boot.cpp:147`. `boot::reset_chip()` is the one SYSRESETREQ of the image and drops the amplifier key first **[code]** `crash_store.cpp:98`; the software-reset cause is decoded (`kResetSoftware`, `platform.h:42`). **The same function leaves the unit in HSRUN**: `SMC_PMCTRL` RUNM = HSRUN with `PMSTAT` waited (`boot.cpp:162-163`), then the PLL to 180 MHz (`boot.cpp:182`); nothing in the tree returns to RUN. The repo says only that HSRUN is needed above 120 MHz (`boot.cpp:161`, `clock_config.h:4`, `README.md:200`); it holds no copy of the reference manual and states nothing about entering VLPR or a stop mode from HSRUN. The risk review's claim that **a low-power mode may not be entered from HSRUN** is therefore **[datasheet]**, unverified in the tree: slice 2 treats it as true (4.4: HSRUN, then RUN, then VLPR) and the engineer confirms the allowed transitions on the reference manual before coding.
- The main loop is `appimg::pass()`: it polls the card, scans the keys, services the display, runs the boot gate, the load phases and the app's frame (`app_main.cpp:2383`). Everything below is a main-loop state machine in that style (`FwService`: bounded steps, deadlines by the millisecond clock, no waits).
- Device settings save themselves 1.5 s after the last change (`SaveService::poll`, `save_service.h:27, 405`); a save is atomic (Temp, read-back, rename; the old file stays whole; a cancel removes the Temp); a running export "cancels like the RECENT file"; an OG export has `project.mt` last, so a stopped one is not a project **[code]** `save_service.h:26-43, 308, 316, 468`.
- The OS has **no unsaved-work prompt except the F1-again questions** of File; `App::dirty()` says whether the project has unsaved changes **[code]** `app/include/o3os/app/app.h:326`.

## 1. Decisions

**Maintainer (2026-10-17, binding):**
1. Holding Power powers the unit off.
2. While it is held, a line shows the hold time filling. When the line reaches its end, at **2 s**, the unit powers off. Letting go earlier cancels.
3. Shift + Power = screenshot is a separate later item (`OS-SCREENSHOT`). This spec only reserves the gesture.

**Fable for the maintainer (2026-10-17, binding; the maintainer delegated the decision table to Fable):**
- Row 1: yes. Ship the low-power off, labelled with the measured draw; the manual says unplug to remove power fully.
- Row 2: optional. Slice 2 does not wait for M1/M2. Plug-start behaviour: unknown.
- Row 3: finish the save up to 5 s, then cancel.
- Row 4: refuse once; a second hold within 10 s stops the export and powers off.
- Row 5: warn on the line only, never save.
- Row 6: warn first, power off on the second hold.
- Row 7: already answered by the maintainer ("power off is also power on").
- Row 8: P1, then P2.
- Row 9: unknown. Keep F0 (restart only after release) and QA-GLB-103 with a gate-checked .ptf in `Firmware/`.
- Conditions kept by Fable:
  - the first unit run is `diag power off dry` with no button held;
  - if the P2 wake test fails on the unit, the alpha ships with P1's restart-off only, never a dark unit that needs a cable pull.

**Taken by this spec** (reversible; the numbers are tuned on the unit):
- **D1 Power is not an `app::Button`.** A button goes through the gesture and binding pipeline, where a modal overlay captures it ("screen buttons do nothing under it", ui-map). Power must work under every overlay, in INPUT TEST and in the boot disk mode. It is a platform input: the pure `core::PowerHold` (section 3) reads the debounced level; the platform shows the app one number (the fill) and runs the shutdown. No new HAL interface and no new `Button` code in slice 1 (this answers README question 9).
- **D2 One-way commit.** When the line reaches its end the unit is committed: a release after that does not cancel, the keys, pads and MIDI input are ignored, and the console answers `ERR powering off` to `reset` and `fw`. The only exits before the commit are a release, a Shift press (D5) and a refusal (section 4.2).
- **D3 No new file, no new format.** The shutdown writes only what the OS already writes (a pending device-settings save). No project is saved by it.
- **D4 The line is a full-width bar, not a new colour.** Theme tokens only (the palette keeps its sixteen). It is drawn after the overlays, so it shows over a modal one. Position and height are the engineer's within: at least 4 px, full width, no collision with the REC frame (OS-RECSIGN draws a three-pixel frame round the grid).
- **D5 Shift cancels.** Shift down when Power goes down: reserved, nothing happens (no line, no hint), as for any blank Shift + key (QA-GLB-013). Shift down during a hold: the hold is cancelled and spent until Power is released. A user who means the screenshot never loses the project by being slow. **Shift down when Power goes down is the screenshot (OS-SCREENSHOT, `docs/specs/OS-SCREENSHOT.md`): `PowerHold` reports it once as `Result::screenshot`; the hold itself stays `Spent` and shows nothing.**

## 2. Can the board cut its own power?

### 2.1 Evidence

|---|---|---|---|

### 2.2 Finding

**No power latch, enable or kill pin is known. [open]** The pin tables and docs of `platform/mk66` do not name one, and the public facts (E2, E3) cannot tell a self-cutting board from a deep sleep. The OG's own power-off behaviour is not recorded anywhere in the tree. The answer comes from measurements on the unit (M1 to M3), never from the official firmware.

**Therefore "off" is built as the fallback** (**new Community OS behaviour**, our own design) and the pin, if it exists, replaces its last step later:
- every peripheral is put in its own shutdown (the codec, the amplifier key, the display and backlight, the pad LEDs, the radio, USB, the SD card unmounted, the SDRAM's power key LOW);
- the MCU drops out of the HSRUN the boot leaves, goes through RUN into **VLPR** (very-low-power RUN) and **polls PTC3** from a small loop in flash; a debounced press ends the loop with a **software reset**, a full boot (4.4, section 6). The maintainer's decision (2026-10-17): "power off is also power on", the same button starts the unit. There is no LLWU, no VLLS and no pad isolation to manage, and the boot path does not change. The mode, clock limits and status values are **[datasheet]**, confirmed on the reference manual in slice 2;
- the board's regulators, the SD card, the codec and the other chips stay powered: the unit is dark and silent, **not** electrically off. The draw (VLPR core at a few MHz [est], plus the board) is **[open]** until measured (2.3).

## 3. The hold: input, timing, the line

`core::PowerHold` (new, header only, `core/`): a pure object, `update(now_ms, raw_pressed, shift_down, ready)` returning the state and the fill; no clock of its own, so it is tested on the host and drives the simulator. States and rules, all constants in one block:

| State | Rule |
|---|---|
| `Booting` | The button is not read as a hold until the app has the screen (`BootGate` released, no load phase) and the level has been **released for `kArmReleaseMs` = 100 ms** (by samples no more than `kMaxGapMs` apart, see below). A Power held through the boot (the wake press, kept down) never counts. This is also what makes a wrong polarity harmless: a switch that always reads "pressed" never arms. After `kStuckLogMs` = 5000 ms in this state the platform logs `power: held or stuck since boot: waiting for a release` once. |
| `Armed` | A debounced press (`kDebounceMs` = 30 ms, both edges, by the millisecond clock, not by passes) starts the hold. Shift down at that moment: `Spent` (D5). |
| `Holding` | `fill = held_ms / kHoldMs`, `kHoldMs` = **2000** (maintainer). Shift pressed: `Spent`, the line empties. A debounced release: back to `Armed`; if `kHintMinMs` (150) <= held < 2000 the strip shows `HOLD POWER 2 S TO SWITCH OFF` for 1.5 s [default]; under 150 ms nothing at all. `held >= kHoldMs`: `Commit` once. |
| `Spent` | Waits for a release, then `Armed`. |

- The line shows from `kShowAfterMs` = 150 ms of hold (a brush leaves no flicker) at its true fill; it is empty again on any exit. While it shows, the strip reads `HOLD TO SWITCH OFF`, or **`UNSAVED WORK - LET GO TO KEEP IT`** when the project is unsaved (`App::dirty()`) or a recorded take / loop is not saved [default]; the user can still let go. The shutdown **never saves a project** (D3).
- The platform polls PTC3 **once per main-loop pass** (`appimg::pass()`) and nowhere else while the app runs (the off loop of 4.4 polls it after the app has stopped). It does **not** poll from the idle hook: that hook runs only inside `boot::delay_ms()` and is the boot gate's display service (`idle_service`, `app_main.cpp:1440`; set at 1454 and 2117, cleared at 2120 and 2412), with no PTC3 read. So two samples can be seconds apart: the card mount blocks up to 3 s (display kept serviced) and `Mk66Audio::unmute()` about 0.2 s. The hold is measured by `system_clock().uptime_ms()`, and the line does not move during a block.
- **Sample gap (`kMaxGapMs` = 250 ms [default]).** A sample that arrives more than `kMaxGapMs` after the previous one is a new start, not a continuation: the debounce restarts from that sample, `Holding` goes back to `Armed` (the press is seen again, needs its 30 ms and then the whole 2000 ms), and the 100 ms release of `Booting` restarts. Two low samples 2 s or more apart (either side of a card mount or an `unmute`) therefore never add up to one hold. The unmute's 0.2 s sits inside the gap, so a hold normally survives it; a longer block only delays the off, never fires it. The host test feeds exactly these gaps (below and above the limit, in `Booting`, `Armed` and `Holding`).
- **Pull and polarity are [open]** (M4). A tact switch needs a pull somewhere, so the board is expected to have an external one (unverified). Default taken in P1 (`board.h` `kPowerPull` = 1): active low with the internal pull-up enabled, so that a pin nothing pulls cannot float low (an external pull-up, if present, is in parallel). `kPowerActiveLow` and `kPowerPull` are the only two board constants; a host test runs the whole table for both polarities. `diag power` prints the raw level, the debounced state, the fill and the counters (presses, holds, taps, commits, refusals).
- Power is not part of any boot chord (Shift + F1 + F8 and Shift + F1 + F7 are read in a 150 ms window and do not read PTC3).

## 4. The shutdown, in order

A pure `PowerService` (new, `platform/mk66/power/`, the shape of `FwService` over a `PowerHost` interface: `quiesce_engine()`, `audio_down()`, `settings_flush()`, `card_busy()`, `card_release()`, `usb_down()`, `lights_out()`, `enter_off()`, `now_ms()`, `log()`) is stepped once per pass. Each stage has a deadline; a stage that cannot finish moves on at its deadline (4.3) so the unit always ends off. **Nothing waits inside the render or an interrupt**; the render and the audio DMA run until stage A2 and are stopped from the main loop by a **new** `Mk66Audio::stop()` (4.6). No audio stop path exists today: `stop_hardware()` (`audio.cpp:159`) is file-local and runs only when `start()` fails, and `diag audio` has only `start`. After the commit a global deadline (4.5) and a power-off latch (4.6) apply. The host test records the call order of a fake host.

### 4.2 Refusals (stage 0)

A refusal empties the line, shows a strip text for 3 s and leaves everything as it was. The button is armed again after the release.

| Case | Text | A second hold |
|---|---|---|
| Firmware update on the card (`firmware_has_card()`: upload, check, arm, hand-over) | `FIRMWARE UPDATE RUNNING` | refused again; the update path ends in seconds |
| A WAV export, a stem set, or the OG project export running (modal ExportProgress overlay) | `EXPORT RUNNING - HOLD POWER AGAIN TO STOP IT` | a second completed hold within 10 s cancels the export (its normal cancel: finished files stay, no `project.mt` for the OG set, no file under a final name for a WAV) and runs the stages |
| The boot disk with a **writable** disk (when the writable step exists; read-only: no refusal) | `COMPUTER MAY BE WRITING - HOLD AGAIN` | a second hold within 10 s runs the stages, with the disk's own step in 5 |

### 4.3 Why save-finishes and export-refuses

An atomic save is short (the cost model is `AtomicSave::kBytesPerUs`, provisional) and the user's intent to keep it is clear; waiting up to 5 s is cheaper than losing it. An export can take a minute or more; refusing once, with the way out printed, protects it without ever leaving the user stuck (the second hold stops it). Both are decided (section 13, rows 3 and 4) as recommended here.

### 4.4 Stage F: the release wait, the restart (slice 1), the VLPR off and the wake (slice 2)

Our own design, **new Community OS behaviour**; it rests on the K66 reference manual, the tree and the maintainer's statements, nothing else. Two facts shape stage F: the user is usually **still holding Power** when the line ends, and the bootloader that runs first after any reset has an unknown trigger (section 6, R8). So both slices start stage F the same way.

- **F0 Release wait.** On entry, by the normal path or by the deadline of 4.5, the amplifier key is driven LOW first (a GPIO write). Then wait until the debounced level of PTC3 has stayed released for `kReleaseStableMs` = 100 ms (the debounce and the gap rule of section 3). By now the unit is dark and silent. This is the one wait that is on the user, not on hardware: it makes no host call, runs once per pass, logs `power: waiting for Power to be released` once at 5 s, and sits outside the global deadline of 4.5. If Power is never released (held, a stuck switch, a wrong polarity constant), **neither the restart nor the off happens**: the unit stays dark and awake and the cable pull is the exit. A bounce on the release restarts the 100 ms.
- **Slice 1, F1: `boot::reset_chip()`** (SYSRESETREQ; it drops the amplifier key again, `crash_store.cpp:98`), only after F0: a normal boot. This is what `diag power off` and `diag power off dry` both end in.
- **Slice 2, F1-F6: the VLPR off.** The unit enters VLPR (very-low-power RUN), puts every pin quiet and polls PTC3 from a tiny loop in flash. A debounced press, once it has ended in a stable release again (`kWakeAfterRelease`, default true), ends the loop with `boot::reset_chip()`: a full boot. No LLWU, no VLLS, no wake source, no pad isolation, no change to the boot path (`SMC_PMPROT` already allows AVLP, `boot.cpp:147`). The order is the point. The millisecond clock is off from step 1, so every wait is a poll count like `wait_until` in `boot.cpp`, and every time is the DWT cycle counter through `delay_us` (which follows `g_core_hz`). The steps sit behind a small `OffPlatform` interface so the order is host-tested.
  1. Interrupts masked, SysTick stopped, every DMA already stopped (A2). **No SDRAM access from here**: the code and the data used by F live in flash and SRAM only (checked in the slice by the linker map and a `static_assert` on the section).
  2. **The USB oscillator off.** The USB module's IRC48M (started by `usb0::start()`, left running by `detach_for_power()`) "should be disabled by software prior to VLPR entry" (RM 6.7.2 p127): `usb0::irc48m_off()` (clock recovery off, then `CLK_RECOVER_IRC_EN` cleared), a write that cannot fail and is skipped when the module's clock gate was never opened.
  3. **Leave HSRUN, in a factor-of-2 step.** The boot leaves the unit in HSRUN at 180 MHz (section 0), neither VLPR nor a stop mode may be entered from HSRUN, and **in HSRUN a clock frequency change is limited to a factor of 2 per step** (RM 16.4.3.3 p352). The crystal is 11 times slower than 180 MHz, so the source is **not** switched in HSRUN. Instead one `SIM_CLKDIV1` write doubles every divider (core /2, bus /4, FlexBus /4, flash /14: 90, 45, 45 and 12.9 MHz, MCGOUTCLK still the PLL), read back (an invalid ratio is ignored by the register, RF9); every domain is then well inside the RUN limits. Then `SMC_PMCTRL[RUNM]` = RUN and a wait for `SMC_PMSTAT` to read RUN. **No settle delay is added:** the RM (16.4.3.3 p352) and AN4503 (p37) prescribe no wait and no status poll after a divider change or after clearing `RUNM`; the only prescribed poll is `PMSTAT` on HSRUN entry. The `PMSTAT` wait here is this code's own check (a transition that did not happen is a restart). **Chosen over a staircase of several steps:** the single step reaches a RUN-legal state in one write with one read-back. Then, **in RUN**, `MCG_C1[CLKS]` from the PLL to the crystal (PEE -> PBE, the x11 drop that the rule forbids in HSRUN) and a wait for `MCG_S[CLKST]`.
  4. **The VLPR clock limits.** In VLPR the core, bus, FlexBus and flash clocks are limited to 4, 4, 4 and 1 MHz (RF8, inclusive maxima), and the MCG must be in a bypassed low-power state, BLPE (the crystal stays the source; RF7). So: `SIM_CLKDIV1` set while still in RUN on the crystal (it cannot be written in VLPR, RF9), where the dividers only ever divide further than the step above (the rule `boot.cpp` follows), so every domain is inside its limit at every moment; then the MCG to BLPE and a wait for its status (`MCG_C6[CME0]` must be 0: the C6 write is VDIV only); `g_core_hz` = the divided core rate.
  5. **Enter VLPR.** `SMC_PMCTRL[RUNM]` = VLPR and a wait for `SMC_PMSTAT` to read VLPR.
  **Any of the waits or checks in steps 3-5 ending at its limit: `boot::reset_chip()` (a normal boot), never a half-entered state.** The SDRAM is still powered at these steps, so that reset starts from a known state; the user sees a restart instead of an off.
  6. **The pins.** The 39 SDRAM interface pins of `sdramc_config.h` `kPins` (mux 5) go to GPIO **outputs LOW** (or high impedance: the reference manual and the SDRAM's input ratings decide, **[datasheet]**; LOW is the default), so that no pin drives a high level into an SDRAM whose supply is about to go (current through its input protection). Then the other quiet pins at their `kQuietPins` levels, the amplifier key confirmed LOW, the status LED off, PTC3's clock gate, direction and pull put back (the last PORTC write), and, only if `kOffCutsSdram` (default false), **PTA24 LOW, last of the outputs**.
  7. **The poll loop** (`[[noreturn]]`, the one deliberate unbounded loop of the design: it is the off state, it makes no host call and it ends only in a reset). Read PTC3 every `kOffPollUs` = 1000 us. Edge semantics: first require the released level for `kReleaseStableMs`, then a press that stays down for `kWakeDebounceMs` = 30 ms. A stuck-pressed switch (a wrong polarity constant) therefore never resets, and a glitch shorter than the debounce never resets. On the press: `boot::reset_chip()`, but only after the press has ended in a stable release of `kReleaseStableMs` while `kWakeAfterRelease` is true (**the default until QA-GLB-103 has passed on the unit**): the bootloader may react to a button that is down at the reset (section 6), so the wake is the release of a press. With the constant false the reset comes at the debounced press itself.
- **The wake is a software reset from VLPR.** The reset returns the SMC to RUN and the clocks to their reset state (RF10: confirmed on paper, RM 16.4.3.2 p352; proven on the unit by the wake), and the boot runs unchanged: the quiet pins, the SDRAM bring-up (it raises PTA24 as at power-on, the SDRAM contents were gone anyway), the display, the audio. The reset cause is the software reset (`RCM_SRS1` SW, `kResetSoftware`, `platform.h:42`), the same as for `reset` and `fw update`; no marker is kept in SRAM. **The maintainer's decision (2026-10-17): "power off is also power on"**, the same button starts the unit.
- The SDRAM key is the one known switched rail. `kOffCutsSdram` is **false by default**: PTA24 stays HIGH in the off, because if the external pull-up of PTC3 hangs on that rail the pin would read pressed for good with PTA24 LOW and the unit would never wake. The cost is the SDRAM's own idle current (its clock and CKE are driven LOW, so it holds no data and draws its power-down level); no figure is known (the part is not recorded in the tree). The unit measurement M3 compares the draw with and without it, and the VLPR draw of the MCU itself; the constant goes to true only after a unit test shows PTC3 still reads released, and the unit still wakes, with PTA24 LOW.
- If the board turns out to have a kill line (M2), slice 3 drives it in stage F and keeps the VLPR loop as the fall-through if the unit is still alive 500 ms later (a supply that is not cut).

### 4.5 After the commit: the global deadline

After the commit the keys, pads, MIDI and console are locked (D2) and the watchdog is off (R11), so nothing else ends a stage that hangs. `PowerService` keeps one **global deadline**, `kGlobalCapMs` = 10000 ms [default] from stage A: at it, every stage not yet finished is abandoned (the card is released only if `card_busy()` is false; otherwise it is left as a pulled card, logged) and the machine jumps to stage F, whose first act in both slices is the amplifier key LOW (a GPIO write, which cannot hang) before F0 (4.4). The stage caps (`kSaveWaitMs`, `kCardHardCapMs` = 8000 ms) are all below it, so it fires only when a stage does not finish. F0 is outside it (it waits for the user). The deadline bounds the state machine, not a call stuck inside a driver: each host call must return on its own (the I2C, USB and card drivers have their own limits), and a call with no stated bound is a review defect. The host test makes **every `PowerHost` call hang** (never finish): `enter_off` is reached within the cap plus one pass, every other call is made at most once, none after `enter_off`.

### 4.6 The audio stop and the power-off latch (an audio-path change)

P1 is not free of the audio path: it changes its start and stop (not the block callback, the DSP or the voices). What exists: `stop_hardware()` (`audio.cpp:159`) is file-local and runs only when `start()` fails (`audio.cpp:333`); `diag audio` has only `start` (`platform/mk66/usb/src/console.cpp:520-526`, "usage: audio start"); `mute()` leaves the I2S and the DMA running. P1 adds:

1. **`Mk66Audio::stop()`** (new, with a free function `audio_stop()` in `audio.h` in the shape of `audio_input_apply`; main thread): the A2 order of 4.1 (DAC ramp, key LOW, `kMute`, the codec's analog power-down plan), then the body of `stop_hardware()` (I2S TCSR and RCSR cleared, the two eDMA channels quiesced, the DMA and render IRQ lines disabled: a render block in flight finishes), then `started_ = false` and `enabled_ = false`. Idempotent, and a no-op when the path never started (`started_` false: the boot disk mode); called only from `PowerHost::audio_down()`.
2. **The stall detector would fire.** With the I2S stopped the boundary count stands still, and `main.cpp:419-424` latches `kAudioFault` (the 11-pulse LED code; "a fault is final") after `kAudioStallMs` = 300 ms (`main.cpp:72`), which stage E and F outlast. The **power-off latch** (`appimg::power_off_latched()`, set at stage A, before anything stops, never cleared; a restart or the poll loop ends the run) makes the audio poll skip the stall verdict and the pattern: the LED keeps its heartbeat.
3. **Nothing may reopen the outputs.** `open_wanted()` (`output_gate.h:64`) gets a sixth argument, `powering_off`, and returns false when it is set, whatever the other arguments are; `OpenRetry` is not consulted. The latch is its own flag: `audio_outputs_open()` is cleared by every mute (the update path's quiesce), so it cannot be the guard, and `audio_open_pending` (a Play or a live note that waits) cannot reopen either, since the latch is checked first.

Tests: `mk66_output_gate_test.cpp` (`open_wanted` is false with the latch for every combination of the other arguments); the `PowerService` fake (`audio_down()` once, latch set before it); the codec's power-down plan on the register model. QA-GLB-116 (unit). Cost: about 0.3 KB of flash [est], no per-block cost.

### 4.7 P2 as built (2026-10-17; code in `platform/mk66/power/`, host-tested in `platform/mk66/tests/mk66_power_off_test.cpp`)

The sequence is the pure `off_prepare()` / `off_poll()` / `off_run()` of `power_off.h` over an `OffPlatform`; the registers are in `Mk66OffPlatform` (`power_host_mk66.cpp`), the VLPR clock numbers in `clock_config.h` with `static_assert`s. A real hold, and `diag power off`, end in the VLPR off after F0; `diag power off dry` and a build with `-DO3OS_POWER_VLPR_OFF=OFF` (the rollback of Fable's condition "if the P2 wake test fails on the unit, ship P1's restart-off only": one build option, no source change) end in P1's restart.

**As 4.4, with these differences** (each reversible): (1) the MCG goes PEE -> PBE -> FBE -> **BLPE** (the crystal stays the source, no BLPI); (2) the dividers are core, bus and FlexBus **/8 = 2 MHz** and flash **/16 = 1 MHz** (the crystal's 16 MHz over the largest divider is exactly the flash limit), not "about 4 MHz"; (3) a step is new before the HSRUN exit: a running watchdog (`WDOG_STCTRLH[WDOGEN]`) makes the off a restart, see below; two more come from the reference-manual check: the IRC48M is switched off (4.4 step 2), and the HSRUN exit is a factor-of-2 divider step with the source switched afterwards, in RUN (4.4 step 3), instead of the crystal first; (4) the quiet-pin step re-applies `kQuietPins` **except the FT812's PD#, which stays LOW** (stage E put the chip in power-down; the table's HIGH would wake it), and also drives the **I2S master clock pin PTE6 LOW** (the audio stop clears TCSR/RCSR but leaves `MCR[MOE]` on, so MCLK would keep toggling from a system clock whose rate has just changed), then the 39 SDRAM pins LOW, then PTC3's input state re-asserted, then (only if `kOffCutsSdram`, default **false**) PTA24 LOW last; (5) every wait is a poll count (`kOffPollLimit` = 200 000 polls: 50 ms at 16 MHz, 0.4 s at 2 MHz); a wait that runs out is a reset; (6) a **record of the last shutdown** (`power_record.h`, 28 bytes of noinit SRAM, a magic and a check word, as the crash record does it): the last stage entered, the time each stage was entered in ms from A (saturated at 65 535; "Done" is the call of `enter_off`, written BEFORE it because it does not return), the notes of the run (dry, global deadline, save cancelled, save at the hard cap, card busy at release, lights cap, export cancelled by the second hold), the last refusal, and the result of the VLPR off (`OffMark`: began, restarted at a step, ended by a press). It exists because the diag log is in SDRAM and the console ends at USB off (stage D), so on a run with no hands (the maintainer's tester now has only the console) stages A to E would otherwise leave nothing to read; `diag power` prints it after the boot (`power: last shutdown dry, reached done`, `power: ms from A: A quiet 0, A2 mute 10, ...`, `power: notes: ...`, `power: last refusal: ...`, `power: last off RESTARTED at step: ...`) and keeps it until the next shutdown or refusal (a new run clears it; a power-up leaves garbage, which the check refuses). It is read-only diagnostics: the boot path never reads it. **This relaxes one sentence of 4.4** ("no marker is kept in SRAM"), which was about telling a wake from a reset in the boot path: nothing in the boot path reads the record. It rests on the premise the crash record already rests on, that the SRAM holds through SYSRESETREQ (`platform/mk66/README.md`, "Whether SRAM keeps its contents...": a hardware check); an empty record after a restart is itself the answer. No persistent format is touched (R13).

**The review's defaults (folded 2026-10-17).** (7) `kWakeAfterRelease` is **true** and `kOffCutsSdram` is **false** until the unit has answered QA-GLB-103 and QA-GLB-117 (see 4.4 step 7 and the SDRAM bullet); the host test pins both with a `static_assert`, so flipping one is a deliberate edit of the test. (8) PTC3 is on none of the pins the off drives (`static_assert`s in `power_host_mk66.cpp` and the same checks in `mk66_power_off_test.cpp`), and `pins_quiet()` ends by putting the PORTC clock gate, the PTC3 input direction and its pull back. (9) `Mk66OffPlatform` touches registers and has no host test; the encodings it relies on are pinned at compile time instead: RF1-RF3, RF5-RF7 and RF12 by `static_assert`s in `regs.h`, RF5 and RF6 (the values written) in `power_host_mk66.cpp`, RF9 (`SIM_CLKDIV1` = `0x777F0000`) in `clock_config.h`. They check the typing of the constants against the table, not the manual: **the RF check on NXP's documents comes first, and the first unit image is cut only after it**.

**The watchdog.** It is off since `startup.cpp` (WDOGEN clear) and nothing re-enables it today (`main.cpp` "Watchdog re-enable point"), so VLPR runs with no watchdog and nothing to feed. The off does not touch it (an unlock sequence in the wrong window can itself reset); it **reads** WDOGEN right after the interrupts are masked and, if a later slice has turned the watchdog on, takes the restart path (a mark `Failed at watchdog running`) rather than enter VLPR with a counter that would reset the unit from there. R11 is closed that way: that slice must also teach the off to stop it.

**Register facts the code relies on.** The engineer of P2 had no copy of the reference manual; **all 13 rows were then checked against NXP's documents on 2026-10-17** (the reference manual K66P144M180SF5RMV2 Rev 2, the data sheet K66P144M180SF5V2 Rev 4, AN4503) and are CONFIRMED, with the pages below. ## 6. What wakes the unit and what boots next

- **Wake: Power only.** **Maintainer's decision (2026-10-17): "power off is also power on"**: the same button starts the unit, and a press while off gives a full boot. In the VLPR off the loop of 4.4 polls PTC3 and nothing else, so no pad, MIDI byte or USB event wakes the unit (a bump in a bag must not boot it; decision row 7, answered). A cable replug is a power-on reset **[open]**: whether the OG starts by itself when the cable is plugged is part of M1.
- **What boots: the normal cold boot**, exactly the path of a power-up: the bootloader, the app, the logo, the card mount, `Workspace/`, the settings, the outputs opening once. The reset cause is the software reset (RCM_SRS1 SW, logged as for any `reset`). Nothing is restored from before the off (the SDRAM is unpowered and the app state is not kept); the project is the one on the card, so unsaved work is lost, as with a pulled cable.
- **The bootloader and a held button.** The bootloader runs first after any reset, **before the app** (so before anything of this spec runs). What it does with a button held at that moment is **[open]**: the hidden reset button makes it flash the first `.ptf` of `Firmware/` (`platform/mk66/README.md:1174`), its own trigger is not known, and this spec claims **no** guarantee that a restart or a wake cannot flash. It applies to **both slices**: slice 1's restart too, because PTC3 is usually still held when the line ends; and in slice 2 the wake reset comes at the **release** of the press (`kWakeAfterRelease`, true by default, 4.4 step 7), so the bootloader runs with the button up; the reset at the press itself (false) is allowed only if the unit test below shows that a held button is harmless. So:
  1. Stage F waits for a stable release of Power before the restart (slice 1) or the VLPR entry (slice 2) (F0, 4.4).
  2. The **first unit run** of slice 1 is `diag power off dry` with **no button held** (no press is involved; QA-GLB-113).
  3. The **wakes** of slice 2 are tested **with a `.ptf` in `Firmware/`** (the build under test, passed through `fw-gate-check`, so a flash by the bootloader would be a known image) **and with no card**, the button held for 1 s and for 10 s (QA-GLB-103). The result is recorded here as the bootloader's observed behaviour (observed behaviour of the unit, not parity).
  The worst cases are the unit flashing that known `.ptf` or staying in the bootloader; recovery is the cable pull or moving the card (`README.md:1174`: a broken candidate that lands first is reflashed by the button).
- The hidden reset button on the rear is unchanged: it starts the bootloader's flash of the first `.ptf` in `Firmware/`, also from the "off" state.

## 9. Level C: risks for the risk review

1. **R1 A card write cut by the off.** A save or settings write in flight at the end of the hold. Mitigated by the finish-then-cancel rule (4.1 B), the atomic save (the old file stays), the held settings timer and stage C only after `card_busy()` is false: `release()` writes and cancels nothing (`device.cpp:44`), and `card_busy()` includes the app's job-runner claim. Residual: the 8 s hard cap proceeds anyway (a cut like a pulled card); a leftover `_o3save.tmp` is cleaned by the next save. To review: that `release()` is never reached while `card_busy()` is true before the hard cap, and that `SaveService::flush_settings` is the same writer and file.
2. **R2 The boot disk mode.** The unmount is the MSC close, the unplug is without an eject. With a writable disk the computer's cache is lost (OS-USBDISK 6.2). The two-hold rule is the only protection.
3. **R3 The SDRAM rail.** PTA24 LOW removes the SDRAM's power: any later access (a stack, the diag log, a DMA, the display service) is a bus hang. Stage F must run from flash and SRAM, with interrupts masked and every DMA stopped. The 39 FlexBus pins are driven LOW (or high impedance) before PTA24 goes LOW and stay GPIO outputs in the poll loop, so no pin drives a high level into an unpowered SDRAM (4.4, step 5). A bug here hangs the unit with the cable pull as the exit.
4. **R4 The reset out of VLPR.** The wake is `boot::reset_chip()` from VLPR; the reset returns the SMC to RUN and the clocks to their reset state (RF10: confirmed on paper, RM 16.4.3.2 p352; proven on the unit by the wake), and the boot runs unchanged. There is no pad isolation, no `ACKISO` and no boot-path change. To verify on the unit: the first boot after a VLPR wake brings up the SDRAM, display and audio as after a power-up (QA-GLB-103).
5. **R5 Polarity and pull of PTC3 unknown.** Wrong polarity: the release-arm rule keeps the unit from switching itself off at boot; the unit session reads the pin first (`diag power`), and the worst case of a wrong constant in slice 1 is a restart, not a stop.
6. **R6 An off that does not stay off, or never wakes.** The poll loop needs the released level and then a 30 ms stable press (edge semantics, 4.4 step 7), so a glitch or a release bounce does not wake it and a stuck-pressed switch never resets. A failed clock or mode step resets (a restart instead of an off, visible). A loop that cannot see the press (a wrong polarity constant, M4, or a PTC3 pull-up that goes down with the SDRAM's rail: `kOffCutsSdram`, false by default) never wakes: the cable replug is the recovery; nothing flash-related is written.
7. **R7 Output stage pops.** The key LOW before the codec's analog power-down is an assumption about the board's output stage ("what the board's output stage does while PTD6 floats" is an open question of OS-OUTON); checked with a scope on both jacks (QA-GLB-102, 105).
8. **R8 The bootloader with a button held, after a wake or a restart.** Its trigger is unknown (`README.md:1174`: the reset button flashes the first `.ptf` of `Firmware/`) and it runs before the app. It applies to slice 1's restart as much as to slice 2's wake, because PTC3 is usually still held when the line ends; and in slice 2 the wake reset comes at the release of the press (`kWakeAfterRelease`, true by default until the unit test), so the button is up at that reset. No claim that no flash write is involved. Mitigations: F0, a stable release before any restart or VLPR entry (4.4); the first unit run is `diag power off dry` with no button held; the wakes are tested with a gate-checked `.ptf` in `Firmware/` and with no card, the button held for 1 s and 10 s (section 6).
9. **R9 USB.** The detach with a host attached and the abrupt end of a stems stream; the CDC console ends. The detach must also stop the USB interrupt before the module clock goes.
10. **R10 Unsaved work.** The off loses it; the line warns; nothing is saved automatically (D3). A decision, not a defect (section 13, row 5).
11. **R11 A future watchdog.** It is off today (`README.md`, "Watchdog re-enable point"); when enabled, stage F must stop or feed it before the VLPR loop. Until then nothing but the global deadline (4.5) ends a stage that hangs after the commit.
12. **R12 Re-entrance and races.** A commit during a hold-again window, `reset` or `fw` in the middle of the sequence (refused, D2), a card event during stage C (`poll_card` held), two commits (the state machine runs once).
13. **R13 No persistent format changes**: none. No new file. The settings flush uses the existing file and version.
14. **R14 Real time and the audio path:** nothing blocking in the render or an ISR; the cost is one GPIO read a pass; the codec I2C writes are main-loop and short. **The audio path does change in P1**: a new `Mk66Audio::stop()` (there was no stop path), a new codec power-down plan, and a power-off latch in the main loop's stall check and in `open_wanted` (4.6). The block callback, the DSP and the voices do not change; no other use of `mute()` changes. The review covers it as Level C audio-path work.
15. **R15 HSRUN and the VLPR entry.** The boot leaves the unit in HSRUN (`boot.cpp:162`) and neither VLPR nor a stop mode may be entered from HSRUN (RF4); VLPR also needs the MCG in BLPE or BLPI and the core, bus and flash clocks inside their VLPR limits (RF7, RF8). Slice 2 switches the USB oscillator off, doubles the dividers in one step (the factor-of-2 rule of HSRUN, RM 16.4.3.3 p352), returns to RUN and waits for `PMSTAT`, switches the source to the crystal in RUN, sets the VLPR dividers, switches the MCG to BLPE, enters VLPR and waits for `PMSTAT` (4.4, steps 2-5), each wait poll-limited; a wait that ends at its limit gives `boot::reset_chip()`, never a half-entered state. SysTick (the millisecond clock) is stopped first, so waits are poll counts and times come from the DWT counter. The register facts are confirmed on paper (RF1-RF13); the sequence is unverified on a unit.
16. **R16 The audio stall latch and a reopen.** With the I2S stopped, the stall detector latches `kAudioFault` and the LED code after 300 ms, and `open_wanted`/`OpenRetry` would reopen the outputs (4.6). The power-off latch is its own flag, set at stage A, checked before the stall verdict and in `open_wanted`, never cleared.
17. **R17 Power held at the end of the sequence.** F0 waits for a stable release; a stuck or wrongly-polarised switch leaves the unit dark and awake (a log line; the cable pull is the exit). The wait is the user's, outside the global deadline.
18. **R18 A hold built from samples seconds apart.** Samples come once per main-loop pass, which a card mount (3 s) or an `unmute` (0.2 s) can delay. The gap rule (`kMaxGapMs`, section 3) restarts the debounce after a large gap; the idle hook does not poll PTC3.
19. **R19 A hung stage after the commit.** Input and console are locked and the watchdog is off. The global deadline (4.5) jumps to stage F; it does not bound a call stuck inside a driver, so each host call states its own bound.
