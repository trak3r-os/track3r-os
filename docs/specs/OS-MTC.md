# OS-MTC — MIDI Time Code out (A) and in (B)

Status: specified 2026-11-05, not implemented · Level C (a device setting appended to `settings.o3st`, the MIDI render path, the sequencer's timeline) · Backlog row OS-MTC, approved by the maintainer 2026-11-01 (option C: A, then B); order: after OS-MIDISYNC, before the INSFX slices S5 to S7 · Facts from `dev` at a6fc0b57 and the OS-MIDISYNC work in progress (`feat/OS-MIDISYNC` 9313887c: unbuilt, untested, local) · Everything this spec proposes is **new Community OS behaviour**: the official firmware sends and follows no MTC (fact F1).

## Maintainer decisions (taken 2026-11-05)

**Decided by the maintainer 2026-11-05: every recommended default (Q1 a, Q2 c, Q3 a, Q4 a, Q5 a, Q6 b), plus four questions asked afterwards, all with their recommended default:**

- **Q7 a, `settings.o3st`:** the device settings block grows from 26 to 32 entries (a version bump, a loader for the 246-byte files, a round-trip test); MTC OUT, MTC START and MTC IN are saved.
- **Q8 a, who owns the transport while MTC IN follows:** the master. The unit's Play, Stop, slot jumps and tempo knob do nothing; the screen shows `MTC IN: FOLLOWING`.
- **MTC OUT at the song's end (maintainer 2026-11-10, "como está"):** Song mode keeps looping back to slot 1 with a full frame 01:00:00:00 (Q6b); the unit does not stop at the song's end.
- **Q9 a, a time code past the end of the song (Song mode):** silence; the unit stays locked and waits until the master locates back inside the song (no loop, no stop). A time before the song start waits armed and starts exactly at MTC START; an empty slot inside the song is silence for its length.
- **Q10 a, Pattern mode with MTC IN:** position = the time modulo the pattern's length (the first loop at the project tempo, then the period the pattern's own tempo FX leave), so the master can loop one pattern without a song.

Only what the maintainer must decide. Every technical detail is decided in this spec and listed as an assumption (section 6).

## 1. Goal

Let a DAW that follows MIDI Time Code, and not MIDI Clock, follow the unit: Logic Pro is the case that asked for it (F14). **A, MTC OUT:** the unit sends quarter-frame messages from its sequencer timeline on the ports its clock uses (DIN and USB), and a full-frame message at Play and at a locate; the song time of a position is computed from the song start through its tempo changes. **B, MTC IN:** the unit follows an incoming time code: a time becomes a song position, the run follows the rate of the quarter frames. MTC carries no tempo, so in A the user sets the same tempo in Logic; in B the unit plays its own tempo.

**MTC itself** (MIDI 1.0 Detailed Specification, MIDI Time Code; documented standard): a quarter frame is `F1 0nnn dddd`, piece n = 0..7 carrying frames low/high, seconds low/high, minutes low/high, hours low, and hours high with the rate code (0 = 24, 1 = 25, 2 = 29.97 drop-frame, 3 = 30 fps). Eight pieces span two frames; the time they spell is the frame at which piece 0 was sent, so a receiver adds two frames when piece 7 arrives. Pieces go 0..7 when running forward, 7..0 in reverse. A full frame is the SysEx `F0 7F 7F 01 01 hh mm ss ff F7` (`hh` = rate code << 5 | hours), sent when locating, not while running. Quarter frames come 4 x fps times a second: 96, 100, 120 per second.

## 3. Design A: MTC OUT

### 3.1 Where the quarter frames are made

In the **sequencer, in the render context** (`Sequencer::step`), next to the clock (F4), and emitted as two new SeqEvent kinds at the end of the MIDI out group (F7): `MidiMtcQf = 28` (`a` = the data byte `0nnndddd`, `value` = the fraction of a sample, as MidiClock) and `MidiMtcFull = 29` (`value` = rate, hours, minutes, seconds, frames packed in 24 bits). The generator works on the **run's wall clock**, not on the song position: during a run, time code advances with the sample timeline whatever the tempo does (MTC has no tempo). It keeps an **anchor**, the pair (sample `s_a` on the timeline, song time `T_a` in samples from the song's first step); the time at sample `s` is `T_a + (s - s_a)` plus the MTC START hours. Quarter frame number `q` (counted from 00:00:00:00) is due at the exact Q32 sample where that time reaches `q x 11025 / fps` samples; its piece is `q mod 8` (so piece 0 always starts an even frame count and every 8-piece cycle is whole). The first quarter frame of a run is the first boundary at least 4 ms after the full frame (DIN has sent the full frame's ten bytes by then). At most one quarter frame falls in a 64-sample block (the shortest period is 367.5 samples), plus a full frame at a start, a relocation or a stop.

### 3.2 Song time (the map) — main loop

`seq/song_time.h` (new, pure, main-loop context; it reads the project the main loop owns): `song_time_at(project, mode, order, step)` returns the Q32 samples from the song start to the start of that step, plus the tempo and swing state there; `song_position_at(project, samples)` returns the first step that starts at or after a time, with its exact time and state. It walks the order list as the sequencer plays it: each slot's pattern length (the longest track), every track's row `k mod len_t` (polymetric tracks), the two FX columns of each row for the timing FX of F6, the step length of F5 with the same `core::samples_per_tick_q32` arithmetic and the swing pair parity from the run start, Break and Order jump followed as the sequencer does. It starts from the project tempo and swing (a run's start state). It does **not** know what is live: the performance tempo, half and double time, the tempo knob during a run, live switches and jumps. A walk is bounded (`kWalkCap` = 65,536 steps: a song that loops on itself through Order jump is cut there) and costs at most 16 tracks x 2 FX reads a step. A walk is done only when a run starts or relocates away from the song start, never per block.

### 3.3 The anchor protocol (render and main loop)

- **Fast path:** a segment that starts at the song's first step (Song mode slot 1 step 1, or step 1 of a pattern in Pattern mode) has `T_a = 0`: the render anchors at once, with no main-loop round trip.
- **Otherwise** the render publishes a request word (one writer, relaxed atomic, as `PlayPosition`): a segment stamp, the order position (0xFF in Pattern mode), the pattern id and the step. The main loop polls it once a pass while MTC OUT is on, calls `song_time_at` and pushes a new command `Command::Kind::MtcAnchor` (`a` = the stamp, `c` = `T_a` in whole samples: 32 bits hold 27 hours). The render takes an anchor only if its stamp is the current segment's; until it arrives the generator is silent (no wrong time is ever sent), then it sends the full frame and resumes quarter frames at the next boundary. The wait is one main-loop pass plus the walk (A1 measures the worst case).
- **Count-in** (OS-METRO): the anchor is set so that the first real step is at `T_a`; the count-in's steps carry the time code before it (a natural pre-roll, Q3). No time below 00:00:00:00 is sent: with MTC START 00 and a song-start Play the time code begins at the first step.

### 3.4 Output path

`MidiOut::send` routes both kinds to `clock_ports` with each port's OUT OFFSET, as the clock (F8). A quarter frame is a 2-byte system common message (DIN: a normal message, 0.64 ms on the wire; USB: code index 0x2, which `usb_cin()` already gives). A full frame needs SysEx on both ports: DIN through `DinEmitter::push_sysex` (F9); USB as four event words, code index 0x4, 0x4, 0x4 then 0x5 (`F7` alone), pushed in order into the message ring (F10: a new `usb_sysex_events()` in `message.h`). A `Staged` item carries the full frame's packed time and a kind flag in its existing bytes (no growth of the 256-entry staging queue). The flush hands the full frame to each port whole or not at all. With MTC OUT on, a Play begins one block later (`start_lead`, as with clock out on), so the full frame is due before the first step.

### 3.5 Timing and jitter budget

The source has no jitter (exact Q32 times, fraction of a sample carried). Each port adds its own: **USB** never early, 0 to 1 ms late (frame quantisation; mean 0.5 ms), plus 1 ms for each frame a full packet defers it (counted in `UsbMidiOut::Stats::deferred`). **DIN** waits for the byte in flight (at most 0.32 ms) and, as a message, behind the messages due before it: with no note traffic under 1 ms; behind a burst of notes it waits for the burst (16 notes are 15 ms). Acceptance: USB quarter frames as the host sees them within 2 ms peak to peak of a straight line (the 1 ms frame plus the host's read), `lateness_max` at most 1 ms and no deferral in the runs; DIN, in the host model, at most 1 ms late with clock and no notes. Time code, MIDI clock and notes come from one timeline, so they never drift apart; the OUT OFFSET moves all three together. DIN load at 30 fps: 240 bytes a second, 7.7 % of the wire. A priority lane for quarter frames on DIN (ahead of due notes, between messages) is not built; it is the follow-up if a DIN receiver complains (risk R1).

### 3.6 Real-time rules

The generator runs in `Sequencer::step` (render): no allocation, no I/O, no double (integer and Q32 arithmetic only), bounded (at most two events a block). The walk runs in the main loop only. Main to render: the command ring (SPSC, the main loop the one producer). Render to main: one relaxed word (the render the one writer). No interrupt changes in A: the DIN and USB consumers handle the new items as they handle any message.

### 3.7 Settings and UI

Two device settings appended by the documented rule (F12): **id 27 MTC OUT** (Off, 24, 25, 30 fps; default Off) and **id 28 MTC START** (00..23 h, default 01; Q2). (Written as ids 26 and 27: OS-MIDICCMAP S1 landed first, took 26 and made the raise 26 -> 32 itself, so A3 takes 27 and 28, B's MTC IN will be 29, the arena and the `mem_map.h` mirror do not move again, and the default file goes 254 -> 270 bytes, not 246 -> 262.) A file written before them reads with no entry skipped and Off / 01; a file with them read by the previous build has two entries it does not know (skipped and counted; saving there drops them). Default file 254 -> 270 bytes. Not learnable (a controller must not start a time code). `sync_config_from_settings` carries them into `MidiConfig` (`mtc_fps`, `mtc_hour`), the link into `Sequencer::Config` (`emit_mtc`, false in the offline export, F13). Config MIDI page (Q4a): MTC OUT and MTC START after TRANSP OUT; `kConfigRows` 10 -> 12 (9 -> 10 with CC MAP). The info line of the row says "time code for Logic and other DAWs; MTC has no tempo".

### 3.8 What relocates (Q6)

A full frame and a new anchor at: every run start (Play, Continue, an external Start or SPP + Continue), and, with Q6b, every Song-mode jump out of the song's own flow: the loop back to slot 1 (fast path), a live slot jump landing (OS-SONG1), a playhead jump (OS-PLAYCUR `LocateRow`), an SPP while running. Break and Order jump are the song's flow: the map walks them and the time runs on. At Stop: quarter frames stop and one full frame gives the stop time (Logic's playhead goes there). Nothing is sent while stopped otherwise.

## 4. Design B: MTC IN

### 4.1 Input

`InParser` learns two kinds: `MtcQf` (F1 and its data byte) and `MtcFull` (the 10-byte full frame, any device id; any other SysEx is still skipped); `InParser::Out::value` widens to 32 bits (an internal struct). Only the port chosen by the new setting **MTC IN** (Off, DIN, USB) is used; the other port's are passed through as today. Stamps are the ISR's, corrected by the port's input latency (F11). No interrupt change.

### 4.2 The chaser (`midi/mtc_in.h`, pure, render)

- **Reading:** pieces are collected in order; after a whole forward cycle (8 pieces, two frames) the time is known (plus two frames). Rates 24, 25, 29.97 drop-frame and 30 are decoded (drop-frame converted to real time); pieces in reverse order mean the master shuttles backward: not followed.
- **Rate and phase:** every quarter frame's stamp feeds a second `ClockDll` (the quarter frame is its "clock": the least-squares fit, the slewing loop, the drop-out and re-acquire rules already exist, F11). The chaser turns the loop's output into the master's time at any local sample, `T_m(s)`, and its rate against the unit's audio clock, `r_m` (1.0 for a master on the same clock; 0.999 for 29.97 non-drop sent as 30).
- **States:** Idle -> Reading -> Acquired (time known and the loop fitted, about 8 quarter frames) -> Armed (the start is scheduled) -> Locked (running) -> Freewheel (quarter frames missing for less than 4 frames: the run goes on at the last rate) -> back to Idle with a stop (4 frames without a quarter frame: the master stopped). A time that disagrees with the prediction by more than one frame, or a full frame while locked, is a **relocation**: stop, then re-arm at the new time (a gap of about the lock time). A master rate outside 0.94..1.06 is not followed (status `MTC RATE`).

### 4.3 Locate and start

When Acquired, the render publishes a request: a stamp and the master time at a near future sample, `T_m(now) + margin` (margin 50 ms, doubled on each retry). The main loop answers with `song_position_at(T - MTC START)`: the first step at or after it, its exact song time `T_P` and the tempo and swing state there (Q5a), as two commands (`ChaseState`: `b` swing, `c` tempo x 100; then `ChaseStart`: `a` stamp, `b` order << 7 | step, `c` `T_P` in samples). The render computes the local sample where the master reaches `T_P` and starts the run there, with the chased FX tempo and swing (a new start variant of the sequencer: an absolute start sample and a start state; today a start always uses the project tempo, F5). An answer that arrives too late (the start sample already past) is dropped and the request repeats with a doubled margin; a request unanswered for 500 ms (the main loop busy with the card) re-arms. A master time before the song start arms step 1 at `T = 0` (Logic's pre-roll is waited out); a time past the song's end plays the song modulo its length when SONG LOOP is on, else waits stopped (status `PAST END`). A full frame while stopped moves the cursor (a `Locate`), nothing plays.

### 4.4 Running: a rate trim, not a second timeline

The run uses the sequencer's own internal timeline, not the clock-follow path (which turns swing off, `sequencer.h:76-81`): the song plays its own tempo changes and swing. A new `Sequencer::set_rate_trim(r)` scales the samples per tick at every step boundary (where tempo changes already land); MIDI clock out follows the trimmed grid. The song time the unit has played is integrated per block (`T_u += n x r`); the error `e = T_u - T_m` drives `r = r_m x (1 - k x e)`, limited to +-6 % and slewed, so a phase error is pulled in over about a second and never jumps. Locked when `|e|` < 1 ms for 8 quarter frames.

### 4.5 Interplay

While MTC IN is not Off: the MIDI clock follow is off (CLOCK IN and CLOCK MODE Slave are ignored, the status says MTC), MTC OUT is muted (no echo between two devices), clock out as a Master follows the trimmed run. The user's Stop wins until the master stops or relocates; the user's Play while the master is silent plays on the unit's own clock, and a master that starts later takes over only once that run is stopped (the clock follow's rule (d), `midi_link.h:38-43`). A tempo change on the unit during a locked run (knob, Perform tempo, half or double time) moves the song away from the master's position until the next relocation; documented, not prevented.

### 4.6 Settings and status

**id 29 MTC IN** (Off, DIN, USB; default Off) appended by the same rule in B3 (room already made in A3); Config MIDI page, the twelfth row, after MTC START. `midi::SyncStatus` gains the chaser's state, the last time and the rate; the info line of the row shows `MTC 01:00:12:05 25 LOCKED` (or READING, FREEWHEEL, MTC RATE, PAST END). The console gets `mtc` (state, time, rate, error, relocations).

### 4.7 B3 notes (as built, 2026-11-07)

- **Setting id.** MTC IN is id 29 (A3 took 27 and 28 after OS-MIDICCMAP S1 took 26), appended by the append rule; the block already held 32 fields, so Q7 a's raise, version bump and loader were not needed (a round-trip test, `settings_format_test.cpp`, and the 270-byte file as a literal, `kFile29`, are there). The default file is 278 bytes.
- **Where the decisions of the maintainer win over 4.3 and 4.5.** Q9 a (a time past the song's end is silence, no loop, no stop) replaces 4.3's "plays the song modulo its length when SONG LOOP is on": `song_position_at(.., loop = false)` answers `past_end`, the sequencer's chase run stops at the end of the order list instead of looping, and the state is PAST END until the master relocates. Q8 a (the master owns the transport while MTC IN follows) replaces 4.5's "the user's Stop wins": while `Sequencer::chase_run()` the main loop's Play, Stop, Resume, Locate, LocateRow, QueuePattern, QueueJump, SetMode and SwitchPattern commands are dropped (counted in `Stats::chase_dropped`); Perform's tempo and half or double time are not dropped (4.5: documented, not prevented), the tempo knob does nothing because the chase pins the FX tempo and swing. A Play of the user while the master is silent is a run of the unit's own clock and is left alone (no request is made while the sequencer plays), the master takes over once it stops.
- **What a request carries.** The mode and pattern the unit would play (`Sequencer::select`), so the chase plays what Play would: Song mode, or Pattern mode (Q10: the walk loops the pattern; beyond `kWalkCap` steps, about 2.3 hours of a 16-step pattern at 120 BPM, a question is not answered and is asked again after 500 ms: the time modulo the pattern is not built).
- **Start state.** The answer carries the tempo and swing before the step's own FX (`SongPoint::tempo_in_x100`, `swing_in`: the Tempo fine of the step's row would otherwise count twice) and the swing pair's parity (`SongPoint::odd`), so a start at an odd step lasts what the map says. The run's first sample is the one at which the master reaches the step (the chaser's `sample_at_master_time`), at least 256 samples ahead, else the request is repeated with a doubled margin.
- **The controller.** Once a step the run reaches the song time `chase_map()` (the step's end, untrimmed) at the sample `chase_end()`; the master's time at that sample (`master_time_at`) gives the phase error e, and r = r_m x (1 - e / 1 s), limited to 0.94 .. 1.06 and to 3 % a step. The error is exact (no integration), the rate changes at step boundaries, where tempo changes already land. Locked when |e| < 1 ms for 8 quarter frames.
- **Stamp latency (B2's review note).** A step of 5 ms in the stamp latency for 3 quarter frames in a row now costs a Stop (the B2 review found it after the folds that made the chaser see a slowed source and a lost quarter frame: the slip bound and the rate gate trade against it; a jitter of +-2 ms is ridden out). With the chase the master's run stops, the chaser reads it again and the question starts over: a gap of about the lock time. A permanent phase step of 5 ms (the master's clock moved) is followed by the rate trim (`seq_mtc_chase_test.cpp`, as far as the test shows). The B1 tool's `--jitter` and `--drop` profiles are the means to find the real threshold on the unit; a looser slip bound is the first thing to try if a real USB host does this.
- **Unit status.** `SyncStatus::mtc_*` carries the state, the last time, the rate in ppm, the error in microseconds and the relocations; the Config row's card draws `MTC 01:00:12:05 25 LOCKED`; the console `diag mtc` adds the chase's counters. A full frame while the unit is stopped moves its cursor (`Sequencer::chase_locate`).
- **Sequencer size.** `static_assert(sizeof(seq::Sequencer) <= row + 768)` of app_main.cpp is raised to 896: B3 adds the answer, the run's phase pair, the rate trim and the flags, and A3 had left 24 bytes.
- **Relocation re-lock time — measured, an open maintainer decision (divergence from the acceptance above).** The acceptance says lock within 250 ms and a `jump` relocated within 300 ms. As built, a relocation waits for the chaser's fit to re-converge (160 quarter frames — at 25 fps 1.6 s; the ±2 ms jitter test does not exercise this path, so a shorter count was not tried) plus the 100 ms settle hold and the ask margin; the 2 s settle max hangs off the relocation itself, not off re-asks. Measured worst case from the relocation to the re-start's first step: **79,852 samples = 1.81 s at 44.1 kHz** (`seq_mtc_chase_test.cpp` asserts 80,000). Whether to shorten the re-convergence wait at the cost of the first steps' accuracy is the maintainer's call. **Decided by the maintainer 2026-11-10: keep it** ("dejar"): the re-lock stays at about 1.75 s (measured on unit b10: 1.74-1.75 s from the first quarter frame, from a `jump` and from a resume, phase within 0.3 ms mean once locked); the 250 / 300 ms limits of the acceptance are replaced by 2.0 s for lock and relocation.

## 6. Assumptions (decided here; each local, testable and reversible)

- A-1 Time code goes where the clock goes: `clock_ports` (MIDI OUT, or the project's CLOCK OUT), with each port's OUT OFFSET; it does not depend on CLOCK MODE or TRANSP OUT.
- A-2 Quarter frames are made in the sequencer (render) from the run's wall clock and an anchor (3.1); pieces are `q mod 8`; a run starts its quarter frames at any piece, at least 4 ms after its full frame.
- A-3 Song time is computed in the main loop on request (3.2, 3.3); the song-start fast path needs no round trip; the generator is silent rather than wrong while it waits.
- A-4 The map honours the timing FX of F6 and the project's tempo and swing at a run start; live tempo (Perform, half and double time, the knob), live switches and jumps are not in it. A walk stops at 65,536 steps.
- A-5 Pattern mode: the time of a step counts from step 1 of the pattern; pattern loops run on (Q6).
- A-6 A recording's count-in carries time code before the first step; no time below 00:00:00:00 is sent; the time wraps at 24 hours.
- A-7 Full frames: at a run start, at each relocation of Q6, and one at Stop with the stop time; none while stopped otherwise (a full frame when the cursor moves while stopped is a possible follow-up).
- A-8 With MTC OUT on, Play begins one block later (`start_lead`), as with clock out on.
- A-9 No time code from the offline export (`emit_mtc = false`).
- A-10 MTC OUT, MTC START and MTC IN are device settings, not learnable, not in the project file (like CLOCK MODE); MTC START also offsets the incoming time in B.
- A-11 No DIN priority lane for quarter frames in this item (R1).
- A-12 A Play from the middle of a song keeps today's start at the project tempo (F5) in A; B chases the tempo and swing at its own starts (4.3). A chase of Tempo and Swing FX at every Play from the middle is recorded as an IDEA, not built here.
- A-13 B: the follow uses a second `ClockDll` on quarter frames, a rate trim of the sequencer's own timeline (swing kept), freewheel up to 4 frames then stop, a relocation is stop then re-arm, reverse is not followed, rate limits +-6 %, start margin 50 ms doubling, request timeout 500 ms; the numbers are constants, tuned by B3's runs.
- A-14 B reads all four rates, 29.97 drop-frame included, whatever Q1 decides for the output.
- A-15 B: the clock follow is off and MTC OUT muted while MTC IN is not Off; the user's Stop and Play follow the clock follow's rules (4.5).
- A-16 A console command `mtc` (status; `mtc at <order> <step>` prints the map time and its cost) exists for the HIL steps.

## 7. Risks

- R1 **DIN quarter frames behind note bursts** (3.5): a dense chord delays a quarter frame by the burst. Measured only by a hands check (no DIN interface on the host). Mitigation: a priority lane in the emitter (between messages, ahead of due notes) as a follow-up, Level C (interrupt code).
- R2 **The map and the sequencer disagree** (a timing rule changed in one place only): the differential test of A1 over the corpus, and the guard on `kFxInfo`'s Row FX.
- R3 **Walk cost** on a 255-slot song from SDRAM: measured in A3 (8); the checkpoint cache if over 10 ms.
- R4 **USB SysEx coding** (code indexes, order across packets with real-time bytes between): host tests on the words; A2's tool decodes full frames through ALSA, which reassembles SysEx.
- R5 **The settings block raise** changes the arena size and its mirror: the static asserts, the settings literals of every older file, `qemu` before merge.
- R6 **Logic's behaviour** (lock time, pre-roll need, the 01:00:00:00 default in the current version, any frame-parity expectation): unknown until the maintainer's Logic check; Q3 and Q2 have fallbacks.
- R7 **B false relocations or stops** from a jittery USB host: thresholds measured with B1's jitter and drop profiles before merge.
- R8 **B start in the past** when the main loop stalls (card I/O): the retry with a doubled margin and the 500 ms re-arm; a test for both.
- R9 **The tempo knob during a locked chase** drifts the position (4.5): documented in the manual; a position-based correction is a possible follow-up.
