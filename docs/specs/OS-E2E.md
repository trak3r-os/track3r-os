# OS-E2E: an end-to-end test battery that uses the OS like a deep user

Status: **approved** (maintainer, 2026-10-18: "GO"). The design came from a Fable consult on two read-only surveys of the repo, and was trimmed by the maintainer. A planner checked the firmware boundary against the build files on 2026-10-18; nothing has been compiled yet. Classification: `new Community OS behaviour` (test tooling only; the image does not change).

## 1. Why

Facts from the catalogue, 2026-10-18 (569 `| QA-` rows in `docs/qa/catalogue/*.md`):

| Level | Rows |
|---|---|
| Passed on the unit | 44 |
| More testing needed | 411 (207 "more testing needed", 204 "unit open") |
| Passed in the simulator | 184 (screenshot hash only) |
| Passed in host code tests only | 315 |
| No pass anywhere | 31 |

- The simulator cannot assert, has no audio and no card. Every simulator check is a SHA-256 of the framebuffer.
- No test plays a whole journey: open, edit, play, export, reload.
- No test checks the whole audio output against a reference.
- The maintainer ended hands-on unit tests on 2026-10-17. Automation is how the open rows get verified.

## 2. Decisions (maintainer, 2026-10-18)

| # | Decision |
|---|---|
| D1 | **No firmware change.** New code lives only in `sim/`, `platform/host/`, `tests/`, `tools/` and `docs/`, plus host-only build scripts. Firmware code is called, never edited. Each slice proves it at merge (§3). |
| D2 | **No `stat drift`** and no other firmware hook. A unit soak, if one is ever done, polls the existing `diag cpu` with o3hil's `collect` and `stat`. |
| D3 | **On demand or at releases only.** The battery runs through `tools/ci.sh e2e`. A ctest label `e2e` keeps it out of `tools/ci.sh host` and out of GitHub CI. |
| D4 | **Release gate.** `tools/ci.sh e2e` joins the release checklist next to the full `tools/ci.sh` and `fw-gate-check`. A failing journey blocks the release. It starts with the release after `v0.7.0-alpha.1`. |
| D5 | **Audio correctness is in scope**, proven four ways: measured properties, reference players, null tests, and regression fingerprints (§5). |
| D6 | **Screen readability is in scope** (§6). |
| D7 | **Two cheap checks run on every push** (recommendation, kept unless the maintainer says otherwise): the catalogue gate (E2E-3, under 1 s), and the unit tests of the new tools (the sound-check maths and the card folder, milliseconds). |
| D8 | **The later slices are IDEA** until the maintainer moves them: E2E-6 MIDI journey, E2E-7 modules in the sim, E2E-8 format generators, E2E-10 random user, E2E-11 HIL re-scope, E2E-12 card and power chaos. |

## 3. The firmware boundary (D1)

- The MK66 image links `usb`, `platform_mk66_pure`, `audio`, `midi`, `hal`, `core`, `app`, `ui`, `eve`, `seq` and `model` (`platform/mk66/CMakeLists.txt`). `o3sim` and `o3os_tests` add `sim`, `platform_host` and `tests/`, which are not in the image.
- Proof at every slice merge:
  - `git diff --stat dev -- app audio core model seq formats ui eve midi usb module hal platform/mk66` is empty.
  - The release image `.hex` is byte-identical before and after.
- If a slice cannot be done without a firmware edit, the slice drops that part and records it as a latent gap. Example: if the stems tap has no public accessor, E2E-2 skips stems rather than add a getter.

- Add `tools/qa_cover.py` with `--check` (the ctest) and `--write`, plus a self-test. Register both in `sim/CMakeLists.txt`, which is host-only. Label `qa_cover` `static` and the self-test `python` in `cmake/O3osLabels.cmake`.
- In `tools/ci.sh` `scope_resolve`, map `docs/qa/*` and `tools/qa_cover.py` to `static`. Today a catalogue edit runs no test.
- Resolution rules:
  - **Sim cell:** `` `file` › `label` `` resolves to a `snap` name in `sim/scenarios/**`. A bare scenario name also resolves.
  - **Unit cell:** a JSON in `platform/mk66/tools/hil/`. The step is found by a `say` or `note` that contains the row ID or the label.
  - **Host reference:** free text, as today (`host PASS (\`x_test\`)`). The name resolves to `tests/<n>.cpp`, `platform/mk66/tests/<n>.cpp`, a ctest name or a `TEST_CASE` title. No new column.
- A row with no reference writes `manual: <reason>`. The legacy forms ("by hand", "manual (not scripted)") are accepted only on rows unchanged since the base.
- A row changed since the base needs at least one reference that resolves. The base is `$O3OS_QA_BASE`, else `git merge-base HEAD dev`, as in `tools/manual_check.py`. With no base, warn and skip this rule.
- The tool regenerates the `docs/qa/catalogue/README.md` index table between `<!-- qa-cover -->` markers. Functions are the rows minus the dropped ones; the PASS counts come from the Status words.

- **Acceptance:**
  - The self-test fails on a dangling label, a missing JSON, a changed row with no reference and a stale table.
  - The real catalogue passes.
  - The index matches the rows.

### E2E-5: screen readability

- The simulator's rasteriser (`sim/src/eve_raster.cpp`, host only) records every glyph it draws: bitmap handle, cell, position, size, colour and the scissor in force.
- A check runs over every gallery state and theme and fails when:
  - a glyph is cut by its scissor or by the screen edge;
  - a glyph overlaps another glyph;
  - a text colour pair is not in the theme contrast table (`tests/theme_test.cpp` holds the ratios).
- New worst-case gallery states: the longest project and instrument names, tempo 800, pattern 255, 64 instruments, both FX cells filled on every visible track, and the longest strip message.
- `tools/ci.sh e2e` writes a contact sheet of every screen to `build-e2e/<date>/screens.png`, for a look once per release.
- Known deliberate overlaps (a cursor over text, for example) go in a named allow list with a reason. The theme contrast tests already use this pattern for decorations.
- **Acceptance:**
  - A planted clipped label fails.
  - A planted overlap fails.
  - The current gallery passes, or each finding becomes a backlog row (`OS-BUG-*`), never a silent allow-list entry.

### E2E-2: audio in the sim

- Copy the wiring from `tests/audio_demo_test.cpp`, `tests/play_after_load_test.cpp` and `app_main.cpp`.
  - Set up the `Engine` with `attach_voices`, `attach_events(seq::event_source(...))` and `attach_live`, rendered by `render_block` directly.
  - The app gets `engine.params()` as its param ring.
  - Transport and preview are small sim sinks that push to the sequencer's command ring.
- New files: `sim/src/sim_audio.{h,cpp}`, `sim/src/audio_check.cpp` and `sim/include/o3os/sim/audio_check.h`.
- `audio on` builds the engine lazily. The fake `playhead` command is refused while audio is on.
- **Pacing:** an integer accumulator renders 0 or 1 blocks of 64 frames per 1 ms tick. That is deterministic, and real time on average.
- **`render <name> <ms>`** captures the master, and the stems if `audio/taps.h` exposes them publicly (§3). It writes `<name>.wav` into the report folder for listening.
- **`assert audio <name> <check>`** offers these checks:

  | Check | What it measures |
  |---|---|
  | `pitch=<Hz\|note>±<cents>c` | the fundamental |
  | `rms=<dB>±<d>`, `peak<dB` | level |
  | `dc<x` | DC offset |
  | `silent` | no sound |
  | `clicks=N` | second-difference outliers against the local MAD |
  | `onset=<ms>±<d>` | note timing |
  | `envelope=<model>` | the level curve against a model |
  | `centroid>`/`<` | brightness, to show a filter or a bit depth acts |
  | `pan=L\|R\|C±<dB>` | left/right balance |
  | `zipper=0` | spectral-flux spikes during a parameter sweep |
  | `alias<dB` | energy outside the harmonic bins of a high sine |
  | `null=<other>,<dB>` | the residual of A minus B |

- The check maths are pure functions over a sample vector. `double` is allowed in `sim/`, because the float ban covers only core, hal, eve, ui, app, model and formats.
- **Acceptance:**
  - `tests/audio_check_test.cpp` checks every measurement on synthetic sines, impulses, steps, sweeps and planted clicks.
  - `sim/scenarios/e2e/e2e_audio.txt` plays one note, asserts pitch, onset and peak, stops, and asserts `silent`.
  - Journeys stay under 2 s of audio each.
- Tolerances only, never sample hashes: float results are reproducible only on the same machine and compiler.

### E2E-4: audio fingerprints

- Each fingerprint is `tests/audio_fingerprints/<key>.json`, about 2 KB. Per 100 ms frame it stores 24 log-band energies, the onsets, the f0 track, and the peak, RMS, DC and click counts.
- A fingerprint fails when the maximum per-frame log-spectral distance is above 1.5 dB or the mean is above 0.5 dB, an onset moves more than 1 ms, or f0 moves more than 10 cents.
- `update_audio_fingerprints` works like `update_goldens`. It rewrites the files and writes `fingerprint_diff.md` (the frames and bands that moved) plus the WAVs.
- A guard rejects a fingerprint change unless the same commit touches `audio/`, `seq/`, `modules/` or the scenario. The commit body gives the reason.
- Who may accept a changed fingerprint: the reviewer, with the diff report. The maintainer decides keys that claim parity with the original firmware.
- **Built** (branch `feat/OS-E2E-4`, no firmware file touched: `git diff origin/dev HEAD -- app audio core model seq formats ui eve midi usb module hal platform/mk66 ':!*.md' ':!platform/mk66/tools/hil'` is empty). Files: `sim/include/o3os/sim/audio_fingerprint.h` and `sim/src/audio_fingerprint.cpp` (the print, the file, the rules, the report; the header has every definition), `band_levels_db` in `audio_check.{h,cpp}` (the band levels, on the FFT `assert audio` uses), the scenario line `fingerprint <render> [nof0]` (`scenario.{h,cpp}`: checks that the render has ended, no tick), `o3sim --fingerprints <dir> (--check-fingerprints | --update-fingerprints) [--fingerprint-diff <file>]` (`main.cpp`; `--twice` also compares the text of the two prints), `tools/update_audio_fingerprints.py` and the CMake target `update_audio_fingerprints` (one `o3sim` per opted-in scenario, at most 4, `--twice`; writes `<build>/sim/fingerprint/fingerprint_diff.md` and `wav/`), `tools/check_fingerprint_guard.py` (ctest `fingerprint_guard` and `fingerprint_guard_selftest`), tests `tests/audio_fingerprint_test.cpp` (14 cases, unit_audio). Keys, `tests/audio_fingerprints/<scenario>.json`: `e2e_audio_stems` (`mix` with `nof0`, `mix.t1`, `mix.t2`), `e2e_pro_session` (`song` with `nof0`, `song.t1`, `song.t2`, `perf.t4`), `e2e_og_migration` (`live.t1`, `again.t1`), `e2e_ref_303` (`acid`, `nof0`): 2.9 to 6.5 KB each (about 150 bytes a frame: 12 frames take 1.8 KB). Every `scenario_<name>` ctest compares its own key in the process that runs the journey (`--check-fingerprints`), so a fingerprint adds nothing to a journey's time (the analysis is about 0.04 s a render under the sanitizers: `e2e_pro_session` takes 9.4 s with its four renders, 9.2 s without); a scenario with no `fingerprint` line and a file of its name, or a line and no file, fails.
  **How the guard works** (`tools/check_fingerprint_guard.py`, in `ci.sh host` as the `static` ctest `fingerprint_guard`, 0.2 s): (1) the files and the scenarios pair up; (2) for every non-merge commit of `origin/dev..HEAD` (else `dev`, `origin/main`, `main`; `$O3OS_FP_BASE`; none: skipped, exit 77) that touches `tests/audio_fingerprints/<key>.json`, the same commit must touch a firmware source directory (`app/`, `audio/`, `core/`, `model/`, `seq/`, `formats/`, `modules/`, `module/`: a sound can come from the app, the model, the formats or the module host as well as from `audio/`), `sim/scenarios/**/<key>.txt` or the rig (`audio_fingerprint.*`, `audio_check.*`, `sim_audio.*`), and its message needs a body of at least two lines (trailers do not count); the uncommitted changes count as one more commit with no message. Self-tested on a scratch repository (`--self-test`: the cases above and each way to fail).
  **Differences from the text above, to confirm.** (1) One file a scenario (the key is the scenario's name), several renders in it, chosen by the scenario's `fingerprint` lines. (2) The band levels, peak, RMS, balance and DC of a frame are those of a Hann window of 200 ms centred on the frame (hop 100 ms), not of the bare 100 ms: with a plain cut, a note that a change moves by 0.5 ms across a frame boundary takes the frame from silence to a tone and fails it, which the 1 ms onset rule allows; measured with a test tone ending 0.5 ms later, the bare frames took frame 9 from silence (-120 dB) to a peak of -5.8 dB and failed, the windows moved the largest distance by 0.34 dB. (3) A band more than 50 dB under the loudest band of either frame counts as being at that level in the distance (the skirts of a window and the splash of an attack, 40 to 80 dB under the note, move by tens of dB with the phase of the attack; the floor was 40 dB in the first build and the review widened it to 50, so that a band between the two is judged: `kFpBandRangeDb`; no stored key changes, the floor acts only in the comparison). (4) f0 is YIN on each half of the frame, kept when the halves agree to 20 cents (a frame that changes note in the middle has none: YIN ties two equally steady notes and a tiny change breaks the tie the other way); a voiced/unvoiced flip fails; `nof0` drops the track for a chord or a resonant voice (the 303's estimate wanders by 10 cents on one note). (5) Additions to the rules, because the spectrum does not see them: peak, RMS and balance of a frame within 1 dB (the balance is new: the mid channel cannot see a swapped pan), DC within 330 steps (1 %: over 100 ms a half-scale 441 Hz tone has 60 steps of its last partial period, so only a real offset is a failure), the click count of a frame within a quarter of the larger (a clean frame must stay clean; a sawtooth's wraps count and move with the phase). (6) The guard also accepts the measuring rig (`audio_fingerprint.*`, `audio_check.*`, `sim_audio.*`), because a change of the analysis or of the engine's wiring in the simulator moves every print, and every firmware source directory above rather than only `audio/`, `seq/` and `modules/`; and a deleted file counts as a change. (7) The onsets are a peak follower (10 ms) that rises through -50 dB and 12 dB over its minimum since it was armed, armed again under a quarter of the peak since the onset: the pro session's sample track changes note with a 1 dB dip, so it has one onset (legato), the hat track six. (8) The commit body must give a reason in at least two lines (the guard checks that there are two, not what they say); who accepts a changed print is the reviewer, with `fingerprint_diff.md` and the WAVs, and the maintainer for a key that claims parity with the original firmware (none does yet).
  **Measured.** The same build gives the same text (`--twice` in every `scenario_e2e_*`, and `update_audio_fingerprints` twice leaves "4 keys, all unchanged"). A pad that is hit 1 ms later (it falls 1.5 ms later: the live note is taken at a block) fails on its onset (moved 1.48 ms), as the rule says; 0.5 ms and 0.2 dB (unit test) pass; 2 ms, 3 dB and 34 cents fail, each by its own rule. Not asserted by it: the f0 of a track that changes note inside a frame (the pro session's 75 ms steps), a legato note's start (see 7), anything under 50 dB below the loudest band.
  **Limits of the print** (review of OS-E2E-4). (1) The print is compared only by `ci.sh e2e` (the `e2e` label: the `scenario_e2e_*` ctests that opt in); `ci.sh host` runs the guard and the unit tests of the comparison but not the journeys. A batch that touches `audio/`, `seq/`, `modules/` (or anything that plays) therefore runs `tools/ci.sh e2e` before it merges. (2) The sustained keys pin timing weakly: only `acid` (49 onsets) and `perf.t4` (6) have many onsets, and the onset rule is the only one that sees a note moved in time; `mix`, `song`, their stems and the OG-migration renders have one or two onsets each (held notes and chords), so a sequencer that shifts a note inside a held sound can move their levels and spectra by less than the tolerances. (3) The baselines belong to one machine and one compiler: the prints are the output of `libm` (`sin`, `pow`, `log10`), the FFT and the engine's float arithmetic, rounded to 0.1 dB, so another libc, an `-ffast-math` or FMA contraction change, or a different compiler version can move a band by a rounding step; `update_audio_fingerprints` twice leaves the files unchanged on the same build only. A key that moves with no source change is a toolchain change: re-baseline it in the commit that changes the toolchain, with that reason in the body.

## 5. What "sounds as it should" means (D5)

| Way | Proves | Slice |
|---|---|---|
| Measured properties | right note, time and level; no clicks, DC or silence; filters, envelopes, pan and bit depth act | E2E-2 |
| Reference players | imports and models play like the format's reference player | E2E-9 |
| Null tests | export = playback, stems summed = master, reload = same sound, live = offline | J2 and E2E-2 |
| Fingerprints | a sound that passed has not changed without a reason | E2E-4 |

What stays outside the battery:
- Taste ("does it sound good") is the maintainer's ear.
- The analogue path: USB audio captures the digital signal before the codec, so the codec and jacks keep an occasional by-ear check.
- Sound parity with the original firmware stays an `open research question` until recordings of an official unit exist as evidence.
